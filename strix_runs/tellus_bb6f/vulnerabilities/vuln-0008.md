# CVE-2026-39244 in adm-zip 0.5.16 (DoS via crafted ZIP — unbounded memory from spoofed size header)

## Description

The direct dependency **`adm-zip@0.5.16`** (declared in `package.json` and pinned via `pnpm-lock.yaml`) is affected by CVE-2026-39244: `zipEntry.js` line 103 allocates `Buffer.alloc(_centralHeader.size)` from the ZIP central-directory declared uncompressed size **without validating it against the actual compressed data or imposing an upper bound**, so a crafted ZIP with a manipulated size header causes excessive memory allocation and denial of service. Fixed in `0.6.0`. References: upstream commit `cthackers/adm-zip@2450dcf`, issue #568, Red Hat CVE advisory.

## Evidence

**Advisory evidence:** `CVE-2026-39244` applies to `adm-zip` at installed version `0.5.16`. The advisory is fixed in `0.6.0`.

**Usage analysis:** not imported by application code. No import of `adm-zip`/`AdmZip` exists in application code or scripts. `rg -n -e "AdmZip" -e "adm_zip" -e "admZip" -e "require\(['\"]adm-zip|from ['\"]adm-zip"` over `--type ts --type js` (excluding node_modules, dist, maps) returned only matches inside `package.json`, `pnpm-lock.yaml`, and `ops/sbom/sbom-*.json` inventory — no code. The app does ZIP work via the system `unzip` binary instead (src/services/zipUploadService.ts:43,58 use `execFileAsync('unzip', ...)`). This does NOT prove safety (dynamic require/reflection could still load it) but no static import was found. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

If `adm-zip` is loaded and handed a crafted archive, the process allocates attacker-controlled buffer sizes, exhausting memory and crashing the Node.js service. Availability impact only. Current code does not import the package, so the sink is latent until used.

## Technical Analysis

**Root cause:** `adm-zip` trusts the central-directory "uncompressed size" field to size a `Buffer.alloc` without cross-checking against actual data, allowing arbitrary memory allocation from a tiny archive.

**Package relationship:** `Relationship: DIRECT` in the trivy graph; declared in `package.json` dependencies as `adm-zip@^0.5.16`; pinned in `pnpm-lock.yaml` at `0.5.16`. Despite being a direct dependency it is currently **unused** by application code (the app shells out to the `unzip` CLI in `src/services/zipUploadService.ts`).

## Remediation

Two acceptable fixes:
1. **Preferred** — since the package is not imported anywhere, remove the dead dependency: delete `"adm-zip"` from `dependencies` in `package.json`, run `pnpm install`, commit the lockfile. This eliminates the vulnerable code entirely.
2. If it must remain, bump `"adm-zip"` in `package.json` to `^0.6.0`, `pnpm install`, commit lockfile, and verify with `trivy fs pnpm-lock.yaml`.
