## Description

The transitive package **`tar@7.5.13`** (pinned via `pnpm-lock.yaml` through `duckdb`'s `@mapbox/node-pre-gyp`) is affected by CVE-2026-59873: node-tar does not enforce hard upper bounds on total decompressed data, entry counts, or decompression ratio in extraction/parsing paths (`src/extract.ts`), so a small crafted gzip bomb can exhaust disk space and CPU. Fixed in `7.5.19`. This is the highest-severity of the tar CVEs on this pinned copy (severity CRITICAL per trivy, advisory vector 7.5 A:H). References: Red Hat errata RHSA-2026:47058/:47060.

## Evidence

**Advisory evidence:** `CVE-2026-59873` applies to `tar` at installed version `7.5.13`. The advisory is fixed in `7.5.19`.

**Transitive dependency:** introduced by the direct dependency `duckdb@1.4.4`.

**Dependency chain:** `duckdb@1.4.4 > @mapbox/node-pre-gyp@2.0.3 > tar@7.5.13`

**Usage analysis:** imported by application code; affected API usage unconfirmed. No application code imports `tar` directly (`rg -n "require\(['\"]tar['\"]|from ['\"]tar['\"]"` over `--type ts` on src/ returned no hits). It is reached only through `duckdb`'s `@mapbox/node-pre-gyp` install/extract step. `duckdb` itself IS imported by application code at src/services/furnaceSqlService.ts:55 (`require('duckdb').Database`) and src/services/duckdb/pool.ts:49. Affected-symbol (`tar.x/tar.t`) check inside node-pre-gyp was not performed. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

A crafted tar/gzip archive without decompressed-size limits can consume unbounded disk and CPU. In this project the `tar` code sits behind `duckdb`'s binary-delivery (`@mapbox/node-pre-gyp` downloads a prebuilt duckdb native binary as a tarball at package install/rebuild), so the realistic trigger is a compromised or hostile binary-distribution channel rather than direct end-user input — an availability-destructive primitive in the build/runtime bootstrap path.

## Technical Analysis

**Root cause:** node-tar < 7.5.19 places no hard caps on decompressed total size, entry count, or expansion ratio in `extract`/parse paths, enabling gzip-bomb exhaustion.

**Dependency chain (`pnpm-lock.yaml`):**
```
duckdb@1.4.4(encoding@0.1.13) > @mapbox/node-pre-gyp@2.0.3 > tar@7.5.13
```
`duckdb@1.4.4` is a direct dependency in `package.json` and is `require`d in `src/services/furnaceSqlService.ts:55` and `src/services/duckdb/pool.ts:49`. `@mapbox/node-pre-gyp` is the binary-fetch layer that uses `tar` to unpack the prebuilt duckdb native binding.

## Remediation

`tar` is transitive (under `duckdb`), so fix at the direct level or via override:
1. Bump the direct `duckdb` dependency in `package.json` to a release whose node-pre-gyp closure resolves `tar@>=7.5.19`, then `pnpm install`; or
2. `pnpm.overrides: { "tar@<7.5.19": "^7.5.19" }` in `package.json` to force the transitive resolution.
3. Commit lockfile, verify with `trivy fs pnpm-lock.yaml`. One bump to ≥7.5.21 also clears the sibling tar CVEs (59874/59871/59875) filed separately.
