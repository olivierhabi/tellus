# IDOR: authenticated users read arbitrary projects and dataset file contents (dataset RBAC disabled by default + default-org auto-enroll voids project read isolation)

**ID:** vuln-0011
**Severity:** MEDIUM
**Found:** 2026-08-18 06:39:32 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/datasets/:datasetId/download
**Method:** GET
**CWE:** CWE-639
**CVSS:** 6.5
**Fix Effort:** Medium

## Description

The Ontology Engine's dataset read endpoints (`GET /api/v1/datasets/:datasetId`, `/preview`, `/download`, `/status`, `/summary`) and project read endpoints (`GET /api/v1/projects/:id`, `/:id/stats`, `/:id/folders`, `/:id/datasets/all`, `/:id/members`) enforce no object-level authorization. Any authenticated user — even one with zero roles and no project membership — can read arbitrary projects and exfiltrate the full contents of any uploaded dataset file by direct object ID (IDOR / Broken Object-Level Authorization). Only write operations are correctly gated.

## Evidence

All requests issued as `cypress-nogroups@tellus.local` (sub `bcd2551e-b985-4d6f-97ff-e0e087a87e20`), a user with only `offline_access` + `default-roles-tellus` and no membership in the victim project `f33e3cec-2676-416f-a095-04e3de11f2ed`.

Project read (HTTP 200):
```json
{"id":"f33e3cec-2676-416f-a095-04e3de11f2ed","owner_id":"5ecbd5cf-...","name":"admin-private"}
```

Dataset list (HTTP 200):
```json
[{"id":"5f8376fa-ae7a-4a2e-95c6-d71da62ba247","name":"admin-secret.csv"}]
```

Preview (HTTP 200):
```json
{"rows":[{"a":"1","b":"SECRET","c":"ADMIN_DATA"},{"a":"2","b":"TOP","c":"SECRET"}]}
```

Download (HTTP 200, raw body):
```

1,SECRET,ADMIN_DATA
2,TOP,SECRET
```

Members (HTTP 200):
```json

```

Write contrast (HTTP 403):
```

```

## Impact

Full contents of any uploaded dataset file are readable cross-user by any holder of a valid bearer token. Project metadata (owner, members' emails/roles), folder trees, datasets lists, stats, and summaries for arbitrary projects are likewise exposed. Confidentiality of all stored file data is broken; only integrity is preserved because write paths (PUT/DELETE project, POST folder/members, upload) correctly return 403/404 for the same actor. No special role, project membership, or org sharing is required beyond authentication.

## Technical Analysis

Root cause is two-part.

**Part A — dataset by-id reads have no object-level authorization by default.**
`src/routes/foundryDatasets.ts:36` mounts `datasetRouter.use(dataPlaneGuard({ post: 'write' }))`. In `src/middleware/requireRole.ts:150-160`, `dataPlaneGuard` short-circuits ALL GET/HEAD/OPTIONS with an immediate `next()` — it only gates DELETE (ontology-admin) and POST/PUT/PATCH (ontology-write). Reads therefore pass with no principal/object binding. The only object-level guard is `requireDatasetRole('viewer')` on routes lines 43-50, but it is OPT-IN: `src/services/datasetAcl.ts:208-209` `isDatasetRbacEnabled()` returns true only when `process.env.DATASET_RBAC_ENABLED === 'true'`; it defaults to `"false"` and is not set in `.env` or any docker-compose file. When disabled the middleware no-ops (`if (!isDatasetRbacEnabled()) return next();`). Net effect: dataset reads are authenticated-but-unauthorized → IDOR.

**Part B — the project/folder membership read-boundary is a no-op.**
`src/services/projectService.ts:127-129` `listProjects` and `:146-160` `getProjectById` use `orgSharedProjects()` / an EXISTS subquery joining `project_organizations`↔`user_organizations`. But `src/foundryMigrate.ts` (B4 Step 19 backfill ~1264-1271 and Step 19b auto-enroll triggers ~1289-1315) seeds ONE shared org `00000000-0000-0000-0000-000000000001` ("default") and auto-enrolls EVERY user and EVERY project into it via `enroll_user_default_org()` and `enroll_project_default_org()` AFTER INSERT triggers. The org-membership EXISTS predicate is therefore trivially true for every (user, project) pair — "org-shared read" is effectively global read, and project-based reads (`/folders`, `/datasets/all`, `/members`, `/stats`) inherit it.

Writes remain correctly gated by `authorizeRoles('owner'/'editor')` and `owner_id` checks in ProjectService/FolderService, confirming the read-side org shortcut was never meant to be the enforcement point.

Both a zero-role user (`cypress-nogroups@tellus.local`, realm_access.roles = only `offline_access` + `default-roles-tellus`, not in `project_members`, in no legitimate shared org) and a `marking:PUBLIC`-viewer context were validated; the IDOR reproduces for both against the admin's private project `f33e3cec-2676-416f-a095-04e3de11f2ed`.

## Proof of Concept

1. As admin, create a private project and note its project id (victim: `f33e3cec-2676-416f-a095-04e3de11f2ed`).
2. As admin, upload a CSV (e.g. `admin-secret.csv`) so it becomes a dataset (id `5f8376fa-ae7a-4a2e-95c6-d71da62ba247`).
3. Mint a bearer token for a non-member, zero-role user (`cypress-nogroups@tellus.local`) from Keycloak (realm `tellus`, client `tellus-frontend`).
4. As that user, `GET /api/v1/projects/{projectId}` → HTTP 200 with full project JSON including `owner_id`.
5. `GET /api/v1/projects/{projectId}/datasets/all` → HTTP 200 listing the admin's dataset.
6. `GET /api/v1/datasets/{datasetId}/preview` → HTTP 200 returning row data containing `SECRET` / `TOP` / `ADMIN_DATA`.
7. `GET /api/v1/datasets/{datasetId}/download` → HTTP 200 returning the raw file body verbatim.
8. `GET /api/v1/projects/{projectId}/members` → HTTP 200 revealing the admin's email and owner role.
9. Contrast: attempt `PUT /api/v1/projects/{projectId}` as the same user → HTTP 403 FORBIDDEN, proving writes are gated and the flaw is read-only.

## Code Analysis

**Location 1:** `src/services/datasetAcl.ts` (lines 208-209)
  Fail-closed per-dataset RBAC (secure-by-default)

  **Suggested Fix:**
```diff
-   // callers. Enable with DATASET_RBAC_ENABLED=true.
-   return (process.env.DATASET_RBAC_ENABLED ?? "false").toLowerCase() === "true";
+   // callers. Disable explicitly with DATASET_RBAC_ENABLED=false (NOT recommended).
+   return (process.env.DATASET_RBAC_ENABLED ?? "true").toLowerCase() === "true";
```

**Location 2:** `src/routes/foundryDatasets.ts` (lines 31-36)
  Guarded dataset read surface (dataPlaneGuard GET passthrough context)
  ```
  export const datasetRouter = Router();
  // Function-level authorization on the by-id dataset surface (the IDOR
  // vector): update (PUT) requires ontology-editor, delete requires
  // ontology-admin, and write-POSTs (duplicate/reparse) require editor. Reads
  // (get/preview/download/status/summary) stay open. PATs are scope-gated
  // upstream (datasets:* scopes); superadmin passes.
  datasetRouter.use(dataPlaneGuard({ post: 'write' }));
  ```

**Location 3:** `src/services/projectService.ts` (lines 127-134)
  Require project membership for listProjects instead of org overlap

  **Suggested Fix:**
```diff
-   async listProjects(ownerId: string, fields?: string[]) {
-     const query = this.knex('projects').where((qb) => {
-       qb.where({ owner_id: ownerId }).orWhereExists(this.orgSharedProjects(ownerId));
-     });
-     if (fields && fields.length > 0) {
-       query.select(fields.map(f => `projects.${f}`));
-     }
-     return query.orderBy('updated_at', 'desc');
-   }
+   async listProjects(ownerId: string, fields?: string[]) {
+     const query = this.knex('projects').where((qb) => {
+       qb.where({ owner_id: ownerId }).orWhereExists(this.projectMembership(ownerId));
+     });
+     if (fields && fields.length > 0) {
+       query.select(fields.map(f => `projects.${f}`));
+     }
+     return query.orderBy('updated_at', 'desc');
+   }
+ 
+   // Projects the user is an explicit member of (project_members), not merely
+   // org-overlapping. Org overlap alone is NOT sufficient for read access.
+   private projectMembership(userId: string) {
+     return this.knex('project_members')
+       .select(this.knex.raw('1'))
+       .whereRaw('project_members.project_id = projects.id')
+       .where('project_members.user_id', userId);
+   }
```

## Remediation

1. Gate ALL dataset read routes on object-level authorization by making per-dataset RBAC fail-closed: default `DATASET_RBAC_ENABLED` to true (or remove the opt-in entirely) so `effectiveRole()` is always enforced and a null role returns 403.
2. Stop auto-enrolling every user and every project into a single shared default org; only enroll entities into real orgs they actually belong to.
3. Change `ProjectService.listProjects` / `getProjectById` (and the folder/dataset/members/stats reads that inherit them) to require `project_members` membership or an explicit share grant rather than org overlap; treat org overlap as additive to membership, never a replacement for it.
4. Add integration tests asserting that a non-member / zero-role user receives 403/404 on project and dataset reads, so the boundary cannot silently regress to fail-open.

## Assumptions

App runs with NODE_ENV=development and DATASET_RBAC_ENABLED unset (default false), matching docker-compose.override. Keycloak realm `tellus` is seeded with cypress users per the bootstrap scripts. Exploitation requires only a valid bearer token — no special role and no project membership.
