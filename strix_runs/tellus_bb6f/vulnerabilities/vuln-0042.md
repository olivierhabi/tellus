# Unauthenticated Remote Code Execution via code-repositories working-tree function invoke (vm sandbox escape to host command execution)

**ID:** vuln-0042
**Severity:** CRITICAL
**Found:** 2026-08-18 07:13:55 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/code-repositories/:rid/functions/invoke
**Method:** POST
**CWE:** CWE-94
**CVSS:** 9.8
**Fix Effort:** Medium

## Description

The working-tree function invoke endpoint `POST /api/v1/code-repositories/:rid/functions/invoke` accepts raw TypeScript `inlineSource` and executes it server-side while requiring **no credentials at all**. Because authentication is not enforced for this route in the running configuration and the code runs in a Node `vm` that is trivially escaped, any remote unauthenticated attacker achieves arbitrary OS command execution as the host user running the API (validated: `uid=501(olivierhabimana)` on the developer's macOS host).

## Evidence

**(a) Zero-credential escape** (no Authorization header), response HTTP 200:


**(b2) `Authorization: Bearer garbage.token.here`** — HTTP 200:
```json

```

## Impact

Full remote code execution on the host running the tellus API without any authentication. The PoC executes `id && hostname && sw_vers` on the target and returns the output of the live host (macOS 26.3.1, user `olivierhabimana`). An attacker can read/write files, exfiltrate the database via the app's own PG credentials, pivot into the network, or destroy the environment.

## Technical Analysis

**1. Unauthenticated admission.** The route `POST /api/v1/code-repositories/:rid/functions/invoke` is mounted under the `/api/v1/code-repositories` prefix, which `src/middleware/globalAuth.ts` (line ~195) allowlists globally. Its own guard `requireCodeReposAuth` (src/services/codeRepos/middleware/principal.ts) substitutes a dev "fallback principal" when `CODE_REPOS_TEST_AUTH=1` and `NODE_ENV != production`. Live proof: a request with **no** `Authorization` header and a request with a deliberately garbage Bearer token both return HTTP 200 with `{"result":"42"}` — the invoke is reachable with zero credentials.

**2. No publish/authorization gate.** The handler accepts `inlineSource` (raw source, "edit-and-run without commit") and executes it immediately. The `authorizePublish()` boundary in `executionPolicy.ts` is only wired into the *registry publish* endpoints, not this working-tree invoke. So arbitrary code runs with no publish authorization whatsoever.

**3. Node `vm` sandbox escape.** Execution flows through the worker-pool / `runSandboxed` path built on Node's `vm` module, which shares the host heap. The classic constructor-chain escape `globalThis.constructor.constructor("return process")()` returns the real host `process`; from there `require("child_process")` yields arbitrary command execution. The documented mitigations (require shim, env whitelist, no process/fs) do not stop this escape.

See the sibling report for the companion registry-publish primitive; this report covers the invoke + escape chain reachable without any credentials.

## Proof of Concept

1. Send a benign probe with NO `Authorization` header to the invoke endpoint and observe HTTP 200 `{"result":"42"}` (proves no auth).
2. Repeat with `Authorization: Bearer garbage.token.here` and again observe HTTP 200 (proves auth is not enforced, not merely a token-less fallback).
3. Send the sandbox-escape payload in `inlineSource` with no credentials.
4. Observe the response `result` field containing the host's `id`, `hostname`, and macOS version output — arbitrary commands executed as the host user.

## Remediation

1. Require real authentication for every code-repositories sub-route: remove the `/api/v1/code-repositories` global allowlist entry in `globalAuth.ts` and delete the dev "fallback principal" substitution in `requireCodeReposAuth` so no unauthenticated request is ever granted an always-authorized synthetic identity. Restrict test-mode principal synthesis to an explicit `X-Tellus-Test-Principal` header under `isTestAuthBypassEnabled`, and never give the synthesized principal publish-capable roles.
2. Gate working-tree / `inlineSource` execution behind the same `authorizePublish()` boundary used by the registry publish endpoints, so server-side code execution requires explicit authorization (the executor is documented as NOT an untrusted-code sandbox).
3. As defense-in-depth, add a sandbox guard that rejects constructor-chain escapes (`globalThis.constructor.constructor`, the `Function` constructor) for untrusted sources, and move inline execution exclusively into the worker-pool / locked-down subprocess.
4. Extend the production boot assertion (`assertNoTestAuthInProduction`) with a check that no route admits anonymous code execution, so the dev toggles can never silently reach production.

## Assumptions

No prerequisites — the chain is proven with zero credentials. The running deployment has `NODE_ENV=development` and `CODE_REPOS_TEST_AUTH=1` active (per the app's `.env`); the production boot assertion (`assertNoTestAuthInProduction`) would fail closed if those toggles were promoted to production, so real-world exploitability depends on the operator not carrying the dev toggles into production. The `vm` sandbox-escape primitive is environment-independent and remains valid even where authentication is correctly enforced — any low-priv authenticated user reaches the same code execution (also validated with a zero-role JWT).
