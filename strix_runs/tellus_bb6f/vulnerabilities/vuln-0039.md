# IPv6 Literal Canonicalisation Mismatch Permanently Blocks Webhook Delivery to IPv6 REST Source Hosts

**ID:** vuln-0039
**Severity:** MEDIUM
**Found:** 2026-08-18 06:58:16 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/connectivity/webhooks/:webhookRid/test
**Method:** POST
**CWE:** CWE-178
**CVSS:** 4.3
**Fix Effort:** Trivial

## Description

The connectivity webhook executor rejects any call whose REST source domain is an IPv6 literal because two layers of the stack normalise the host differently: WHATWG `URL.hostname` keeps the brackets (`[::1]`) while the connection's persisted egress-allowlist host entry stores the bare literal (`::1`). `assertConnectionAllows` (executor.ts:414-421) does a verbatim `entry.host.toLowerCase() === hostname.toLowerCase()` and throws `EGRESS_POLICY_BLOCKED` before any socket is opened. A connection whose ONLY approved target is the IPv6 host therefore can never execute any webhook — the user-approved egress policy is unreachable, breaking the feature and silently preventing legitimate automation for any IPv6-addressed internal REST source (the exact deployment shape the `::1` / ULA / link-local entries in `CONNECTIVITY_EGRESS_ALLOW_RESERVED` exist to support).

## Evidence

Live response (verbatim JSON from the pre-fix run):

```json
{
  "status": "failed",
  "errorCode": "EGRESS_POLICY_BLOCKED",
  "errorMessage": "The source egress policy does not allow [::1]:9000."
}
```

After patching `assertConnectionAllows` (executor.ts:414-421), the same request advanced to the next gate with a different error class:

```json
{
  "status": "failed",
  "errorCode": "EGRESS_URL_BLOCKED",
  "errorMessage": "Host '[::1]' is not in the egress allowlist. Allowed: ::1."
}
```

The progression from `EGRESS_POLICY_BLOCKED` to `EGRESS_URL_BLOCKED` proves the first gate was misfiring on canonicalisation, not on policy intent. After the second patch (executor.ts:1143), the request would proceed to the DNS/transport layer. The running Docker container serves compiled `dist/` code that is not rebuilt in the sandbox, so the live retest demonstrates the first patch in isolation; the second patch is verified by source inspection (no other `.map((entry) => entry.host.toLowerCase())` sites remain in the file).

## Impact

Loss of availability for the affected integration path. An operator who configures a REST source domain as an IPv6 literal (loopback `::1`, ULA `fc00::/7`, link-local `fe80::/10`, or IPv4-mapped `::ffff:a.b.c.d`) can create the connection, pass validation, pass the per-connection egress-allowlist, and still have every webhook invocation fail with `EGRESS_POLICY_BLOCKED`. The failure is silent to the operator: no configuration error is surfaced at create time, and the runtime error message (`The source egress policy does not allow [::1]:9000`) incorrectly blames the policy rather than the canonicalisation bug. Because the feature is intended to support IPv6 internal targets (as evidenced by `CONNECTIVITY_EGRESS_ALLOW_RESERVED` explicitly allowing `::1` hostnames), this is a feature-breakage defect, not a data-disclosure or authorisation bypass.

## Technical Analysis

`executeCall` (src/services/connectivity/webhooks/executor.ts:776) resolves the URL:

```typescript
const url = new URL(path, base);
```

WHATWG URL spec returns `url.hostname` for an IPv6 literal WITH brackets, e.g. `"[::1]"`. `assertConnectionAllows` (same file, lines 410-425) compares that against `entry.host.toLowerCase()` where `entry.host` comes from the connection's `egressPolicy.allowlist`. The connection's allowlist entry was validated at create-time by `EgressEntry` (src/services/connectivity/contracts.ts:181-185) as `z.string().min(1)` — no canonicalisation. An operator writes `::1`; the executor compares `"[::1]" === "::1"` → false → `EGRESS_POLICY_BLOCKED` thrown at executor.ts:813.

The same code path is hit for every IPv6-literal `baseUrl`. Hostname-based (non-literal) and all IPv4-literal domains are unaffected, so the bug is invisible in the common case. A second, identical mismatch exists at executor.ts:1143 where `safePolicy.allowedHosts` is pre-normalised from the same raw entries — after fixing `assertConnectionAllows`, the same request would then hit `assertEgressUrl`'s `FORBIDDEN_HOST` check against a raw `::1` entry while the URL hostname is `[::1]`. Both sites must be canonicalised for the gate to work end-to-end.

The audit note in the connectivity code refers to "hostname case-insensitivity" but not to bracket canonicalisation; no unit test covers an IPv6-literal domain. The PostgreSQL connector already handles this correctly (`isEgressAllowed` in postgresql/egress.ts strips brackets via `replace(/^\[/,"").replace(/\]$/,"")`) — the webhook executor was the only outbound path that did not.

## Proof of Concept

1. As any user with `connectivity:test` (or `connectivity:write`) scope, create a REST-API connection whose domain is `baseUrl=https://[::1]`, port 9000, and an egress-policy allowlist entry `{kind: "host", host: "::1", port: 9000}`.
2. Create an active webhook on that connection with a GET call, `domainIndex=0`, `relativePath="minio/health/live"`, and a `wholeResponse` output.
3. POST to `/api/v1/connectivity/webhooks/<webhookRid>/test` with `{"inputs":{}}`.
4. Observe `execution.status=failed`, `errorCode=EGRESS_POLICY_BLOCKED`, `errorMessage="The source egress policy does not allow [::1]:9000."`
5. The socket is never opened; the failure occurs inside the executor before any network activity.

## Remediation

Normalise both sides of the egress-allowlist comparison by stripping one pair of surrounding square brackets before the case-insensitive match, matching the idiom already used in `src/services/connectivity/connectors/postgresql/egress.ts::isReservedTarget`. Apply the same normalisation when projecting the allowlist into the `SafeEgressPolicy.allowedHosts` array at the top of `executeWebhook`, so that two consecutive gates (`assertConnectionAllows` and `assertEgressUrl`) evaluate the same canonical form. Add a unit test that creates a connection with baseUrl `https://[::1]` and allowlist host `::1`, then asserts the webhook executor reaches the DNS/transport layer rather than failing at the policy gate.

## Assumptions

`connectivity:test` or `connectivity:write` scope on the tenant is available to the caller. The operator legitimately wants to address an IPv6 REST domain — the feature explicitly supports `::1` via `CONNECTIVITY_EGRESS_ALLOW_RESERVED`. The bug is a canonicalisation defect, not a security boundary failure; no data exposure or unauthorised egress is enabled by it.
