## Description

The direct dependency **`uuid@13.0.0`** (pinned via `package.json` and `pnpm-lock.yaml`) is affected by CVE-2026-41907: `v3`, `v5`, and `v6` accept an external output buffer + offset but do not reject out-of-range writes (small `buf` or large `offset`), allowing silent partial writes into caller-provided memory. Fixed in `14.0.0` (also patched at `11.1.1`, `12.0.1`, `13.0.1`). References include upstream fix commits `uuidjs/uuid@32389c8` and `@3d2c5b0`.

## Evidence

**Advisory evidence:** `CVE-2026-41907` applies to `uuid` at installed version `13.0.0`. The advisory is fixed in `13.0.1`.

**Usage analysis:** the advisory's affected API is used in application code. The affected symbol `uuid.v5` IS imported and used by application code: `src/services/branchContext.ts:22` (`import { v5 as uuidv5 } from "uuid"`) and called at `src/services/branchContext.ts:44` as `uuidv5(`${ontologyId}:main`, DNS_NS)`. However, the vulnerable code path requires the optional `buf`/`offset` arguments; the current call sites pass only `(name, namespace)` with no caller-provided buffer, so the OOB-write primitive is not exercised by existing code. Direct `uuid` imports confirmed at src/config/foundryMulter.ts:4, src/middleware/correlationId.ts:2 (both `v4`, unaffected), src/services/quiver/rids.ts:11 (`v7`, unaffected). This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

If `uuid.v5` (or v3/v6) is ever invoked with a caller-controlled output buffer and offset, the caller can coerce a write outside the intended buffer range, corrupting adjacent Node.js process memory. This is a memory-corruption primitive with integrity impact; the current application code paths do not pass the optional buf/offset arguments, so exploitation would require a future change or a dependency-chain caller.

## Technical Analysis

**Root cause:** `uuid` prior to the fix does not bounds-check the optional `(buf, offset)` out-params on `v3`/`v5`/`v6`. Passing a `buf` that is too small or an `offset` larger than the buffer silently writes out of range.

**Application usage:** `uuid@^13.0.0` is a direct dependency in `package.json`. Import scan found:
- `src/config/foundryMulter.ts:4` — `v4` (not affected)
- `src/middleware/correlationId.ts:2` — `v4` (not affected)
- `src/services/branchContext.ts:22,44` — `v5` (**affected API**, but called as `uuidv5(name, DNS_NS)` with no `buf`/`offset`)
- `src/services/quiver/rids.ts:11` — `v7` (not affected)

The vulnerable `v5` symbol is used, so per the evidence ladder this is `vulnerable_symbol_used`, but the specific OOB-write invocation pattern is not present in existing code.

## Remediation

Bump the direct dependency: raise `"uuid"` in `package.json` from `^13.0.0` to `^13.0.1` (or `^14.0.0`), run `pnpm install`, and verify with `trivy fs pnpm-lock.yaml` that the resolved version is `>=13.0.1`. Because `^13.0.0` already permits `13.0.1`, a plain `pnpm update uuid` may pick the fix without editing `package.json`; committing the regenerated lockfile is sufficient. No code changes are required.
