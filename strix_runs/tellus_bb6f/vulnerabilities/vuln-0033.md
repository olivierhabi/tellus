# Design flaw: client-controlled authorizeApplyAction flag bypasses the OMS authorization gate for the privileged apply_action LLM tool

**ID:** vuln-0033
**Severity:** MEDIUM
**Found:** 2026-08-18 06:47:04 UTC
**Target:** tellus Ontology Engine — http://host.docker.internal:3000
**Endpoint:** /quiver/api/v1/aip/generate
**Method:** POST
**CWE:** CWE-863
**CVSS:** 4.3
**Fix Effort:** Low

## Description

The Quiver AIP routes decide whether the privileged `apply_action` tool appears in the LLM's authorized manifest based solely on a client-supplied `authorizeApplyAction` boolean in the request body. This bypasses the intended server-side OMS `canApplyAction` check, so any authenticated user can claim authorization to the privileged tool. Live execution of the action is not demonstrated on the current in-process mock backend, so the impact is latent/design-level — but the same route will trust the same flag when the production AIP service is wired in.

## Evidence

The route trusts a client boolean for the privileged tool — `src/routes/quiver/aip.ts`:

```typescript title=src/routes/quiver/aip.ts startLineNumber=60 endLineNumber=65
const GenerateBody = z.object({
  analysisRid: z.string().min(1),
  contextCardIds: z.array(z.string()).optional(),
  prompt: z.string().min(1),
  /** Test hook: pre-validated apply_action authorization for this analysis. */
  authorizeApplyAction: z.boolean().optional(),
});
```

```typescript title=src/routes/quiver/aip.ts startLineNumber=92 endLineNumber=96
function authorizedToolsFor(authorizeApplyAction: boolean): ReadonlyArray<ToolName> {
  const base = [...defaultAuthorizedTools()];
  if (authorizeApplyAction) base.push("apply_action");
  return base;
}
```

Whereas the intended server-side gate (`canApplyAction` against a `candidateActionTypeRid`) in `src/services/quiver/aip/tools.ts` is never invoked by the route, and `orchestrator.ts` only checks membership against the request-derived manifest.

## Impact

The authorization decision for the most privileged AIP tool (`apply_action` — deterministic ontology action execution) is client-controlled at the HTTP boundary. A low-privilege authenticated user can self-authorize the tool simply by sending `"authorizeApplyAction": true`, and the orchestrator will accept `apply_action` tool calls from the LLM against that forged manifest. On the current in-process mock backend this does not reach a real action execution (the backend does not invoke actions and a test guard intercepts the proposal), so the demonstrated impact today is the ability to manipulate the tool manifest and obtain privileged-tool proposals the user's role should not allow — a compromised authorization boundary rather than a proven write. The flaw is critical to fix before the production `tellus-aip-logic-service` is connected, because the identical route and flag would then gate real action execution.

## Technical Analysis

The codebase already has the correct design: `src/services/quiver/aip/tools.ts` implements `buildAuthorizedManifest`, whose `apply_action` entry is only retained if the user passes a server-side `AuthPort.canApplyAction` check against a `candidateActionTypeRid` resolved from the analysis:

```typescript title=src/services/quiver/aip/tools.ts startLineNumber=67 endLineNumber=80
    if (entry.name === "apply_action") {
      // Only retain apply_action if the user can actually apply at least one
      // configured action on the analysis (B9 C-07).
      if (!args.candidateActionTypeRid) {
        removed.push("apply_action");
        continue;
      }
      const ok = await args.auth.canApplyAction({
        userRid: args.user.userRid,
        actionTypeRid: args.candidateActionTypeRid,
        branch: args.branch,
      });
      if (!ok) {
        removed.push("apply_action");
        continue;
      }
    }
```

However, the HTTP route never calls `buildAuthorizedManifest`. Instead, `src/routes/quiver/aip.ts` accepts `authorizeApplyAction` as a plain `z.boolean()` in the request bodies of `generate`/`configure`/`assist`, and `authorizedToolsFor` appends `apply_action` to the manifest whenever that client boolean is true:

```typescript title=src/routes/quiver/aip.ts startLineNumber=92 endLineNumber=96
function authorizedToolsFor(authorizeApplyAction: boolean): ReadonlyArray<ToolName> {
  const base = [...defaultAuthorizedTools()];
  if (authorizeApplyAction) base.push("apply_action");
  return base;
}
```

That manifest is passed straight into `orchestrate(...)` at line 144. In `orchestrator.ts` (lines 53–70) the only authorization applied to a `tool_call` is membership in this request-derived manifest (`allowed.has(toolName)`), emitting `Tellus:Quiver:LlmToolUnauthorized` otherwise. So the server-side `canApplyAction` gate is skipped entirely at the route: the trust decision for a privileged tool is made from an attacker-owned JSON field. The in-process mock port (`inProcessAip.ts`) additionally raises `Tellus:Quiver:LlmToolUnauthorized`, which is why full apply execution is not reachable on the current deployment — but this is a backend artifact, not an authorization control.

## Proof of Concept

1. Mint a JWT for a low-privilege user (viewer) with no OMS action-apply grants on the analysis.
2. Call `POST /quiver/api/v1/aip/generate` with `"authorizeApplyAction": true` in the body.
3. Observe that the request is accepted and the orchestrator runs with `apply_action` in the authorized manifest (i.e. the manifest gate was satisfied by the client flag rather than by a server-side `canApplyAction` decision).
4. Confirm, from `src/routes/quiver/aip.ts` and `src/services/quiver/aip/tools.ts`, that the intended `buildAuthorizedManifest` / `AuthPort.canApplyAction` path is never invoked by the route.

## Remediation

Do not let a client field decide tool authorization. Remove `authorizeApplyAction` from the public request schemas (or accept it only on paths explicitly gated by the Quiver test-auth bypass), and have the route build the authorized tool set via the existing `buildAuthorizedManifest` in `tools.ts`, resolving the `candidateActionTypeRid` server-side from the analysis context and calling `AuthPort.canApplyAction` for the real user before `apply_action` is ever added to the manifest. The same fix must be kept when the production `tellus-aip-logic-service` replaces the in-process mock. Add a regression test asserting `authorizeApplyAction: true` from an unprivileged user does not result in an authorized `apply_action` manifest entry.

## Assumptions

Assumes the deployed stack with the in-process mock AIP backend (`NODE_ENV=development` as deployed). Full live execution of a real ontology action was not demonstrated: the mock backend does not invoke actions and its test guard raises `Tellus:Quiver:LlmToolUnauthorized` before a proposal propagates, so no Integrity-high impact is claimed. The attacker is a legitimately authenticated low-privilege user. The finding's weight is that the authorization boundary at the route is already wrong and will gate real execution once the production AIP service is wired in.
