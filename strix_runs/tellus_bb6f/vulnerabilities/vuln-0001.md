## Description

The transitive package **`ip-address@10.1.0`** (pinned via `pnpm-lock.yaml`) is affected by CVE-2026-69192: `Address4` decodes IPv4 octets with a leading zero as **decimal**, whereas the WHATWG URL host parser, `inet_aton`, and `getaddrinfo` decode them as **octal**. The library and the network stack disagree about which host a string names, enabling SSRF and trust-boundary bypass when `ip-address` is used to validate destination hosts. Fixed in `10.3.1`. Published 2026-08-03; references include the upstream fix commit `beaugunderson/ip-address@56368cb` and Red Hat CVE advisory.

## Impact

An attacker who can influence any host/IP validation performed through this chain can craft an address (e.g. `012.0.0.1`, `0x0a.1`) that the library validates as a benign/internal host while the actual DNS/connect layer resolves it to an arbitrary target, bypassing SSRF host allow/deny checks. Scope is Changed because the parsing confusion crosses a security authority boundary between validation and resolution.

## Technical Analysis

**Root cause:** `ip-address` ≤ 10.1.0 treats an IPv4 octet written with a leading zero (e.g. `012`) as base-10. The WHATWG host parser, libc `inet_aton`, and `getaddrinfo` treat it as octal.  `new Address4('012.0.0.1')` therefore returns a different address than the one the network stack will actually connect to. Any validation/allowlist built on `ip-address` can be bypassed by an attacker-controlled host string.

## Remediation

The fix version `ip-address@10.3.1` is a *minor* bump within the range that `socks@2.8.7` declares (`^10.0.0`), so re-resolving the lockfile will pick it up automatically. Options:
1. Bump the **direct** dependency in `package.json`: raise `@kubernetes/client-node` to a version whose closure pins `ip-address@>=10.3.1` (≥ 1.4.x patch that vendors the fix), then `pnpm install`.
2. Add a pnpm override to force the transitive resolution, then commit the updated `pnpm-lock.yaml`:
   `pnpm.overrides: { "ip-address@<10.3.1": "^10.3.1" }` in `package.json`.
3. Re-run `pnpm install` and confirm with `trivy fs pnpm-lock.yaml` that `ip-address` resolves to `>=10.3.1`.
Do not edit `pnpm-lock.yaml` by hand; use `pnpm.overrides` so the lockfile stays reproducible.
