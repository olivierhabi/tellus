# Unauthenticated remote publication of executable TypeScript Functions via dev test-auth fallback

**ID:** vuln-0038
**Severity:** HIGH
**Found:** 2026-08-18 06:51:25 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/functions/:repositoryRid/versions
**Method:** POST
**CWE:** CWE-306
**CVSS:** 7.5
**Fix Effort:** Medium

## Description

The publish gate that protects the non-sandboxed worker_threads+vm Function executor (`POST /api/v1/functions/:repositoryRid/versions`) is bypassable from the network with no credentials. When `CODE_REPOS_TEST_AUTH=1` is active and the request carries no `X-Tellus-Test-Principal` header, `requireCodeReposAuth()` substitutes a hard-coded dev fallback principal whose `userId` already holds a **global** `function_publish_grants` row; `authorizePublish()` then admits the caller via `db_grant`. A forged `X-Tellus-Test-Principal` header that simply names the realm role `function:publish` also yields publish rights via `keycloak_role`. Both paths create immutable, executable function-version rows in the Functions registry with no authentication.

## Impact

An unauthenticated network attacker can write arbitrary TypeScript artifacts into the Functions registry (the platform's executable-code store) under semver tags of their choosing. This defeats the security boundary documented in `src/services/executionPolicy.ts` and `src/services/functionExecutor.ts` — the executor is explicitly *not* a sandbox (worker_threads + Node `vm`), so publication is the only control preventing untrusted code from reaching the runtime. The demonstrated impact is an unauthorized **integrity** violation: the attacker can plant and version executable code (immutable, content-addressed, so it cannot be overwritten — confirmed HTTP 409 on re-POST with different sha256). This is the enabling step for the documented (but not demonstrated in this test) follow-on risk of remote code execution inside the API container. No confidentiality or availability impact was demonstrated; the runtime sandbox rejected `process`/`Function`-based escape probes during a safe invocation attempt.

## Technical Analysis

Two independent paths in `requireCodeReposAuth()` (src/services/codeRepos/middleware/principal.ts) let an unauthenticated caller become an authorized publisher:

1. **Dev-fallback substitution (no header)** — When `CODE_REPOS_TEST_AUTH=1` and no `X-Tellus-Test-Principal` header is present, and the TCP peer is classified as localhost, the middleware replaces the request's principal with `DEV_FALLBACK_PRINCIPAL = "53cf9bcf-4c20-4aed-83f4-3c7e405453b4/OWNER,EDITOR,READER,tellus-superadmin"`. Requests from the sandbox arrive via the Docker gateway and satisfy the `isLocalhost()` check, so the substitution fires for *remote* callers. The hard-coded `userId` `53cf9bcf-...` has a pre-existing global `function_publish_grants` row (seeded on 2026-08-08 with reason "local dev fallback principal (CODE_REPOS_TEST_AUTH dev mode)"), so `authorizePublish()` admits the request with `decision_source = db_grant`. The audit row records the fallback identity, not the caller's — cross-user attribution is broken.

2. **Forged header** — `applyHeaderPrincipal()` passes roles from `X-Tellus-Test-Principal: <userId>/<role>` verbatim into `principal.roles`. `authorizePublish()` step (a) checks `roles.includes(policy.publishRole)` where `publishRole = "function:publish"`, so a header value of `<any-uuid>/function:publish` yields publish rights via `decision_source = keycloak_role`. No Keycloak signature or role assignment is consulted.

The authorization model itself (`executionPolicy.ts`) is otherwise robust: a forged principal **without** the `function:publish` role is denied (403 `Functions:PermissionDenied`), and the artifact-integrity controls are sound (re-publishing the same semver with a different sha256 returns HTTP 409 `Functions:VersionImmutable`). Live config: `NODE_ENV=development`, `TELLUS_TEST_HOOKS=1`, `CODE_REPOS_TEST_AUTH=1`, `FUNCTION_EXECUTION_TRUST_MODE` unset → `trusted-authors-only`. No Keycloak user (including superadmin) is assigned the `function:publish` realm role — verification of the JWTs `realm_access.roles` — so the *only* admission paths are the two above, both of which are attacker-controlled. The `globalAuth.ts` allowlist (lines 195, 210) permits unauthenticated traffic to reach the per-router middleware, exposing the bypass.

## Proof of Concept

1. Confirm the live configuration: `CODE_REPOS_TEST_AUTH=1`, `NODE_ENV=development`, `FUNCTION_EXECUTION_TRUST_MODE` unset (`trusted-authors-only`), and that no seeded Keycloak account (editor/viewer/nogroups/superadmin) carries the `function:publish` realm role.
2. Send `POST /api/v1/functions/:repositoryRid/versions` with **no** `Authorization` header, **no** `X-Tellus-Test-Principal` header, and a valid publish body. Observe HTTP 201 with a created `function-version` row.
3. Send the same request with header `X-Tellus-Test-Principal: <any-uuid>/function:publish` and **no** auth. Observe HTTP 201.
4. Send the same request with header `X-Tellus-Test-Principal: <any-uuid>/BOGUS_ROLE_XYZ` and **no** auth. Observe HTTP 403 `Functions:PermissionDenied` (proves the gate is functional when the role is absent).
5. Re-POST the same semver with a different `artifactSha256`. Observe HTTP 409 `Functions:VersionImmutable` (proves artifact immutability).
6. Inspect the server audit table `function_publish_audit_log`: step 2 records `decision_source=db_grant, subject_id=53cf9bcf-4c20-4aed-83f4-3c7e405453b4`; step 3 records `decision_source=keycloak_role`.

## Remediation

1. Delete the dev-fallback principal substitution in `requireCodeReposAuth()` — there is no legitimate reason to bind an unauthenticated request to an identity that owns privileges. Unauthenticated requests must fail closed with 401 regardless of the `isLocalhost` classification.
2. Restrict the `X-Tellus-Test-Principal` synthetic principal so it can only be used with `isTestAuthBypassEnabled("CODE_REPOS_TEST_AUTH")` **and** a localhost peer **and** an explicit header; never let it inject the `function:publish` role (or any role matching `executionPolicy().publishRole`).
3. Revoke the existing global `function_publish_grants` row whose `subject_id = 53cf9bcf-4c20-4aed-83f4-3c7e405453b4` and add a migration/CI assertion that no grant exists for a test/fallback subject in any shared environment.
4. Keep the `globalAuth.ts` allowlist, but treat it as transport-only; the per-router auth must be the sole enforcement, and it must not accept test principals in any environment reachable from outside localhost.
5. Add an integration test that POSTs to the publish endpoints with no auth and asserts HTTP 401, exercising both the no-header and forged-header paths.

## Assumptions

The finding is **conditional** on the assessed deployment's non-production configuration: `NODE_ENV=development` and `CODE_REPOS_TEST_AUTH=1` (both active in the running `.env`). The `assertNoTestAuthInProduction()` guard throws at boot if `CODE_REPOS_TEST_AUTH=1` is set with `NODE_ENV=production`, so a production deployment would fail fast — the production risk is therefore limited to misconfiguration or non-production environments exposed to the network (the exact scenario under test). The leftover global grant row for the dev-fallback subject is also required for the no-header path; it exists in the current database. The RCE consequence of publishing into the non-sandboxed executor is documented in the codebase but was **not** re-demonstrated (safe sandbox probes were denied), so the scored impact reflects the demonstrated unauthorized write primitive only.
