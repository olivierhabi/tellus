# Internal Service Fingerprinting via Rate-Limit-Exempt PostgreSQL Connectivity Probe (/api/v1/connectivity/connections/test-config)

**ID:** vuln-0040
**Severity:** MEDIUM
**Found:** 2026-08-18 06:59:23 UTC
**Target:** http://host.docker.internal:3000
**Endpoint:** /api/v1/connectivity/connections/test-config
**Method:** POST
**CWE:** CWE-200
**CVSS:** 4.3
**Fix Effort:** Low

## Description

`POST /api/v1/connectivity/connections/test-config` opens a real TCP socket to a caller-supplied `host:port` and returns response envelopes whose error-class deterministically distinguishes a **closed port** (`502 Tellus:Connectivity:JdbcConnectFailed`), an **open non-PostgreSQL port** (`500 InternalError "Connection terminated unexpectedly"`), an **open PostgreSQL port** (`401 Tellus:Connectivity:JdbcAuthFailed`), and a **firewalled / non-answering service** (`500 InternalError "Connection terminated due to connection timeout"` after ~5 s). The route's `testRateLimit` middleware deliberately exempts every authenticated principal from the request rate limit, so any authenticated caller holding the `connectivity:test` scope can sweep loopback and any operator-allowlisted address space at full speed and enumerate internal services by port, protocol family, and reachability.

## Evidence

Live reproduction on the current stack (admin token, `connectivity:test`):

```
port 80   -> Tellus:Connectivity:JdbcConnectFailed            (closed port)
port 3000 -> InternalError "Connection terminated unexpectedly" (Express app = open, non-PG)
port 5432 -> 401 Tellus:Connectivity:JdbcAuthFailed           (PostgreSQL — auth failure proves service type)
port 7233 -> InternalError "Connection terminated unexpectedly" (Temporal gRPC = open, non-PG)
port 9000 -> InternalError "Connection terminated due to connection timeout" (5.0 s — MinIO exists, no PG reply)
port 8086 -> InternalError "Connection terminated due to connection timeout" (5.0 s — Keycloak exists)
port 6379 -> InternalError "Connection terminated due to connection timeout" (5.0 s — Redis exists)
port 9200 -> InternalError "Connection terminated due to connection timeout" (5.0 s — OpenSearch exists)
```

Rate-limit exemption (pre-fix): repeated probes returned distinct classes with no `429`; the `testRateLimit` short-circuit `if (principalId && ... !== "1") next();` bypassed the bucket for every authenticated caller.

Post-fix verification (same endpoint, after edits): repeated probes exhaust the 6-per-minute bucket and return `429 Tellus:Connectivity:EgressRateLimited`, and the auth-failure envelope (`401 JdbcAuthFailed`) is collapsed to the shared `502 JdbcConnectFailed` — the caller can no longer distinguish refused-connection from auth-failure from termination.

## Impact

An authenticated, connectivity-privileged attacker learns the internal service inventory (which TCP services exist on loopback and any operator-allowlisted hosts, which speak PostgreSQL, and which are slow/blackhole) without needing network-level access to those segments. On the verified stack this fingerprinted the Express app (3000), the frontend (3001), PostgreSQL (5432), Temporal gRPC (7233), and non-answering services on 9000 (MinIO), 8086 (Keycloak), 6379 (Redis), and 9200 (OpenSearch). This is internal service metadata disclosure that materially assists targeting for every other finding, but it does not itself expose application data or allow modification — hence Confidentiality impact is limited (C:L) and Integrity/Availability are unaffected.

## Technical Analysis

`src/services/connectivity/handlers/test.handler.ts` `testConfig` (~line 310): after `assertEgressResolved` allows the target (the dev stack sets `CONNECTIVITY_EGRESS_ALLOW_RESERVED=localhost,127.0.0.1/8,::1`; the equivalent operator allowlist plays the same role in any deployment), the handler builds a one-shot `pg.Pool` and awaits `SELECT version()` within a 5 s probe budget. `mapPgError` classifies the pg driver's outcome into `auth` / `connect` / `other`, and the error mapping then emits a **different HTTP envelope per outcome**:

- closed port (`ECONNREFUSED` etc.) → `502 Tellus:Connectivity:JdbcConnectFailed`
- TCP connected but not a PG server → `500 InternalError "Connection terminated unexpectedly"`
- PG server that rejects the credentials (`28P01`/`28000`) → `401 Tellus:Connectivity:JdbcAuthFailed`
- TCP connect hangs / no reply within the budget → `500 InternalError "Connection terminated due to connection timeout"` (5 s)

That four-way distinction is a clean oracle: status + `errorName` + message reveal whether a socket succeeded and what kind of service answered. The egress *blocker* (`assertEgressForConfig` / `assertEgressResolved`) correctly refuses reserved targets that are not allowlisted, so the residual issue is the **response-side oracle on allowed targets**, not the guard.

Separately, `testRateLimit` (lines 60-104) short-circuits with `next()` for any request whose bearer token resolves to a principal:

```
if (principalId && process.env.CONNECTIVITY_TEST_RATE_LIMIT_ALL !== "1") {
    next();           // authenticated → exempt from the 6/min token bucket
    return;
}
```

so the only velocity bound on the sweep is disabled by default for exactly the attackers who can authenticate. Combined, an authenticated principal with `connectivity:test` can fingerprint the internal service inventory without any network-level access.

## Proof of Concept

1. Mint a short-lived bearer token for any account that holds the `connectivity:test` scope (e.g. the seeded admin). 2. Loop `POST /api/v1/connectivity/connections/test-config` with `{"host":"127.0.0.1","port":<P>,"database":"x","user":"x","password":"x"}` across a port list, with no throttling. 3. Parse each JSON envelope's `errorName`/`message` and record the per-port class. 4. Observe the deterministic four-way split: `502 JdbcConnectFailed` = closed; `500 InternalError "Connection terminated unexpectedly"` = open non-PG; `401 JdbcAuthFailed` = live PostgreSQL; `500 InternalError "Connection terminated due to connection timeout"` (5 s) = blackholed service. 5. Note that, before the fix, this loop returns answers with no `429` even after dozens of requests (rate limit exempt). After the fix, all four ports collapse to the single `502 JdbcConnectFailed` envelope and the loop returns `429 Tellus:Connectivity:EgressRateLimited` after the 6-per-minute budget is spent.

```python
import json, urllib.request, urllib.error

BASE = "http://host.docker.internal:3000/api/v1/connectivity/connections/test-config"
TOKEN = "<admin-or-connectivity-test-scope bearer token>"

def probe(port):
    body = json.dumps({"host": "127.0.0.1", "port": port,
                       "database": "x", "user": "x", "password": "x"}).encode()
    req = urllib.request.Request(BASE, data=body, method="POST", headers={
        "Authorization": f"Bearer {TOKEN}",
        "Content-Type": "application/json",
    })
    try:
        with urllib.request.urlopen(req, timeout=30) as r:
            d = json.loads(r.read().decode())
    except urllib.error.HTTPError as e:
        d = json.loads(e.read().decode())
    return d.get("errorName"), (d.get("message") or "")[:55]

for port in [80, 3000, 5432, 7233, 9000, 6379, 8086, 9200]:
    print(port, "->", probe(port))
# Pre-fix: each port yields a distinct class with NO 429 even after many calls.
# Post-fix: all ports collapse to 502 JdbcConnectFailed, then 429 EgressRateLimited
# after the 6-per-minute budget is exhausted.
```

## Remediation

1. Apply the rate limit to every caller. In `testRateLimit`, invert the exemption so the token bucket applies by default and only an explicit operator opt-out disables it (treat the env var as an opt-out `=== "0"` rather than an opt-in `!== "1"`). 2. Make the client-facing error envelope uniform. In `testConfig`, return the same `502 Tellus:Connectivity:JdbcConnectFailed` for every connect/auth/timeout/protocol outcome, keeping the fine-grained internal classification only in `observeProbe` metrics and the `console.warn` server-side log (where it already exists). Return a distinct auth envelope only when the caller's own presented credentials are wrong for a positively-identified PG server — never let the HTTP envelope reveal whether a socket to a third-party target succeeded.

## Assumptions

Assumes an authenticated principal that holds the `connectivity:test` scope (the seeded admin/superadmin roles have it on this stack; viewer and editor do not — they are rejected with `403 ScopeRequired`). Also assumes the operator has allowlisted at least one reachable target (the dev stack sets `CONNECTIVITY_EGRESS_ALLOW_RESERVED=localhost,127.0.0.1/8,::1`; on other deployments the per-connection allowlist plays the equivalent role for the hosts the operator approves). The finding does not require the attacker to bypass the reserved-target egress guard — it is the response-side oracle on *allowed* targets plus the disabled rate limit.
