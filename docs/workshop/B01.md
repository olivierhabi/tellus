# B01 — Workshop Module Service Runbook

## What it does
Owns CRUD for `ri.workshop.main.module.*` documents at
`/workshop/api/v1/modules`. Every mutation goes through `validateModule`
(B02) + ETag/If-Match (§0.2) + Idempotency-Key (§0.3) + audit emission +
the in-process recording adapter pattern that forwards `branch` and
`Authorization` to downstream services (§0.5/§0.6).

Service surface:
- `src/services/workshop/moduleService.ts` — business logic
- `src/services/workshop/{etag,errors,idempotency,audit,metrics}.ts` —
  primitives shared across B01..B10
- `src/routes/workshopModules.ts` — HTTP edges
- `src/migrations/058_b1_workshop_module.sql` + `059_b1_workshop_idempotency.sql`

## Diagnose

### Symptom: PUT returns 500
1. Read the `errorInstanceId` from the response body.
2. `grep <errorInstanceId> /var/log/tellus/server.log` — every WorkshopError
   logs its instance id at the global error handler.
3. The most common 500 sources are: Postgres connection pool exhaustion
   (`workshop_db_pool_used` near max) or a validator regression that
   threw a non-WorkshopError. Either way, the audit row is *not* written
   on a 500, so the audit gap itself is a signal.

### Symptom: PUT returns 412 unexpectedly
1. The client sent a stale ETag. This is the documented stale-conflict
   path (§B01 + Forbidden Behaviors: never auto-merge).
2. Verify the response body's `parameters.currentEtag` matches the
   server-side row: `SELECT encode(sha256(definition::text::bytea), 'hex')
   FROM workshop_module WHERE rid = $1`. If they differ, the canonical
   JSON encoder has a regression — see `etag.ts` canonicalization.

### Symptom: POST returns 409 ModuleNameConflict
1. Two POSTs raced for the same `(parent_folder_rid, display_name)`.
   Exactly one should win, the rest receive 409. Verify with:
   ```
   SELECT rid, display_name, created_at FROM workshop_module
   WHERE parent_folder_rid = $1 AND display_name = $2;
   ```
2. If the winning row already exists from before the request, the client
   needs to disambiguate the displayName. This is expected behavior, not
   an outage.

### Symptom: Idempotency replay returns wrong body
1. Cause is almost always a body-hash regression. The hash is
   `sha256(canonicalize(body))`. See `idempotency.ts:hashBody`.
2. To verify the stored hash:
   ```
   SELECT encode(body_sha256, 'hex')
   FROM workshop_idempotency_record
   WHERE idempotency_key = $1 AND user_id = $2 AND route = $3;
   ```
3. If the hashes diverge across replays of the same body, the
   `canonicalize` function is non-deterministic. Bug. Open a P1.

## Remediate

| Issue | Action |
|---|---|
| Pool exhaustion | Scale `pg_pool_max` upward; long-running PUTs are a sign that B02 validator regressed — check `workshop_validate_seconds` |
| Stuck idempotency record blocking retries | `DELETE FROM workshop_idempotency_record WHERE idempotency_key = $key AND user_id = $u` only if the original write *also* failed; otherwise the user gets two writes for one Idempotency-Key |
| Audit gap (5xx without audit row) | Reconstruct from server logs + the response body the client received; backfill the audit row manually after RCA |
| Branch-forwarding regression | Check `workshop_module_request_total{branch_present="true"}` is non-zero when `branch` is in the URL; if not, the request context propagation is broken — check middleware ordering |

## Prometheus

- `workshop_module_request_seconds` (histogram, label `op`, no per-RID labels)
- `workshop_module_request_total` (counter, label `op`, `status`)
- `workshop_validate_seconds` (B02; consumed by the PUT path)
- `workshop_db_pool_used` (gauge)

Per §0.4, exemplars carry the `errorInstanceId` for 5xx — never the RID.
