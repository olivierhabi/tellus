# TASK 1: Create the Interface PostgreSQL Tables and Migration Infrastructure

This task has two sub-tasks that must be completed in order.

## Objective
Create the database table that stores Interface definitions in PostgreSQL. In Palantir's Ontology, an Interface is an abstract type that defines a shape (a set of property names and their types) that multiple Object Types can implement. This enables polymorphism — you can write queries, functions, and applications that work with any Object Type that implements a given Interface, without knowing the specific Object Type at compile time. For example, an Interface called "HasLocation" might define properties `latitude` (double) and `longitude` (double), and both the "Airport" and "Warehouse" Object Types could implement it by mapping their own location properties to the Interface's property definitions.

## Exact Specification

## Sub-task 1A: Create the Interface Tables

Create a file at `/src/migrations/007_create_interfaces.sql` that contains the SQL to create the `interface` table. The table must have the following columns:

- `interface_id`: UUID type, PRIMARY KEY, should be generated by the application layer (not auto-generated by the database) because the application needs to know the ID before inserting related records in other tables. Do NOT use DEFAULT gen_random_uuid() on this column — the application will provide the UUID.

- `ontology_id`: UUID type, NOT NULL, FOREIGN KEY referencing `ontology(ontology_id)`. This establishes which Ontology this Interface belongs to. In Palantir, all Ontology resources belong to a single Ontology instance. The ON DELETE behavior should be CASCADE — if the Ontology is deleted, all its Interfaces are deleted too. This matches Palantir's behavior where deleting an Ontology removes all its resources.

- `api_name`: TEXT type, NOT NULL, UNIQUE. This is the programmatic identifier for the Interface, used in API calls and code generation. It must follow the convention of PascalCase identifiers (e.g., "HasLocation", "Auditable", "Schedulable"). The UNIQUE constraint is across the entire table, not just within an Ontology, because Palantir enforces globally unique API names for Interfaces. Add a CHECK constraint that ensures the api_name matches the regex pattern `^[A-Z][a-zA-Z0-9]*$` — it must start with an uppercase letter and contain only alphanumeric characters. This prevents invalid names like "has-location" or "123abc" from being stored.

- `display_name`: TEXT type, NOT NULL. This is the human-readable name shown in the Ontology Manager UI and Object Explorer. It can contain spaces, special characters, and Unicode. There is no format constraint on this field. Examples: "Has Geographic Location", "Is Auditable", "Can Be Scheduled".

- `description`: TEXT type, nullable. A free-form description of what this Interface represents and when Object Types should implement it. Can be multiple paragraphs. No length limit in the database, but the API should enforce a maximum of 10,000 characters to prevent abuse.

- `created_at`: TIMESTAMPTZ type, NOT NULL, DEFAULT now(). Records when the Interface was first created. This value should never be updated after initial creation.

- `updated_at`: TIMESTAMPTZ type, NOT NULL, DEFAULT now(). Records when the Interface definition was last modified. This must be updated whenever any property of the Interface changes (including its properties list, display name, or description). The application layer must update this field explicitly (via `SET updated_at = now()` in the UPDATE statement) on every modification. Do NOT use a database trigger — Task 4's PUT endpoint already sets `updated_at = now()` explicitly.

Additionally, create the `interface_property` table that defines the properties that an Interface declares. This is separate from the `property` table (which belongs to Object Types) because Interface properties are abstract declarations, not backed by actual data columns. The `interface_property` table must have:

- `interface_property_id`: UUID type, PRIMARY KEY.

- `interface_id`: UUID type, NOT NULL, FOREIGN KEY referencing `interface(interface_id)` with ON DELETE CASCADE. If the Interface is deleted, all its property declarations are deleted.

- `api_name`: TEXT type, NOT NULL. The property name as it appears in the Interface definition. Must follow the same naming convention as Object Type properties: camelCase starting with a lowercase letter (e.g., "latitude", "longitude", "createdDate"). Add a CHECK constraint for the regex `^[a-z][a-zA-Z0-9]*$`.

- `display_name`: TEXT type, NOT NULL.

- `base_type`: TEXT type, NOT NULL. Must be one of the exact same base types supported by Object Type properties: 'string', 'boolean', 'integer', 'long', 'double', 'float', 'date', 'timestamp', 'byte', 'short', 'decimal', 'geopoint', 'geoshape', 'string_array', 'integer_array', 'long_array', 'double_array', 'boolean_array', 'timestamp_array', 'struct'. Add a CHECK constraint that validates against this exact list.

- `is_required`: BOOLEAN type, NOT NULL, DEFAULT false. If true, any Object Type implementing this Interface MUST map one of its properties to this Interface property — it cannot be left unmapped.

- `ordinal`: INTEGER type, NOT NULL, DEFAULT 0. Controls the display order of properties in the Interface definition. Properties with lower ordinal values appear first.

- A UNIQUE constraint on `(interface_id, api_name)` — within a single Interface, each property name must be unique.

After creating both tables, also create an index on `interface.ontology_id` for efficient lookups of all Interfaces in an Ontology, and an index on `interface_property.interface_id` for efficient lookups of all properties in an Interface.

## Sub-task 1B: Create the Migration Runner

**Dependency:** None (independent of Sub-task 1A)

Also create the migration runner code: a function in `/src/migrations/runner.js` that reads all SQL migration files in order (by numeric prefix) and executes them against the PostgreSQL database. If a migration has already been applied (track this in a `_migrations` table with columns `filename TEXT PRIMARY KEY, applied_at TIMESTAMPTZ DEFAULT now()`), skip it. This ensures migrations are idempotent and can be re-run safely.

## Verification
After running the migration:
1. Query `SELECT * FROM information_schema.tables WHERE table_name IN ('interface', 'interface_property')` — both tables must exist.
2. Attempt to INSERT an interface with api_name = 'lowercase' — must fail (CHECK constraint).
3. Attempt to INSERT an interface with api_name = 'HasLocation' — must succeed.
4. Attempt to INSERT two interface_properties with the same api_name on the same interface — must fail (UNIQUE constraint).
5. DELETE the interface — all its interface_properties must also be deleted (CASCADE).
