# T-08 — Saved Explorations: visibility check on single-GET; marking-aware config tagging

**Status:** DONE 2026-04-30

## Contracts covered

| ID    | Contract |
|-------|----------|
| C-110 | `collectConfigRefs` walks `{objectType, apiName, from}` keys (top-level and array forms) plus nested `{field, property}` keys, scoping property refs to the most-recent object-type seen. `currentOt` propagates through recursion so deeply-nested filter trees are correctly attributed |
| C-111 | `resolveRequiredMarkings` unions `object_type.marking_required` and `property.marking_required` across every collected ref, returns sorted+deduped string array |
| C-112 | Unknown api-names are silently dropped (over-collection tolerance — the property pass is gated by the `otIdByName` map) |
| C-113 | Empty / null / non-object configs return `[]` with **zero** DB I/O |
| C-114 | `GET /:id` returns the SAME `OBJECT_NOT_FOUND` envelope (with `parameters.kind = "saved_exploration"`) for: (a) row does not exist, (b) row owned by another user, (c) caller lacks markings. IDOR-shape preserved — no timing or status-code distinction |
| C-115 | `GET /` list query carries `required_markings <@ $3::text[]` with the caller's marking set; pre-T-08 rows backfilled to `'{}'` are visible to all who pass the visibility filter |
| C-116 | `tellus_saved_exploration_marking_misses_total` increments when the row exists but is filtered out solely by the marking check (SOC dashboard signal) |
| C-117 | `POST /` and `PUT /` re-resolve `required_markings` and reject the write with `FORBIDDEN` (+ structured `parameters.missingMarkings`) when the caller does not hold every required marking — privilege-escalation guard. System principals are exempted |

## Decisions

- **Schema strategy:** the migration covers TWO additions in one PR — `saved_exploration.required_markings` (the T-08 spec column) plus `property.marking_required` (a prerequisite the T-08 spec assumes already exists from migration 044, but 044 only added it to `object_type`). Bundling minimises out-of-order migration risk; both columns ship reversible `.down.sql`.
- **Over-collection vs spec walker:** the resolver's walker is intentionally permissive (collects every string under conventional keys and silently drops unknowns) rather than spec-exact (parsing the saved query AST). The strictest-plausible interpretation: an attacker should not be able to evade the marking gate by hiding a referenced api-name behind a non-standard JSON key, so we collect more than the spec strictly requires. The cost is a few extra SELECTs per resolve; the security payoff is a wider gate.
- **IDOR-shape over `403/404` distinction:** spec §8.3 says return 404 with `parameters.kind = "saved_exploration"` if no row matches. The strictest interpretation extends that to "no distinguishable signal even when the row exists but is marking-filtered". The marking-miss counter satisfies the SOC dashboard need without leaking the existence signal to the requesting caller.
- **Backfill:** the migration's `DEFAULT '{}'` means existing rows are visible to anyone who passes the visibility filter (i.e. unchanged from the pre-T-08 state). A one-time backfill that recomputes `required_markings` per row is needed as an out-of-band script — the shape of which is documented but not run from the migration itself, because re-walking config with DB lookups inside a migration risks lock contention. Backfill task surfaced in `FINAL_REPORT.md`.

## Files changed

- `src/migrations/045_saved_exploration_required_markings.sql` (+ `.down.sql`) — schema migration with reversible down path.
- `src/services/explorations/configMarkingResolver.ts` — new module: `walkRefs`, `collectConfigRefs`, `resolveRequiredMarkings`. Two-pass walker: first promote sibling `objectType` keys, then collect `field` keys with the correct OT scope.
- `src/routes/explorations.ts` — full rewrite of read paths:
  - POST: pre-resolve `required_markings`, reject with FORBIDDEN if caller's markings don't cover the result, INSERT with the resolved array.
  - GET /: filter via `<@ $3::text[]` and cap at 100 rows.
  - GET /:id: filter on visibility + ownership + markings. On 0-row result, sniff for "row exists but markings short" to increment the marking-miss counter; return identical 404 envelope in all cases.
  - PUT /:id: re-resolve markings only if `config` is being touched; reject FORBIDDEN on privilege escalation; UPDATE via COALESCE so metadata-only edits leave `required_markings` alone.
  - DELETE: unchanged.
- `tests/unit/object-explorer/configMarkingResolver-unit.test.ts` — 10 tests: walker scoping (C-110), resolver union semantics (C-111), null-row tolerance (C-111b), unknown-OT silent-drop (C-112), no-DB-I/O for empty configs (C-113).
- `tests/unit/object-explorer/explorations-T08-route-unit.test.ts` — 7 route-level integration tests using `supertest` against a minimal Express harness with `req.security` injected: not-found path (C-114a), row-exists-but-marking-short path (C-114b/C-116), allowed read path (C-114c), POST FORBIDDEN guard (C-117a), POST happy path with INSERT verification (C-117b), POST validation (C-117c), GET / list filter SQL parameter (C-115).

## Rubric items satisfied

- **Input validation** — POST title required, INSERT-only-when-author-holds-markings.
- **CBAC/Markings at the data layer** — the SQL filter `required_markings <@ $::text[]` is the data-layer enforcement; route-level checks are belt-and-braces but not the only line of defence.
- **Audit-log signal** — the marking-miss counter is the SOC dashboard's signal that someone tried to read out-of-marking explorations. Counter has zero label cardinality so it cannot blow up Prometheus storage.
- **Reversibility** — both schema additions ship reversible `.down.sql`. Idempotent forward path (`ADD COLUMN IF NOT EXISTS`) so repeated migration runs are safe.
- **Branch propagation** — `saved_exploration` is per-ontology, not per-branch (per existing schema). The route already filters on `ontology_id`. T-08 does not extend the branch dimension.

## Open spec questions

- The walker's tolerance for over-collection means it walks the entire JSON tree. For a 1MB saved config with thousands of nested filters, the property-resolution step would issue one batched query per object-type. If a future feature ships configs with thousands of OT references, the resolver should add a result cache. Documented for follow-up.
- Backfill of existing rows is left for an out-of-band script — the migration intentionally does not embed re-walking + DB lookups inside a transaction. The strictest-plausible interpretation is "ship the gate now, accept the temporary visibility relaxation for legacy rows, schedule the backfill". Surfaced in `FINAL_REPORT.md`.
