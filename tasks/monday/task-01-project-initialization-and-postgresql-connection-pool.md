# TASK 1 OF 30: Project Initialization and PostgreSQL Connection Pool

**Objective:** Initialize the Node.js project with all dependencies and create a robust PostgreSQL connection pool. This pool is the single database access point for the entire application. Every service, route, and middleware will import this pool. It must handle connection failures, support concurrent queries, and reconnect automatically.

**Step-by-step instructions:**

First, create the project directory called ontology-engine. Run npm init with the name set to "ontology-engine", version "0.1.0", and main set to "src/server.js". Install these exact production dependencies: express (version 4.x, the web framework that handles all HTTP routing), pg (version 8.x, the PostgreSQL client library that provides both Pool and Client classes), cors (version 2.x, for cross-origin resource sharing during development), multer (version 1.x, for multipart file upload handling needed by the datasource registration endpoint), and csv-parse (version 5.x, for parsing CSV files when scanning backing datasource files). Install nodemon as a devDependency for automatic server restart during development when files change.

Second, create the file src/db.js. This file exports a PostgreSQL connection pool using the Pool class from the pg library. Configure the pool with host set to process.env.PGHOST or default "localhost", port set to process.env.PGPORT or default 5432, database set to process.env.PGDATABASE or default "ontology", user set to process.env.PGUSER or default "postgres", and password set to process.env.PGPASSWORD or default "ontology". Set the maximum pool size to 20 connections. This number is chosen because our Express server can handle dozens of concurrent requests and each request may need its own database connection. The idle timeout must be 30000 milliseconds, meaning a connection that has been idle for 30 seconds is released back to PostgreSQL. The connection timeout must be 5000 milliseconds, meaning if a new connection cannot be established within 5 seconds, the query fails with a timeout error.

Critical configuration for timestamp handling: PostgreSQL returns TIMESTAMPTZ values as JavaScript Date objects by default, which causes inconsistent serialization in JSON responses. We need raw ISO 8601 strings instead. Import the types module from pg and set a custom type parser for OID 1184 (which is PostgreSQL's internal identifier for the timestamptz type). The parser function should simply return the raw string value without any conversion. This ensures that every timestamp in every API response is a consistent ISO 8601 string like "2025-03-11T14:30:00.000Z" rather than a JavaScript Date that might serialize differently depending on the server's timezone.

The pool must export a query helper function that accepts a SQL text string and an optional values array for parameterized queries. This function calls pool.query(text, values) and returns the result. If the query throws an error, the helper must log the error including the full SQL text and parameter values (this is essential for debugging parameterized queries where the error alone doesn't tell you what SQL was executed), then re-throw the error so the calling code can handle it appropriately (usually by sending an error response to the client).

Also export a getClient function that checks out a dedicated client from the pool. This is needed for transactions where multiple queries must execute on the same connection. The function calls pool.connect() and returns the client. The calling code is responsible for calling client.release() when done. Add a warning comment reminding developers to always release clients in a finally block to prevent connection leaks.

Add event listeners on the pool: the error event fires when an idle client encounters an unexpected error (like the database restarting). Log this error with level "error" but do NOT crash the process, because the pool will automatically remove the broken client and create a new one on the next query. The connect event fires when a new client is created, log it at debug level.

Third, create src/server.js. Create an Express application. Add express.json() middleware with a limit of "10mb" for the request body size. This large limit is needed because some API requests (like registering a backing datasource with a very large column mapping) can have substantial JSON bodies. Add cors() middleware with no configuration (allows all origins during development). Add the request logger middleware (Task 10) and error handler middleware (Task 10) after they are created, but set up the mount points now with TODO comments.

Define a GET /health endpoint that executes SELECT NOW() against PostgreSQL and returns status 200 with body {"status":"healthy","database":"connected","timestamp":"<result of NOW()>"}. If the query fails, return status 503 with body {"status":"unhealthy","database":"disconnected","error":"<error message>"}. This endpoint is used by the human operator and later by Kubernetes health checks to verify the system is running.

The server must listen on the port specified by process.env.PORT or default 3000. Before starting the listener, execute a startup check: call pool.query("SELECT NOW()"). If this succeeds, log "Ontology Engine started on port 3000 | PostgreSQL connected" and start listening. If this fails, log "FATAL: Cannot connect to PostgreSQL: <error message>" and call process.exit(1). The server must NOT start if the database is unreachable because every subsequent request would fail anyway.

Set package.json scripts: "start" runs "node src/server.js", "dev" runs "nodemon src/server.js", "migrate" runs "node src/migrate.js", "seed" runs "node src/seed.js", "test" runs "node tests/day1.test.js".

**Files to create:** package.json, src/db.js, src/server.js
**Verification:** npm run dev starts server. curl localhost:3000/health returns healthy JSON. Stop PostgreSQL container, curl returns 503.
