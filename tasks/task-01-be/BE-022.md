# BE-022: Implement Consistent API Response Envelope

**Palantir Feature:** Project Setup — Predictable API contract (standardized response format across all endpoints)

## Reuse from Ontology Engine (Daily Tasks)

**Monday Task 9** (`/src/utils/responseFormatter.js`) already implements a response formatter with:
- `successResponse(data, message)` → `{ success: true, data, message, timestamp }`
- `errorResponse(error, statusCode)` → `{ success: false, error: { code, message, details }, timestamp }`
- `paginatedResponse(data, pagination)` → includes `nextPageToken`, `totalCount`
- Consistent error code strings: `VALIDATION_ERROR`, `NOT_FOUND`, `DUPLICATE`, `INTERNAL_ERROR`

**Sunday Task 12** implements a global error handler middleware:
- Custom error classes (`AppError`, `NotFoundError`, `ValidationError`, `ConflictError`)
- PostgreSQL error code mapping (23505 → CONFLICT, 23503 → FK_VIOLATION)
- OpenSearch error mapping
- Development vs. production error detail exposure

**What to reuse vs. build new:**
- **REUSE** Monday Task 9's response formatter directly — the envelope shape `{ success, data, error }` is identical to BE-022. Port to TypeScript and add the `meta` field for paginated responses
- **REUSE** Sunday Task 12's error handler pattern — custom error classes, PG error code mapping, and dev/prod behavior already match BE-022's requirements
- **BUILD NEW** the TypeScript type definitions (`ErrorCode` type, `ValidationErrorDetail` interface), the `paginated()` helper with `{ total, page, limit, totalPages }` meta shape
- **IMPROVE** Monday's formatter by adding the `DATASET_NOT_READY`, `FILE_TOO_LARGE`, `UNSUPPORTED_FILE` error codes specific to the data ingestion layer. Consider standardizing error codes across both services.

## Objective

Standardize all API responses into a consistent envelope format. Create response helper functions, define error code constants, update the global error handler to use the envelope format, and refactor all existing controllers to use the helpers. **This task must be implemented BEFORE BE-021** so the validation middleware can use the standard envelope.

## Response Envelope Formats

### Success Response
```json
{
  "success": true,
  "data": { /* any payload */ }
}
```

### Paginated Success Response
```json
{
  "success": true,
  "data": [{ /* items */ }],
  "meta": {
    "total": 150,
    "page": 2,
    "limit": 20,
    "totalPages": 8
  }
}
```

### Error Response
```json
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "Project not found",
    "details": null
  }
}
```

## Response Helper Functions

Create `src/utils/response.ts`:

```typescript
import { Response } from 'express';

export function success(res: Response, data: unknown, statusCode: number = 200): void {
  res.status(statusCode).json({ success: true, data });
}

export function paginated(
  res: Response,
  data: unknown[],
  meta: { total: number; page: number; limit: number; totalPages: number }
): void {
  res.status(200).json({ success: true, data, meta });
}

export function error(
  res: Response,
  statusCode: number,
  code: string,
  message: string,
  details: ValidationErrorDetail[] | null = null
): void {
  res.status(statusCode).json({
    success: false,
    error: { code, message, details }
  });
}
```

The `details` parameter is typed as `ValidationErrorDetail[] | null` (not `any`). It is only used for validation errors (from BE-021). For all other errors, pass `null`.

## Update Global Error Handler

Modify `src/middleware/errorHandler.ts` to use the envelope format:

```typescript
import { error as errorResponse } from '@/utils/response';
import { ERROR_CODES } from '@/types/errorCodes';

export function errorHandler(err: Error, req: Request, res: Response, next: NextFunction): void {
  if (err instanceof AppError && err.isOperational) {
    errorResponse(res, err.statusCode, err.code, err.message);
    return;
  }

  // Log the full error for debugging
  logger.error('Unhandled error', { error: err.message, stack: err.stack });

  if (process.env.NODE_ENV === 'development') {
    errorResponse(res, 500, ERROR_CODES.INTERNAL_ERROR, err.message, null);
  } else {
    errorResponse(res, 500, ERROR_CODES.INTERNAL_ERROR, 'An unexpected error occurred');
  }
}
```

## Refactoring Existing Controllers

Replace all `res.json()` and `res.status().json()` calls with envelope helpers in these files:

1. **`src/controllers/projectController.ts`**
   - `res.status(201).json(project)` → `success(res, project, 201)`
   - `res.json(projects)` → `success(res, projects)`
   - `res.status(204).send()` → stays as-is (204 has no body)

2. **`src/controllers/folderController.ts`**
   - Same pattern: wrap all JSON responses in `success()` or `paginated()`

3. **`src/controllers/uploadController.ts`**
   - `res.status(201).json({ success: true, data: datasets.map(...) })` → `success(res, datasets.map(...), 201)`

4. **`src/controllers/datasetController.ts`**
   - Listing endpoint: use `paginated(res, datasets, { total, page, limit, totalPages })`
   - Detail endpoint: use `success(res, dataset)`

## Acceptance Criteria

- All success responses have shape `{ success: true, data: ... }`
- All paginated responses have shape `{ success: true, data: [...], meta: { total, page, limit, totalPages } }`
- All error responses have shape `{ success: false, error: { code, message, details } }`
- `success(res, data)` sends 200 with correct envelope
- `success(res, data, 201)` sends 201 with correct envelope
- `paginated(res, data, meta)` sends 200 with data array and meta object
- `error(res, 404, 'NOT_FOUND', 'message')` sends 404 with error envelope
- Global error handler uses envelope format for both operational and unexpected errors
- Unexpected errors in production show generic message, not stack trace
- Unexpected errors in development show the actual error message
- All error code constants are defined and exported from `src/types/errorCodes.ts`
- All four controller files use response helpers instead of raw `res.json()`
- 204 responses (DELETE) remain as `res.status(204).send()` (no envelope needed)
- Existing API behavior is preserved — only the response wrapper changes
