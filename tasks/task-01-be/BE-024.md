# BE-024: Implement Structured Logging with Winston and Correlation IDs

**Palantir Feature:** Project Setup — Operational observability (structured JSON logging with request correlation)

## Reuse from Ontology Engine (Daily Tasks)

**Monday Task 8** already implements request logging middleware:
- Logs HTTP method, URL, status code, and response time for every request
- `console.log` with structured format: `[REQUEST] ${method} ${url} → ${status} (${duration}ms)`
- Applied globally in the Express middleware chain

**Sunday Task 13** implements structured request logging:
- JSON log format with `{ timestamp, method, path, statusCode, responseTime, ip, userAgent }`
- Header sanitization (strips Authorization, Cookie values)
- Response body size tracking

**Sunday Task 14** implements structured logging throughout:
- Winston-based logger with JSON format for production
- Color-coded console output for development
- Log levels (error, warn, info, debug)
- `logInfo()`, `logError()`, `logWarn()` convenience functions

**What to reuse vs. build new:**
- **REUSE** Sunday Task 14's Winston configuration pattern — port to TypeScript, the JSON production format and colorized dev format are directly applicable
- **REUSE** Sunday Task 13's header sanitization logic — prevents sensitive data (Authorization tokens) from appearing in logs
- **REUSE** Monday Task 8's request timing pattern (`Date.now()` diff before/after) — adapt into the Morgan stream integration
- **BUILD NEW** the `AsyncLocalStorage`-based correlation ID propagation (neither the ontology-engine's Monday nor Sunday tasks implement correlation IDs — this is a genuinely new capability), the `X-Request-ID` header forwarding, and the Morgan-through-Winston stream piping
- **IMPROVE** the ontology-engine's logging by backporting correlation ID support. The ontology-engine currently has no way to trace a request across multiple service calls — correlation IDs would significantly improve debuggability.

## Objective

Replace all `console.log` and `console.error` calls throughout the codebase with a Winston structured logger. Implement correlation ID propagation using `AsyncLocalStorage` so every log entry within a request lifecycle includes the same `correlationId`. Configure environment-specific output formats. Integrate Morgan HTTP request logging through Winston so all log output flows through a single logging pipeline.

## Winston Logger Configuration

Create `src/config/logger.ts`:

```typescript
import winston from 'winston';

const logger = winston.createLogger({
  level: config.LOG_LEVEL,
  defaultMeta: { service: 'foundry-backend' },
  transports: [
    new winston.transports.Console({
      format: config.NODE_ENV === 'production'
        ? winston.format.combine(
            winston.format.timestamp(),
            winston.format.json()
          )
        : winston.format.combine(
            winston.format.timestamp({ format: 'HH:mm:ss' }),
            winston.format.colorize(),
            winston.format.printf(({ timestamp, level, message, correlationId, ...meta }) => {
              const metaStr = Object.keys(meta).length > 1 ? ` ${JSON.stringify(meta)}` : '';
              const corrId = correlationId ? ` [${correlationId.slice(0, 8)}]` : '';
              return `${timestamp} ${level}${corrId}: ${message}${metaStr}`;
            })
          )
    })
  ]
});

export { logger };
```

## Correlation ID Middleware

Create `src/middleware/correlationId.ts`:

```typescript
import { AsyncLocalStorage } from 'async_hooks';
import { v4 as uuidv4 } from 'uuid';

interface RequestContext {
  correlationId: string;
}

export const asyncLocalStorage = new AsyncLocalStorage<RequestContext>();

export function correlationIdMiddleware(req: Request, res: Response, next: NextFunction): void {
  const correlationId = (req.headers['x-request-id'] as string) || uuidv4();
  res.setHeader('X-Request-ID', correlationId);

  asyncLocalStorage.run({ correlationId }, () => {
    next();
  });
}

export function getCorrelationId(): string | undefined {
  return asyncLocalStorage.getStore()?.correlationId;
}
```

### Logger Wrapper

Create a wrapper that auto-injects the correlation ID into every log entry:

```typescript
// In src/config/logger.ts
export function log(level: string, message: string, meta?: Record<string, unknown>): void {
  const correlationId = getCorrelationId();
  logger.log(level, message, { ...meta, correlationId });
}

// Convenience methods
export const logInfo = (msg: string, meta?: Record<string, unknown>) => log('info', msg, meta);
export const logError = (msg: string, meta?: Record<string, unknown>) => log('error', msg, meta);
export const logWarn = (msg: string, meta?: Record<string, unknown>) => log('warn', msg, meta);
export const logDebug = (msg: string, meta?: Record<string, unknown>) => log('debug', msg, meta);
```

## Morgan Integration

Pipe Morgan HTTP request logging through Winston instead of directly to stdout. In `src/index.ts`, replace the existing Morgan setup:

```typescript
// BEFORE (BE-001)
app.use(morgan(config.NODE_ENV === 'production' ? 'combined' : 'dev'));

// AFTER
app.use(morgan('combined', {
  stream: {
    write: (message: string) => logger.log('http', message.trim())
  }
}));
```

This ensures all HTTP request logs appear in the same structured format as application logs, with consistent JSON formatting in production.

## Replacing console.log/console.error

Replace all `console.log` and `console.error` calls across the codebase with the appropriate logger method:

| File Pattern | Replacement Rule |
|-------------|-----------------|
| `src/services/*.ts` | `console.log(...)` → `logInfo(...)`, `console.error(...)` → `logError(...)` |
| `src/middleware/errorHandler.ts` | `console.error(...)` → `logError('Unhandled error', { error: err.message, stack: err.stack })` |
| `src/index.ts` | `console.log('Server running...')` → `logInfo('Server running', { port: PORT })` |
| `src/jobs/*.ts` | `console.log(...)` → `logInfo(...)`, `console.error(...)` → `logError(...)` |

Use appropriate log levels:
- `logError()` — for errors and exceptions
- `logWarn()` — for warnings (e.g., file cleanup failures, deprecated endpoint usage)
- `logInfo()` — for operational messages (startup, shutdown, request completion)
- `logDebug()` — for diagnostic detail (query execution, cache hits/misses)
