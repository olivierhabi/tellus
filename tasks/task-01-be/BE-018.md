# BE-018: Implement Dataset Versioning with Immutable History

**Palantir Feature:** Data Ingestion — Foundry immutable versioned datasets (patent US9,483,506B2). In Foundry, every dataset is versioned — each write transaction creates a new immutable version. Users can browse version history and roll back to prior versions. This task implements a simplified file-based analog of that system.

## Objective

Implement dataset versioning so that re-uploading a file with the same name to the same folder creates a new version instead of a separate dataset. Build endpoints to list versions, view specific version details, preview historical versions, and restore old versions by creating a new version from a historical snapshot.

## Database Schema

Create a new migration file `src/migrations/005_create_dataset_versions.ts`:

**dataset_versions table:**
- `id` UUID PRIMARY KEY DEFAULT gen_random_uuid()
- `dataset_id` UUID NOT NULL REFERENCES datasets(id) ON DELETE CASCADE
- `version_number` INTEGER NOT NULL
- `file_path` TEXT NOT NULL (path to this version's file on disk)
- `row_count` INTEGER
- `column_count` INTEGER
- `schema_info` JSONB (parsed schema metadata for this version)
- `created_by` UUID REFERENCES users(id) ON DELETE SET NULL
- `created_at` TIMESTAMPTZ DEFAULT NOW()
- UNIQUE(dataset_id, version_number)

Add index: `CREATE INDEX idx_dataset_versions_dataset ON dataset_versions(dataset_id)`.

Migration `down()` drops the index and the table.

**Note on the `datasets` table relationship:** The `datasets` table continues to store the "current" state — its `file_path`, `row_count`, `column_count`, `schema_info`, and `status` fields always reflect the latest version. When a new version is created, both the `dataset_versions` row and the `datasets` row are updated in the same transaction. The `dataset_columns` table always reflects the latest version's column metadata. Historical column metadata is preserved in each version's `schema_info` JSONB field.

## Version Detection During Upload

Modify `src/services/uploadService.ts` `processUpload()` to detect re-uploads:

After Multer saves the file and before the database INSERT, check for an existing dataset with the same name in the target folder:

```sql
SELECT d.id, COALESCE(MAX(v.version_number), 0) AS latest_version
FROM datasets d
LEFT JOIN dataset_versions v ON v.dataset_id = d.id
WHERE d.name = $1 AND d.folder_id = $2
GROUP BY d.id
```

- **If no match found:** Create a new dataset record (existing BE-005 behavior) AND create a `dataset_versions` row with `version_number = 1`.
- **If match found:** Do NOT create a new dataset record. Instead:
  1. Create a `dataset_versions` row with `version_number = latest_version + 1`, the new `file_path`, and `created_by = req.user.id`.
  2. Update the existing `datasets` row: set `file_path` to the new file, `status = 'pending'`, `row_count = NULL`, `column_count = NULL`, `updated_at = NOW()`.
  3. Schedule a parse job for the existing dataset ID (re-parsing updates `datasets` and `dataset_columns` with the new version's schema).

Both paths (new dataset + new version) run within the same Knex transaction.

## Backfill Existing Datasets

In the migration `up()`, after creating the `dataset_versions` table, backfill all existing datasets:

```sql
INSERT INTO dataset_versions (dataset_id, version_number, file_path, row_count, column_count, schema_info, created_at)
SELECT id, 1, file_path, row_count, column_count, schema_info, created_at
FROM datasets
```

This ensures every existing dataset has at least version 1.

## Version Listing Endpoint

`GET /api/datasets/:datasetId/versions`

Query:
```sql
SELECT v.*, u.display_name AS created_by_name
FROM dataset_versions v
LEFT JOIN users u ON u.id = v.created_by
WHERE v.dataset_id = $1
ORDER BY v.version_number DESC
```

Return 200 with array of version objects. Return 404 if dataset not found.

## Version Detail Endpoint

`GET /api/datasets/:datasetId/versions/:versionNumber`

Query:
```sql
SELECT v.*, u.display_name AS created_by_name
FROM dataset_versions v
LEFT JOIN users u ON u.id = v.created_by
WHERE v.dataset_id = $1 AND v.version_number = $2
```

Return 200 with the version object including `schema_info`. Return 404 if version not found.

## Preview and Detail with Version Parameter

Update the existing `GET /api/datasets/:datasetId/preview` and `GET /api/datasets/:datasetId` endpoints to accept an optional `?version=N` query parameter:

- When `?version` is omitted: use the current `datasets.file_path` (latest version behavior — no change from BE-007).
- When `?version=N` is provided: look up the version's `file_path` from `dataset_versions` where `dataset_id = $1 AND version_number = $2`. Return 404 with `'Version N not found for this dataset'` if not found. Use the version's file path for preview/detail.

For the detail endpoint with `?version=N`, return column metadata from the version's `schema_info` JSONB instead of the `dataset_columns` table (which only stores the latest version's columns).

## Restore Endpoint

`POST /api/datasets/:datasetId/versions/:versionNumber/restore`

Restoring a version creates a NEW version (highest number + 1) by copying the historical version's file:

1. Look up the historical version: `SELECT * FROM dataset_versions WHERE dataset_id = $1 AND version_number = $2`. Return 404 if not found.
2. Check if the historical file exists on disk: `fs.promises.access(version.file_path, fs.constants.F_OK)`. If not found, return 410 Gone with `'Historical version file is no longer available on disk'`.
3. Get the latest version number: `SELECT MAX(version_number) AS max FROM dataset_versions WHERE dataset_id = $1`.
4. Copy the file: `fs.promises.copyFile(version.file_path, newFilePath)` where `newFilePath` uses a new UUID prefix in the same directory.
5. In a Knex transaction:
   a. Insert new `dataset_versions` row with `version_number = max + 1`.
   b. Update `datasets` row with new `file_path`, `status = 'pending'`, clear `row_count` and `column_count`.
6. Schedule a parse job for the dataset.
7. If the transaction fails, delete the copied file in a catch block.
8. Return 201 with the new version object.

## Acceptance Criteria

- Re-uploading a file with the same name to the same folder creates a new version (version_number increments)
- Re-uploading a file with a new name creates a new dataset with version_number = 1
- First upload of any file creates both a dataset record and a version 1 record
- Migration backfills existing datasets with version 1 records
- GET /api/datasets/:id/versions returns all versions ordered by version_number DESC
- GET /api/datasets/:id/versions/:num returns specific version detail
- GET /api/datasets/:id/versions/:num returns 404 for non-existent version
- GET /api/datasets/:id/preview without ?version= returns latest version preview
- GET /api/datasets/:id/preview?version=1 returns version 1 file preview
- GET /api/datasets/:id?version=1 returns version 1 schema from schema_info JSONB
- POST /api/datasets/:id/versions/:num/restore creates a new version (highest number + 1) by copying the file
- POST restore returns 404 for non-existent version number
- POST restore returns 410 when the historical version's file is missing from disk
- Restore triggers a re-parse of the dataset (status goes to 'pending' then 'processing' then 'ready')
- If restore file copy succeeds but DB transaction fails, the copied file is cleaned up
- dataset_versions has UNIQUE(dataset_id, version_number) constraint enforced
- datasets table always reflects the latest version's file_path, row_count, column_count
- dataset_columns always reflects the latest version's column metadata
- Migration down() drops dataset_versions table
