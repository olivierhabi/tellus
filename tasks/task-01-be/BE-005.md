## Objective

Build the file upload endpoint that accepts one or more CSV files via multipart/form-data, stores them on disk with collision-proof naming, validates file types and sizes with streaming (never buffering the entire file in memory), creates corresponding dataset records in the database within a transaction, and triggers background CSV parsing jobs. This is the entry point for all data into the system — the Pipeline Builder and Ontology Manager both operate on datasets created through this upload mechanism. The upload is all-or-nothing: all files in a batch are processed within a single database transaction. If any file fails (constraint violation, disk error, or any other failure), the entire transaction rolls back — all database records are removed and all stored files are deleted from disk. No orphaned records or files should remain. This atomic approach is simpler and safer than partial-success semantics because it eliminates the complexity of communicating mixed success/failure states to the frontend.

## Why Disk Storage, Not Memory Storage

Multer, the standard Express middleware for multipart file handling, offers two storage engines: `multer.memoryStorage()` and `multer.diskStorage()`. Memory storage reads the entire file into a Node.js Buffer object in RAM. Disk storage streams the file directly to a temporary location on disk.

The choice of disk storage is a critical architectural decision. Memory storage means a 500MB CSV upload consumes 500MB of server RAM for the duration of the request. With 10 concurrent uploads, that is 5GB of RAM solely for file buffering — far exceeding typical server memory allocations. Additionally, Node.js imposes a maximum Buffer size (approximately 2GB on 64-bit systems), meaning files larger than 2GB would cause a hard crash with memory storage. Disk storage streams the file to disk with approximately 64KB of buffer at any given time, regardless of file size. A 10GB file and a 10KB file use the same ~64KB of memory during upload.

## Multer Configuration

Create `src/config/multer.ts` with a factory function pattern. The factory is necessary because Multer's storage configuration needs `projectId` and `folderId` from the URL parameters, which are not available at module import time — they only exist when a request arrives.

```typescript
import multer from 'multer';
import path from 'path';
import fs from 'fs';
import { v4 as uuidv4 } from 'uuid';
import { AppError } from '@/utils/AppError';

export function createUploadMiddleware(uploadDir: string, maxSizeMB: number) {
  const storage = multer.diskStorage({
    destination: (req, _file, cb) => {
      const dir = path.join(uploadDir, req.params.projectId, req.params.folderId);
      fs.mkdirSync(dir, { recursive: true });
      cb(null, dir);
    },
    filename: (_req, file, cb) => {
      const uniqueName = uuidv4() + '_' + file.originalname.replace(/[^a-zA-Z0-9._-]/g, '_');
      cb(null, uniqueName);
    }
  });

  const fileFilter = (_req: any, file: Express.Multer.File, cb: multer.FileFilterCallback) => {
    const ext = path.extname(file.originalname).toLowerCase();
    const allowed = ['.csv', '.tsv', '.txt'];
    if (allowed.includes(ext)) {
      cb(null, true);
    } else {
      cb(new AppError(415, `Unsupported file type: ${ext}. Only CSV, TSV, and TXT files are accepted.`));
    }
  };

  return multer({
    storage,
    fileFilter,
    limits: {
      fileSize: maxSizeMB * 1024 * 1024,
      files: 10
    }
  });
}
```

The `filename` function generates a UUID-prefixed filename: `a1b2c3d4_orders_office_goods.csv`. The UUID prefix guarantees uniqueness even when multiple users upload files with identical names simultaneously. The `replace(/[^a-zA-Z0-9._-]/g, '_')` sanitizes the original filename by replacing special characters with underscores, preventing filesystem issues with names containing spaces, unicode, or shell-special characters.

The `destination` function creates the directory tree `<UPLOAD_DIR>/<projectId>/<folderId>/` if it doesn't exist. The `recursive: true` option on `mkdirSync` creates all parent directories, handling the case where neither the project directory nor the folder directory exist yet.

## Upload Service Implementation

Create `src/services/uploadService.ts` with a `processUpload` method that accepts the project ID, folder ID, owner ID, and the array of Multer file objects. The entire operation is wrapped in a Knex transaction to ensure atomicity.

```typescript
async processUpload(
  projectId: string,
  folderId: string,
  ownerId: string,
  files: Express.Multer.File[]
): Promise<Dataset[]> {
  const createdDatasets: Dataset[] = [];
  const storedFilePaths: string[] = files.map(f => f.path);

  try {
    return await this.knex.transaction(async (trx) => {
      for (const file of files) {
        // Extract dataset name: "orders_office_goods.csv" → "orders_office_goods"
        const datasetName = path.basename(file.originalname, path.extname(file.originalname));

        const [dataset] = await trx('datasets').insert({
          name: datasetName,
          folder_id: folderId,
          file_path: file.path,
          original_filename: file.originalname,
          mime_type: file.mimetype || 'text/csv',
          file_size_bytes: file.size,
          status: 'pending'
        }).returning('*');

        createdDatasets.push(dataset);
      }

      return createdDatasets;
    });
  } catch (error) {
    // Transaction failed — clean up ALL stored files
    await Promise.allSettled(
      storedFilePaths.map(fp =>
        fs.promises.unlink(fp).catch(() => {}) // Ignore cleanup errors
      )
    );
    throw error;
  }
}
```

The critical detail is the error handling: if the database transaction fails (for any reason — constraint violation, connection error, disk full), ALL uploaded files must be deleted from disk. The `storedFilePaths` array is populated from Multer's output before the transaction begins, so it's available in the catch block even if the transaction never started. `Promise.allSettled` is used instead of `Promise.all` because we want to attempt deletion of every file regardless of whether earlier deletions failed. The inner `.catch(() => {})` silences individual file deletion errors (the file might not exist if Multer failed mid-stream).

After the transaction succeeds, schedule CSV parsing for each dataset:

```typescript
for (const dataset of createdDatasets) {
  scheduleParseJob(dataset.id);
  eventBus.emit('upload.completed', {
    event: 'upload.completed',
    projectId,
    payload: { datasetId: dataset.id, fileName: dataset.original_filename }
  });
}
```

The parsing jobs run asynchronously — they do NOT block the upload response. The frontend receives the dataset objects with `status: 'pending'` immediately and uses either WebSocket notifications (BE-012) or polling (GET /api/v1/datasets/:id/status) to track when parsing completes.

## Upload Controller Implementation

Create `src/controllers/uploadController.ts`. The controller must perform pre-upload validation before Multer processes any files:

```typescript
async upload(req: Request, res: Response, next: NextFunction) {
  try {
    const { projectId, folderId } = req.params;

    // 1. Validate project exists BEFORE accepting files
    const project = await this.projectService.getProjectById(projectId, req.user.id);
    if (!project) throw new AppError(404, 'Project not found');

    // 2. Validate folder exists BEFORE accepting files
    const folder = await this.folderService.getFolderById(projectId, folderId);
    if (!folder) throw new AppError(404, 'Folder not found');

    // 3. Now process the multipart upload
    const upload = createUploadMiddleware(config.UPLOAD_DIR, config.MAX_FILE_SIZE_MB);
    const multerMiddleware = upload.array('files', 10);

    multerMiddleware(req, res, async (multerError) => {
      if (multerError) {
        // Map Multer error codes to HTTP status codes
        if (multerError instanceof multer.MulterError) {
          switch (multerError.code) {
            case 'LIMIT_FILE_SIZE':
              return next(new AppError(413, `File exceeds maximum size of ${config.MAX_FILE_SIZE_MB}MB`));
            case 'LIMIT_FILE_COUNT':
              return next(new AppError(400, 'Maximum 10 files per upload'));
            case 'LIMIT_UNEXPECTED_FILE':
              return next(new AppError(400, `Unexpected field name. Use 'files' as the form field name.`));
            default:
              return next(new AppError(400, multerError.message));
          }
        }
        return next(multerError);
      }

      // 4. Verify files were provided
      const files = req.files as Express.Multer.File[];
      if (!files || files.length === 0) {
        return next(new AppError(400, 'No files provided. Send files using the "files" form field.'));
      }

      // 5. Process the upload (DB records + schedule parsing)
      const datasets = await this.uploadService.processUpload(
        projectId, folderId, req.user.id, files
      );

      res.status(201).json({
        success: true,
        data: datasets.map(d => ({
          id: d.id,
          name: d.name,
          originalFilename: d.original_filename,
          fileSizeBytes: d.file_size_bytes,
          fileSizeHuman: formatFileSize(d.file_size_bytes),
          status: d.status,
          folderId: d.folder_id,
          createdAt: d.created_at
        }))
      });
    });
  } catch (error) {
    next(error);
  }
}
```

The order of operations is deliberate: validate project and folder existence FIRST, before Multer processes any file data. This prevents storing files in orphaned directories (directories for non-existent projects/folders). Without this pre-validation, a request to upload to a deleted project would succeed in storing files on disk but fail when creating database records, leaving orphaned files.

## Acceptance Criteria

- Single CSV file upload creates one dataset record with status 'pending' and returns 201
- Batch upload of 3 CSV files (matching Palantir course) creates 3 records in one request
- Files stored at `UPLOAD_DIR/<projectId>/<folderId>/<uuid>_<sanitized_filename>`
- Directories created automatically via mkdirSync recursive
- Files exceeding MAX_FILE_SIZE_MB rejected with 413 BEFORE full file is buffered
- Non-CSV files (.xlsx, .pdf, .exe) rejected with 415 and descriptive message
- Upload to non-existent project returns 404 before any file storage occurs
- Upload to non-existent folder returns 404 before any file storage occurs
- If database transaction fails after files are stored, all files are cleaned up
- Response includes array with id, name, originalFilename, fileSizeBytes, fileSizeHuman, status
- CSV parsing jobs are scheduled but do NOT block the HTTP response
- Concurrent uploads by different users to the same folder do not conflict (UUID filenames)
