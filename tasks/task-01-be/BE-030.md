# BE-030: Implement Graceful Shutdown with Connection Draining

**Palantir Feature:** Project Setup — Production server lifecycle (graceful shutdown with zero data loss)

- **REUSE** the active request draining approach — Sunday tracks active requests via middleware and waits for them to complete before closing the server

Consider backporting these improvements — especially the configurable timeout and the in-progress indexing job reset (`UPDATE funnel_state SET status = 'pending' WHERE status = 'indexing'`).

## Objective

Handle OS signals (SIGTERM, SIGINT) to gracefully shut down the server: stop accepting new connections, drain existing connections with a configurable timeout, close the database pool, close WebSocket connections, reset in-progress dataset processing so records are not stuck in an error state, and clean up temporary files. This ensures zero data loss during deployments and restarts.

## Shutdown Module

Create `src/utils/shutdown.ts`:

```typescript
import { Server } from 'http';
import { Knex } from 'knex';
import { WebSocketServer, WebSocket } from 'ws';
import { logger } from '@/config/logger';

let isShuttingDown = false;

export async function shutdown(
  server: Server,
  knex: Knex,
  wss: WebSocketServer | null
): Promise<void> {
  if (isShuttingDown) {
    logger.warn('Forced shutdown (second signal received)');
    process.exit(1);
  }

  isShuttingDown = true;
  logger.info('Shutting down gracefully...');

  const timeoutMs = Number(process.env.SHUTDOWN_TIMEOUT_MS) || 30000;

  // Start hard timeout
  const forceTimeout = setTimeout(() => {
    logger.error('Graceful shutdown timed out, forcing exit');
    process.exit(1);
  }, timeoutMs);
  forceTimeout.unref(); // Don't prevent Node from exiting if everything else is done

  try {
    // Step 1: Stop accepting new HTTP connections
    await new Promise<void>((resolve) => {
      server.close(() => resolve());
    });
    logger.info('HTTP server closed');

    // Step 2: Close WebSocket connections
    if (wss) {
      wss.clients.forEach((client) => {
        if (client.readyState === WebSocket.OPEN) {
          client.close(1001, 'Server shutting down');
        }
      });
      await new Promise<void>((resolve) => {
        wss.close(() => resolve());
      });
      logger.info('WebSocket server closed');
    }

    // Step 3: Reset in-progress dataset processing
    const resetCount = await knex('datasets')
      .where({ status: 'processing' })
      .update({ status: 'pending', updated_at: knex.fn.now() });
    if (resetCount > 0) {
      logger.info(`Reset ${resetCount} in-progress datasets to pending`);
    }

    // Step 4: Drain database connection pool
    await knex.destroy();
    logger.info('Database pool drained');

    // Step 5: Clean up temp files
    await cleanupTempFiles();
    logger.info('Temp files cleaned up');

    clearTimeout(forceTimeout);
    logger.info('Graceful shutdown completed');
    process.exit(0);
  } catch (error) {
    logger.error('Error during graceful shutdown', { error: (error as Error).message });
    clearTimeout(forceTimeout);
    process.exit(1);
  }
}

export function getIsShuttingDown(): boolean {
  return isShuttingDown;
}
```

### Why Reset Processing to Pending

When the server shuts down, any dataset with `status = 'processing'` has its parse job interrupted mid-execution. If left as `processing`, these datasets appear permanently stuck — they never transition to `ready` or `error`. Resetting them to `pending` allows the parse job to be re-scheduled on server restart. This is a global UPDATE (no project/user scoping) because shutdown affects all in-flight processing regardless of ownership.

### Temp File Cleanup

```typescript
async function cleanupTempFiles(): Promise<void> {
  try {
    const tmpDir = os.tmpdir();
    const entries = await fs.promises.readdir(tmpDir);
    const foundryTemps = entries.filter(e => e.startsWith('foundry-upload-'));
    for (const entry of foundryTemps) {
      const fullPath = path.join(tmpDir, entry);
      await fs.promises.rm(fullPath, { recursive: true, force: true });
    }
  } catch (error) {
    // Log but don't fail shutdown for temp file cleanup issues
    logger.warn('Failed to clean up some temp files', { error: (error as Error).message });
  }
}
```

The `foundry-upload-*` temp files are created by the ZIP upload service (BE-016) when extracting ZIP archives to `os.tmpdir()`. If a ZIP upload is interrupted during extraction, the temp directory may remain. This cleanup ensures they are removed on shutdown.

## Signal Registration

In `src/index.ts`, register signal handlers after server startup:

```typescript
import { shutdown } from '@/utils/shutdown';

const server = http.createServer(app);
initWebSocketServer(server); // From BE-012
const wss = getWebSocketServer(); // Export a getter from BE-012

server.listen(PORT, () => {
  logger.info(`Server running on port ${PORT}`);

  process.on('SIGTERM', () => shutdown(server, knex, wss));
  process.on('SIGINT', () => shutdown(server, knex, wss));
});
```

### Second Signal = Force Exit

The `isShuttingDown` boolean check at the top of `shutdown()` ensures that receiving a second signal during an ongoing shutdown triggers an immediate `process.exit(1)`. This is standard Unix behavior — Ctrl+C once for graceful, Ctrl+C twice for force.

## SHUTDOWN_TIMEOUT_MS Environment Variable

Add to `src/config/environment.ts` Zod schema:

```typescript
SHUTDOWN_TIMEOUT_MS: z.coerce.number().int().min(5000).max(120000).default(30000)
```

Default 30 seconds. In development, you might want a shorter timeout (5 seconds). In production with long-running connections, up to 120 seconds.

Update `.env.example` to include `SHUTDOWN_TIMEOUT_MS=30000`.

## Exporting for Tests

The `shutdown()` function is exported for programmatic use in tests. Tests should mock `process.exit` to prevent the test process from actually exiting:

```typescript
// In tests
jest.spyOn(process, 'exit').mockImplementation(() => { throw new Error('exit called'); });
```

## Acceptance Criteria

- Sending SIGTERM to the running server logs "Shutting down gracefully..." and exits with code 0
- Active HTTP connections complete before the server closes (server.close waits for in-flight requests)
- After shutdown, no dataset records have `status = 'processing'` (all reset to 'pending')
- WebSocket clients receive close frame with code 1001 and reason "Server shutting down"
- Database connection pool is drained (no dangling connections)
- Temp files matching `foundry-upload-*` in os.tmpdir() are deleted
- Sending SIGTERM twice in rapid succession exits immediately with code 1 on the second signal
- If shutdown takes longer than SHUTDOWN_TIMEOUT_MS, process.exit(1) is called
- The shutdown() function can be called programmatically in tests
- SHUTDOWN_TIMEOUT_MS is configurable via environment variable (default 30000)
- The isShuttingDown flag prevents duplicate shutdown sequences
- Shutdown completes within 5 seconds when no connections are active
