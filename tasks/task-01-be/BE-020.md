# BE-020: Implement Request Rate Limiting with Sliding Window Algorithm

**Palantir Feature:** Project Setup — Platform stability (protect endpoints from abuse via per-category rate limits)

- `createRateLimiter({ windowMs, maxRequests, keyGenerator })` factory function
- In-memory store with `Map<string, { count, windowStart }>` tracking

**What to reuse vs. build new:**
- **REUSE** Friday Task 25's rate limiter implementation directly — port to TypeScript and extend with the sliding-window-log algorithm (Friday uses a simpler fixed-window approach; BE-020 uses a more precise sliding-window-log with timestamp arrays)
- **REUSE** the header format and 429 response shape — already matches the BE-020 spec
- **BUILD NEW** the per-category configuration (upload/read/write/auth categories), the `RATE_LIMIT_MULTIPLIER` env variable, user-based key extraction (Friday only uses IP-based), and the periodic memory cleanup interval
- **IMPROVE** Friday's fixed-window implementation by upgrading to sliding-window-log (more accurate, prevents burst at window boundaries). Consider backporting this improvement to the ontology-engine's rate limiter

## Objective

Create a `rateLimiter` middleware factory using a sliding-window-log algorithm, configure per-endpoint-category limits, and apply rate limits to all route definitions. The rate limiter uses an in-memory store (not shared across processes — multi-process shared state is explicitly out of scope for this task).

## Rate Limiter Middleware Factory

Create `src/middleware/rateLimiter.ts`:

```typescript
interface RateLimitConfig {
  maxRequests: number;
  windowMs: number;
  keyExtractor: (req: Request) => string;
}

export function rateLimiter(config: RateLimitConfig) {
  const store = new Map<string, number[]>();

  return (req: Request, res: Response, next: NextFunction) => {
    const key = config.keyExtractor(req);
    const now = Date.now();
    const windowStart = now - config.windowMs;

    // Get or create timestamp array for this key
    let timestamps = store.get(key) || [];

    // Remove timestamps older than the window
    timestamps = timestamps.filter(ts => ts > windowStart);

    // Check if limit is exceeded
    if (timestamps.length >= config.maxRequests) {
      const oldestInWindow = timestamps[0];
      const retryAfterMs = oldestInWindow + config.windowMs - now;
      const retryAfterSec = Math.ceil(retryAfterMs / 1000);

      res.set('X-RateLimit-Limit', String(config.maxRequests));
      res.set('X-RateLimit-Remaining', '0');
      res.set('X-RateLimit-Reset', String(Math.ceil((oldestInWindow + config.windowMs) / 1000)));
      res.set('Retry-After', String(retryAfterSec));

      return res.status(429).json({
        success: false,
        error: {
          code: 'RATE_LIMITED',
          message: 'Too many requests. Please try again later.',
          retryAfter: retryAfterSec
        }
      });
    }

    // Add current timestamp and store
    timestamps.push(now);
    store.set(key, timestamps);

    // Set rate limit headers on successful requests
    res.set('X-RateLimit-Limit', String(config.maxRequests));
    res.set('X-RateLimit-Remaining', String(config.maxRequests - timestamps.length));
    res.set('X-RateLimit-Reset', String(Math.ceil((now + config.windowMs) / 1000)));

    next();
  };
}
```

### Memory Cleanup

Add a periodic cleanup interval to evict expired entries from the store:

```typescript
setInterval(() => {
  const now = Date.now();
  for (const [key, timestamps] of store) {
    const active = timestamps.filter(ts => ts > now - config.windowMs);
    if (active.length === 0) {
      store.delete(key);
    } else {
      store.set(key, active);
    }
  }
}, config.windowMs); // Run cleanup once per window period
```

## Key Extractors

```typescript
// For authenticated endpoints: rate limit per user
const userKeyExtractor = (req: Request) => `user:${req.user?.id || 'anonymous'}`;

// For auth endpoints: rate limit per IP
const ipKeyExtractor = (req: Request) => `ip:${req.ip}`;
```

For unauthenticated requests to non-auth endpoints (e.g., `GET /health`), the rate limiter is not applied. Health endpoints are explicitly exempt from rate limiting.

## Per-Category Configuration

| Category | Max Requests | Window | Key | Applied To |
|----------|-------------|--------|-----|-----------|
| `upload` | 10 | 60 seconds | `req.user.id` | `POST .../upload` |
| `read` | 100 | 60 seconds | `req.user.id` | All `GET` routes (except health) |
| `write` | 30 | 60 seconds | `req.user.id` | All `POST`, `PUT`, `PATCH`, `DELETE` routes (except auth and upload) |
| `auth` | 5 | 60 seconds | `req.ip` | All `/api/auth/*` routes |

## Environment Multiplier

Add `RATE_LIMIT_MULTIPLIER` to `src/config/environment.ts` Zod schema:

```typescript
RATE_LIMIT_MULTIPLIER: z.coerce.number().min(1).max(100).default(1)
```

The multiplier is applied to `maxRequests` only (not to `windowMs`). In development, set `RATE_LIMIT_MULTIPLIER=10` in `.env` to allow 10x the normal limits. In production, leave at default 1.

Usage: `rateLimiter({ maxRequests: 100 * config.RATE_LIMIT_MULTIPLIER, windowMs: 60000, keyExtractor: userKeyExtractor })`.

## Applying to Routes

In each route file, apply the appropriate rate limiter:

```typescript
// src/routes/projects.ts
import { rateLimiter } from '@/middleware/rateLimiter';
const readLimit = rateLimiter({ maxRequests: 100 * config.RATE_LIMIT_MULTIPLIER, windowMs: 60000, keyExtractor: userKeyExtractor });
const writeLimit = rateLimiter({ maxRequests: 30 * config.RATE_LIMIT_MULTIPLIER, windowMs: 60000, keyExtractor: userKeyExtractor });

router.get('/', authenticate, readLimit, controller.list);
router.post('/', authenticate, writeLimit, controller.create);
```

## Acceptance Criteria

- Sending 101 GET requests within 60 seconds returns 429 on the 101st request
- 429 response includes `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After` headers
- 429 response body matches the error envelope: `{ success: false, error: { code: 'RATE_LIMITED', message, retryAfter } }`
- `X-RateLimit-Remaining` decrements correctly on each successful request
- After the window expires, requests are allowed again (sliding window, not fixed)
- Upload endpoints have a separate limit (10/min) from read endpoints (100/min)
- Auth endpoints are rate-limited by IP (5/min), not by user
- Write endpoints (POST/PUT/PATCH/DELETE) have a 30/min limit per user
- `RATE_LIMIT_MULTIPLIER=10` allows 10x the requests (1000 GETs/min instead of 100)
- GET /health is NOT rate-limited
- Two different users sending requests simultaneously are rate-limited independently
- Rate limiter cleans up expired entries (no memory leak over time)
