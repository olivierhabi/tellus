# BE-004: Implement Folder CRUD REST API with Recursive Tree Operations and Path Computation

**Palantir Feature:** Workspace Navigator — Full Folder Lifecycle Management (create, list, tree view, breadcrumb navigation, rename, move with LTREE path recalculation, cascading delete with file cleanup). In the Speedrun course, after creating the Learning Project, the user navigates inside it and creates a subfolder named "Speedrun: Your First E2E Workflow." All subsequent work (pipeline, ontology, workshop) happens inside this folder.

## Objective

Build the complete folder management API that supports creation at any nesting depth, listing folder contents with child counts, recursive subtree retrieval, ancestor breadcrumb computation, folder renaming, moving folders between parents with LTREE path recalculation for all descendants, and cascading deletion that also removes physical files. The folder system is the organizational backbone of the entire application. The Pipeline Builder saves its output dataset into a folder. The Ontology Manager references datasets in folders. The Workshop application is created within a folder context. Without a correctly functioning folder API, none of these downstream features can operate.

## Route Design

All folder routes are nested under the project scope: `/api/projects/:projectId/folders`. The Express router must use `mergeParams: true` so that `:projectId` from the parent router is accessible inside the folder router. This is a common Express gotcha — without `mergeParams`, `req.params.projectId` is `undefined` in nested routers.

The routes are:

`POST /api/projects/:projectId/folders` — Create a folder. Body: `{ name: string, parentFolderId: string | null }`. When `parentFolderId` is null or omitted, the folder is created at the root level of the project. When provided, the folder is nested under the specified parent.

`GET /api/projects/:projectId/folders` — List folders with query parameter `parentId`. When `parentId=null` (the literal string "null"), return root-level folders. When `parentId=<uuid>`, return direct children of that folder. Each folder in the response must include a `childCount` integer computed via a correlated subquery: `(SELECT COUNT(*) FROM folders WHERE parent_folder_id = f.id) AS child_count`. This count enables the frontend to show expand/collapse icons on folders that have children without fetching the children upfront.

`GET /api/projects/:projectId/folders/:folderId` — Get a single folder with its contents. Return the folder object plus two nested arrays: `children.folders` (direct child folders sorted by name ASC) and `children.datasets` (datasets in this folder sorted by name ASC). Execute both child queries in parallel using `Promise.all([childFoldersQuery, childDatasetsQuery])` to minimize response time.

`GET /api/projects/:projectId/folders/:folderId/tree` — Get the complete recursive subtree starting from this folder. This is the most query-efficient endpoint because it uses LTREE rather than recursive CTEs. The query: `SELECT id, name, parent_folder_id, path, depth, created_at FROM folders WHERE project_id = $1 AND path <@ (SELECT path FROM folders WHERE id = $2) ORDER BY path ASC`. The `<@` operator returns all folders whose path is a descendant of (or equal to) the target folder's path. The `ORDER BY path ASC` sorts results in depth-first pre-order traversal, which is exactly the order needed for the frontend to build a nested tree structure. The frontend algorithm: iterate the flat sorted list, use the `depth` field to determine nesting level, and push each folder into its parent's `children` array. This avoids the need for the backend to construct a nested JSON tree, which would require O(n log n) processing — the flat list with depth metadata lets the frontend build the tree in O(n).

`GET /api/projects/:projectId/folders/:folderId/breadcrumb` — Get the ancestor chain from root to current folder. Query: `SELECT id, name, depth FROM folders WHERE project_id = $1 AND path @> (SELECT path FROM folders WHERE id = $2) ORDER BY depth ASC`. The `@>` operator returns all folders whose path is an ancestor of the target folder's path. Prepend the project as the first breadcrumb element: `[{ id: project.id, name: project.name, type: 'project' }, ...ancestors.map(a => ({ id: a.id, name: a.name, type: 'folder' }))]`. This matches Palantir's Workspace Navigator breadcrumb exactly.

`PUT /api/projects/:projectId/folders/:folderId` — Update a folder's name and/or move it to a different parent. Accepts body `{ name?: string, parentFolderId?: string | null }`. When only `name` is provided, this is a simple database UPDATE with no path recalculation. When `parentFolderId` is provided, this triggers the full move operation with transactional LTREE path recalculation for all descendants. Both fields can be provided simultaneously (rename + move in one request). The cross-project validation check from folder creation also applies to moves: the new parent must belong to the same project. This is the most complex endpoint and requires careful transaction handling.

`DELETE /api/projects/:projectId/folders/:folderId` — Delete a folder and all contents recursively.

## Validation Rules

Define `CreateFolderSchema` in `src/types/folder.ts` using Zod:

```
z.object({
  name: z.string()
    .min(1, 'Folder name is required')
    .max(255, 'Folder name must be 255 characters or fewer')
    .trim()
    .refine(name => !name.includes('/') && !name.includes('\\'), {
      message: 'Folder name cannot contain path separators'
    }),
  parentFolderId: z.string().uuid('Invalid parent folder ID format').nullable().optional()
})
```

The `refine` check prevents folder names that could cause confusion with filesystem paths. While the LTREE path uses UUID-based segments (not folder names), allowing slashes in names would confuse users who expect slash-separated paths in breadcrumbs.

Define `UpdateFolderSchema` in the same file:

```
z.object({
  name: z.string()
    .min(1, 'Folder name is required')
    .max(255, 'Folder name must be 255 characters or fewer')
    .trim()
    .refine(name => !name.includes('/') && !name.includes('\\'), {
      message: 'Folder name cannot contain path separators'
    }).optional(),
  parentFolderId: z.string().uuid('Invalid parent folder ID format').nullable().optional()
}).refine(data => data.name !== undefined || data.parentFolderId !== undefined, {
  message: 'At least one of name or parentFolderId must be provided'
})
```

## Create Folder Implementation

The `createFolder` method in `FolderService` performs four validation steps before inserting:

Step 1 — Verify the project exists and the current user has access: `SELECT id FROM projects WHERE id = $1 AND owner_id = $2`. If no row returned, throw `AppError(404, 'Project not found')`. This prevents creating folders in projects the user doesn't own.

Step 2 — If `parentFolderId` is provided, verify it exists AND belongs to the same project: `SELECT id, project_id FROM folders WHERE id = $1`. If no row returned, throw `AppError(404, 'Parent folder not found')`. If `row.project_id !== projectId`, throw `AppError(400, 'Parent folder belongs to a different project')`. This cross-project validation is critical — without it, a malicious request could create a folder in Project A that references a parent in Project B, corrupting both folder trees.

Step 3 — Check for duplicate names under the same parent. This query must handle NULL correctly because in SQL, `NULL = NULL` evaluates to `NULL` (falsy), not `TRUE`: `SELECT id FROM folders WHERE name = $1 AND project_id = $2 AND (parent_folder_id = $3 OR (parent_folder_id IS NULL AND $3::uuid IS NULL))`. If a row exists, throw `AppError(409, 'A folder with this name already exists in this location')`.

Step 4 — Insert the folder: `INSERT INTO folders (name, parent_folder_id, project_id) VALUES ($1, $2, $3) RETURNING *`. The database trigger created in BE-002 automatically computes the `path` and `depth` columns. Return the full folder object including the computed path.

## Move Folder Implementation (The Hardest Operation)

Moving a folder requires updating the LTREE path of the moved folder AND every single descendant. This must be atomic — if the path update fails halfway through, the folder tree becomes corrupted with some folders having old paths and others having new paths.

Implementation in a Knex transaction:

```typescript
async moveFolder(projectId: string, folderId: string, newParentFolderId: string | null): Promise<Folder> {
  return this.knex.transaction(async (trx) => {
    // 1. Get the folder being moved and its current path
    const folder = await trx('folders').where({ id: folderId, project_id: projectId }).first();
    if (!folder) throw new AppError(404, 'Folder not found');
    const oldPath = folder.path;

    // 2. If moving to a new parent (not root), get the new parent's path
    let newParentPath: string | null = null;
    if (newParentFolderId) {
      const newParent = await trx('folders').where({ id: newParentFolderId, project_id: projectId }).first();
      if (!newParent) throw new AppError(404, 'Target parent folder not found');
      newParentPath = newParent.path;

      // 3. CRITICAL: Verify the new parent is NOT a descendant of the folder being moved
      // This prevents circular references (moving a folder into its own subtree)
      const isDescendant = await trx('folders')
        .where({ id: newParentFolderId })
        .whereRaw('path <@ ?', [oldPath])
        .first();
      if (isDescendant) {
        throw new AppError(400, 'Cannot move a folder into its own subtree (circular reference)');
      }
    }

    // 4. Update the folder's parent_folder_id (trigger updates its own path)
    await trx('folders').where({ id: folderId }).update({ parent_folder_id: newParentFolderId, updated_at: trx.fn.now() });

    // 5. Refresh the moved folder to get its new path (computed by trigger)
    const updatedFolder = await trx('folders').where({ id: folderId }).first();
    const newPath = updatedFolder.path;

    // 6. Update ALL descendants' paths
    // For each descendant, replace the old prefix with the new prefix
    // subpath(path, nlevel(oldPath)) extracts the relative path from the old parent
    // newPath || relative gives the new absolute path
    await trx.raw(`
      UPDATE folders
      SET path = ? || subpath(path, nlevel(?)),
          depth = nlevel(? || subpath(path, nlevel(?))) - 1,
          updated_at = NOW()
      WHERE path <@ ? AND id != ? AND project_id = ?
    `, [newPath, oldPath, newPath, oldPath, oldPath, folderId, projectId]);

    return updatedFolder;
  });
}
```

The circular reference check in step 3 is essential. Without it, moving folder A into folder A/B/C would create an infinite loop in the tree: A → B → C → A → B → C → ... The check uses LTREE's `<@` operator to determine if the target parent's path is a descendant of the folder being moved. If it is, the move is rejected.

## Delete Folder Implementation

Before executing the SQL DELETE (which cascades to child folders and dataset records), the service must first delete physical files from disk. The query to find all affected files:

```sql
SELECT d.file_path FROM datasets d
INNER JOIN folders f ON d.folder_id = f.id
WHERE f.path <@ (SELECT path FROM folders WHERE id = $1)
AND f.project_id = $2
```

This uses LTREE to find all datasets in the folder AND all descendant folders in a single query. Iterate the file paths and delete each using `fs.promises.unlink`, wrapped in try-catch (ignore ENOENT, log other errors). After all files are cleaned up, execute `DELETE FROM folders WHERE id = $1 AND project_id = $2`. The CASCADE constraint handles child folders and dataset records automatically.

## Acceptance Criteria

- Root folder creation works when parentFolderId is null or omitted
- Nested folder creation correctly sets LTREE path via database trigger
- Creating a folder with duplicate name under same parent returns 409 Conflict
- GET /tree returns all descendants ordered by LTREE path (depth-first traversal)
- GET /breadcrumb returns ordered ancestor chain from project root to current folder
- Move operation updates paths for the moved folder AND all descendants atomically
- Moving a folder into its own subtree returns 400 with circular reference message
- Moving a folder to a different project returns 400
- Delete removes physical files for all datasets in the subtree before removing DB records
- GET with parentId=null returns only root-level folders for the specified project
- Each folder in list responses includes accurate childCount
- GET /api/projects/:projectId/folders/:folderId returns folder with children.folders and children.datasets arrays
- PUT with only name field performs rename without LTREE path recalculation
- POST to non-existent project returns 404
- POST with parentFolderId belonging to a different project returns 400
