# BE-019: Implement Cursor-Based Pagination for Large Collections

**Palantir Feature:** Data Ingestion — Foundry efficient data browsing (constant-time pagination for large collections)

## Reuse from Ontology Engine (Daily Tasks)

**Wednesday Task 5** (`/src/services/paginationService.js`) already implements cursor-based pagination using OpenSearch's `search_after` parameter:
- Base64-encoded `pageToken` containing the sort values of the last document
- `$pageSize` validation (1–10,000, default 100)
- `hasNextPage` detection by fetching `pageSize + 1` results
- Token encoding/decoding with error handling

**What to reuse vs. build new:**
- **REUSE** the cursor encoding/decoding pattern from Wednesday Task 5 — the `base64url(JSON.stringify({ sortValue, id }))` approach is identical to what's needed here, just adapted from OpenSearch `search_after` to PostgreSQL keyset pagination
- **REUSE** the `hasMore` detection pattern (fetch `limit + 1`, slice to `limit`) — already proven in Wednesday's implementation
- **BUILD NEW** the PostgreSQL keyset condition SQL (Wednesday uses OpenSearch `search_after` which works differently from SQL `WHERE (col, id) > (val, id)`), the deprecation headers, and the `prevCursor` support (Wednesday only provides `nextPageToken`)
- **IMPROVE** Wednesday's pagination by adding backward navigation (`prevCursor`), which the ontology-engine currently lacks. Consider backporting this to the object query API

## Objective

Add cursor-based pagination to the dataset listing, project listing, and folder listing endpoints alongside the existing offset-based pagination. Cursor-based pagination provides constant-time performance regardless of page depth (offset-based degrades because `OFFSET N` requires scanning N rows). Existing offset parameters (`page`, `limit`) remain functional with a deprecation header to signal migration.

## Target Endpoints

The following list endpoints receive cursor pagination:

1. `GET /api/projects` (from BE-003)
2. `GET /api/projects/:projectId/folders` (from BE-004)
3. `GET /api/projects/:projectId/folders/:folderId/datasets` (from BE-007)

## CursorPagination Helper Class

Create `src/utils/CursorPagination.ts`:

```typescript
interface CursorPaginationOptions {
  sortColumn: string;  // The column to sort by (e.g., 'updated_at', 'name')
  sortOrder: 'asc' | 'desc';
  limit: number;       // Items per page (default 20, max 100)
  cursor: string | null; // base64url-encoded cursor from previous response, or null for first page
}

interface CursorPaginationResult<T> {
  data: T[];
  nextCursor: string | null;  // null when there are no more pages
  prevCursor: string | null;  // null on the first page
  hasMore: boolean;
}
```

### Cursor Encoding

A cursor encodes the sort value and ID of the last item on the current page:

```typescript
// Encode: creates a cursor string from a row
function encodeCursor(sortValue: unknown, id: string): string {
  return Buffer.from(JSON.stringify({ sortValue, id })).toString('base64url');
}

// Decode: parses a cursor string back into its components
function decodeCursor(cursor: string): { sortValue: unknown; id: string } {
  try {
    return JSON.parse(Buffer.from(cursor, 'base64url').toString('utf-8'));
  } catch {
    throw new AppError(400, 'Invalid cursor format');
  }
}
```

### SQL Keyset Condition

The `apply()` method modifies any Knex `QueryBuilder`:

```typescript
apply(query: Knex.QueryBuilder, options: CursorPaginationOptions): Knex.QueryBuilder {
  const { sortColumn, sortOrder, limit, cursor } = options;

  if (cursor) {
    const { sortValue, id } = decodeCursor(cursor);
    // Keyset condition: (sort_col, id) > (decoded_sortValue, decoded_id)
    // Direction flips for DESC sort
    const op = sortOrder === 'asc' ? '>' : '<';
    query.where(function() {
      this.where(sortColumn, op, sortValue)
        .orWhere(function() {
          this.where(sortColumn, '=', sortValue)
            .andWhere('id', op, id);
        });
    });
  }

  query.orderBy(sortColumn, sortOrder).orderBy('id', sortOrder);
  query.limit(limit + 1); // Fetch one extra to detect hasMore

  return query;
}
```

### Result Processing

After executing the query:

```typescript
processResults<T extends { id: string }>(rows: T[], limit: number, sortColumn: string, cursor: string | null): CursorPaginationResult<T> {
  const hasMore = rows.length > limit;
  const data = hasMore ? rows.slice(0, limit) : rows;

  const nextCursor = hasMore ? encodeCursor(data[data.length - 1][sortColumn], data[data.length - 1].id) : null;
  const prevCursor = cursor && data.length > 0 ? encodeCursor(data[0][sortColumn], data[0].id) : null;

  return { data, nextCursor, prevCursor, hasMore };
}
```

`prevCursor` is the encoding of the first row in the current page. It is `null` when `cursor` input is `null` (i.e., on the first page). The frontend can use `prevCursor` to navigate backward, but backward navigation requires reversing the sort order and the keyset operator.

## Applying to Each Endpoint

### GET /api/projects

Accept new query params: `?cursor=<string>&limit=20&sort=updated_at&order=desc`. When `cursor` is present, use keyset pagination. When `page` is present (no cursor), use existing offset pagination.

### GET /api/projects/:projectId/folders

Same pattern: `?cursor=<string>&limit=20&sort=name&order=asc`.

### GET /api/projects/:projectId/folders/:folderId/datasets

Same pattern: `?cursor=<string>&limit=20&sort=name&order=asc`. The existing `status` filter from BE-007 applies before the cursor condition.

## Deprecation Headers

When a request uses offset-based pagination (contains `page` parameter but no `cursor`), include these response headers:

```
Deprecation: true
Sunset: 2026-06-01
Link: <https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Deprecation>; rel="deprecation"
```

The offset endpoints continue to work — they are not removed, only deprecated.

## Acceptance Criteria

- GET /api/projects with `?cursor=<valid>` returns the next page using keyset pagination
- GET /api/projects with `?cursor=<invalid>` returns 400 with 'Invalid cursor format'
- Cursor pagination returns same results as offset pagination (data consistency)
- `hasMore: true` when there are more items; `hasMore: false` on the last page
- `nextCursor` is null on the last page
- `prevCursor` is null on the first page (when cursor input is null)
- `prevCursor` is non-null on subsequent pages
- Fetching `limit + 1` rows and slicing to detect `hasMore` (not a separate COUNT query)
- Deprecation headers present when `page` param is used without `cursor`
- Offset pagination (page/limit) still works correctly (backward compatible)
- GET /api/projects/:projectId/folders supports cursor pagination
- GET /api/projects/:projectId/folders/:folderId/datasets supports cursor pagination with status filter
- CursorPagination helper is reusable (used by all three endpoints without duplication)
- Performance: page 1000 of a 100K-row table responds in under 10ms (vs ~500ms with OFFSET 20000)
