# BE-014: Implement Project Settings API with Cascade Statistics

**Palantir Feature:** Project Setup — Managing project settings in Foundry, including viewing project statistics, renaming, updating configuration, and deleting projects with full cascade cleanup.

## Objective

Build the backend API support for the Project Settings page (FE-014). This includes a project statistics endpoint that returns aggregate counts (folders, datasets, total size, members), partial update support on the existing PUT endpoint to handle individual field changes, and cascade delete behavior that cleanly removes all child resources when a project is deleted. The statistics are displayed in the FE-014 danger zone to inform users exactly what will be destroyed on project deletion.

## Project Statistics Endpoint

`GET /api/v1/projects/:projectId/stats`

Returns aggregate statistics for the project, used by the settings page to display project summary information and by the delete confirmation dialog to show cascade impact.

### Query

Compute all statistics in a single query using subqueries to avoid multiple round-trips:

```sql
SELECT
  (SELECT COUNT(*) FROM folders WHERE project_id = $1) AS folder_count,
  (SELECT COUNT(*) FROM datasets d
   JOIN folders f ON f.id = d.folder_id
   WHERE f.project_id = $1) AS dataset_count,
  (SELECT COALESCE(SUM(d.file_size_bytes), 0) FROM datasets d
   JOIN folders f ON f.id = d.folder_id
   WHERE f.project_id = $1) AS total_size_bytes,
  (SELECT COUNT(*) FROM project_members WHERE project_id = $1) AS member_count
```

The `COALESCE(SUM(...), 0)` handles projects with no datasets, returning 0 instead of null.

### Response Shape

```json
{
  "success": true,
  "data": {
    "folderCount": 5,
    "datasetCount": 12,
    "totalSizeBytes": 52428800,
    "memberCount": 3
  }
}
```

The `totalSizeBytes` field is a raw integer. The frontend is responsible for formatting it as human-readable (e.g., "50 MB").

### Error Cases

- Return 404 if the project does not exist.
- Return 403 if the requesting user is not a member of the project (via `authorize()` middleware from BE-014 RBAC).

## Partial Update Support

Extend `PUT /api/v1/projects/:projectId` (originally defined in BE-003) to support partial updates. The request body may contain any combination of the following fields:

```typescript
const UpdateProjectSchema = z.object({
  name: z.string().min(1).max(255).trim().optional(),
  description: z.string().max(1000).trim().optional(),
  defaultRole: z.enum(['viewer', 'editor']).optional()
}).refine(data => Object.keys(data).length > 0, {
  message: 'At least one field must be provided for update'
});
```

### Implementation

Only update the fields that are present in the request body. Build the update object dynamically:

```typescript
async updateProject(projectId: string, updates: Partial<ProjectUpdate>): Promise<Project> {
  const updateData: Record<string, unknown> = {};

  if (updates.name !== undefined) updateData.name = updates.name;
  if (updates.description !== undefined) updateData.description = updates.description;
  if (updates.defaultRole !== undefined) updateData.default_role = updates.defaultRole;

  updateData.updated_at = new Date();

  const [project] = await this.knex('projects')
    .where({ id: projectId })
    .update(updateData)
    .returning('*');

  if (!project) throw new AppError(404, 'Project not found');
  return project;
}
```

### Duplicate Name Detection

The UNIQUE constraint on `(owner_id, name)` (from BE-002) prevents duplicate project names per user. Catch the unique constraint violation:

```typescript
try {
  return await this.updateProject(projectId, updates);
} catch (error) {
  if (error.code === '23505') {
    throw new AppError(409, 'A project with this name already exists');
  }
  throw error;
}
```

Return 409 with `'A project with this name already exists'` so the frontend can display the error inline below the name field.

### Empty Body Rejection

If the request body contains no recognized fields (or is empty), return 400 with `'At least one field must be provided for update'`. This prevents no-op database calls.

## Cascade Delete Behavior

Ensure `DELETE /api/v1/projects/:projectId` (originally defined in BE-003) cleanly removes all child resources. The PostgreSQL `ON DELETE CASCADE` constraints (defined in BE-002's schema) handle most of the cascade automatically:

1. `folders.project_id REFERENCES projects(id) ON DELETE CASCADE` — deleting a project deletes all its folders.
2. `datasets.folder_id REFERENCES folders(id) ON DELETE CASCADE` — deleting folders deletes all their datasets.
3. `dataset_columns.dataset_id REFERENCES datasets(id) ON DELETE CASCADE` — deleting datasets deletes all their column metadata.
4. `project_members.project_id REFERENCES projects(id) ON DELETE CASCADE` — deleting a project removes all membership records.

### File System Cleanup

The `ON DELETE CASCADE` cleans up database records but does NOT clean up uploaded files on disk. Add a pre-delete step to the project deletion logic:

```typescript
async deleteProject(projectId: string): Promise<void> {
  // 1. Collect file paths before deletion (they'll be gone after CASCADE)
  const datasets = await this.knex('datasets')
    .join('folders', 'folders.id', 'datasets.folder_id')
    .where('folders.project_id', projectId)
    .select('datasets.file_path');

  // 2. Delete the project (CASCADE handles DB cleanup)
  const deleted = await this.knex('projects').where({ id: projectId }).delete();
  if (!deleted) throw new AppError(404, 'Project not found');

  // 3. Clean up files on disk (best-effort, don't fail if files are missing)
  for (const dataset of datasets) {
    try {
      await fs.promises.unlink(dataset.file_path);
    } catch {
      // File may already be deleted — log warning but don't throw
    }
  }

  // 4. Remove the project upload directory
  const projectUploadDir = path.join(UPLOAD_DIR, projectId);
  try {
    await fs.promises.rm(projectUploadDir, { recursive: true, force: true });
  } catch {
    // Directory may not exist — ignore
  }
}
```

### Delete Response

Return 204 No Content on successful deletion (no response body).

## Validation

All endpoints validate `projectId` as a UUID. Return 400 for malformed UUIDs.

The stats endpoint requires the user to be a member of the project (any role: viewer, editor, or owner). The update endpoint requires editor or owner role. The delete endpoint requires owner role.

## Acceptance Criteria

- GET /api/v1/projects/:projectId/stats returns `folderCount`, `datasetCount`, `totalSizeBytes`, and `memberCount`
- Stats endpoint returns `totalSizeBytes: 0` for projects with no datasets (not null)
- Stats endpoint returns 404 for non-existent project
- PUT /api/v1/projects/:projectId accepts partial updates (any combination of `name`, `description`, `defaultRole`)
- PUT with only `name` updates only the name and `updated_at`, leaving other fields unchanged
- PUT with only `description` updates only the description
- PUT with only `defaultRole` updates only the default_role column
- PUT with empty body returns 400 with 'At least one field must be provided for update'
- PUT with duplicate project name returns 409 with 'A project with this name already exists'
- PUT trims whitespace from `name` and `description` before saving
- DELETE /api/v1/projects/:projectId cascade-deletes all folders, datasets, dataset_columns, and project_members via ON DELETE CASCADE
- DELETE cleans up uploaded files on disk (best-effort, does not fail if files are missing)
- DELETE removes the project's upload directory
- DELETE returns 204 No Content on success
- DELETE returns 404 for non-existent project
