## BE-021: Implement Standardized HTTP Error Response Contracts

**Palantir Feature:** Platform Infrastructure — Consistent error response shapes across all API endpoints, enabling predictable frontend error handling.

### Objective

Define and enforce exact error response shapes for every HTTP error status code used across the API. FE-021 builds an `ApiErrorHandler` that switches on `error.response.data.error.code` to display contextual toasts, redirect on 401, and render inline validation messages from `details[]`. If the backend returns inconsistent shapes (e.g., some controllers return `{ message }` while others return `{ error: { code, message } }`), the frontend handler breaks. This task ensures ALL error responses from ALL controllers conform to a single contract.

### Implementation

**Error Response Envelope**

Every non-2xx response MUST use this exact JSON shape:

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE_STRING",
    "message": "Human-readable description of the error",
    "details": []
  }
}
```

The `success` field is always `false` for error responses. The `error.code` field is a machine-readable constant string. The `error.message` field is a human-readable sentence suitable for display in a toast. The `error.details` array is optional and only populated for 400 validation errors.

**Status-Specific Contracts**

400 Bad Request (validation errors):
```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": [
      { "field": "name", "message": "Required", "expected": "string", "received": "undefined" }
    ]
  }
}
```

401 Unauthorized (missing or expired token):
```json
{
  "success": false,
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Authentication required. Please log in."
  }
}
```

403 Forbidden (valid token but insufficient permissions):
```json
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this action."
  }
}
```

404 Not Found (resource does not exist or does not belong to user):
```json
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "The requested resource was not found."
  }
}
```

409 Conflict (duplicate name, version mismatch):
```json
{
  "success": false,
  "error": {
    "code": "CONFLICT",
    "message": "A project with this name already exists."
  }
}
```

429 Too Many Requests (rate limit exceeded). Include `Retry-After` header with seconds until the client may retry:
```json
{
  "success": false,
  "error": {
    "code": "RATE_LIMITED",
    "message": "Too many requests. Please try again later.",
    "retryAfter": 30
  }
}
```
Response header: `Retry-After: 30`

500 Internal Server Error (unhandled exceptions, database failures):
```json
{
  "success": false,
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "An unexpected error occurred."
  }
}
```
In development mode (`NODE_ENV=development`), include an additional `stack` field with the full stack trace. In production, never expose stack traces.

**Refactor the Global Error Handler**

Update `src/middleware/errorHandler.ts` to be the single source of truth for error formatting. The error handler must:

1. Check if the error is an instance of `AppError` (operational error). If so, format the response using the status code and code from the AppError instance.
2. Check if the error is a Zod validation error. If so, format as 400 with code `VALIDATION_ERROR` and populate `details[]`.
3. Check for known library errors: `MulterError` (file upload errors) maps to 400 with code `UPLOAD_ERROR`. `JsonWebTokenError` maps to 401 with code `UNAUTHORIZED`. `TokenExpiredError` maps to 401 with code `TOKEN_EXPIRED`.
4. For all other errors, return 500 with code `INTERNAL_ERROR`.

**Audit All Controllers**

Search every controller file for any direct `res.status().json()` calls that return error responses. Replace them with `throw new AppError(statusCode, message, code)` so all errors flow through the global error handler. No controller should format its own error response.

Run this verification after implementation:
```bash
grep -rn 'res\.status\(4\|5' src/controllers/
```
This should return zero results for error status codes. Controllers should only call `res.status(2xx)` for success responses.

**Rate Limiting Headers**

When the rate limiter (from BE-013) triggers a 429 response, it must set the `Retry-After` header and include `retryAfter` in the response body. Update the rate limiter middleware to throw an `AppError(429, 'Too many requests', 'RATE_LIMITED')` with a custom `retryAfter` property rather than sending a response directly.

### Acceptance Criteria

- All 400 responses include `{ success: false, error: { code: 'VALIDATION_ERROR', message, details: [...] } }`
- All 401 responses include `{ success: false, error: { code: 'UNAUTHORIZED', message } }`
- All 403 responses include `{ success: false, error: { code: 'FORBIDDEN', message } }`
- All 404 responses include `{ success: false, error: { code: 'NOT_FOUND', message } }`
- All 409 responses include `{ success: false, error: { code: 'CONFLICT', message } }`
- All 429 responses include `Retry-After` header and `{ success: false, error: { code: 'RATE_LIMITED', retryAfter } }`
- All 500 responses include `{ success: false, error: { code: 'INTERNAL_ERROR', message } }` with no stack trace in production
- No controller file contains direct error response formatting (all errors flow through global error handler)
- The `success` field is present and set to `false` in every error response
- FE-021's `ApiErrorHandler` can switch on `error.response.data.error.code` for all error types without fallback parsing
