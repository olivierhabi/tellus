# BE-006: Implement Folder Tree Retrieval API for Dialog Components

**Palantir Feature:** Project Setup — Folder hierarchy browsing in Foundry dialog components. When creating a new folder or moving a folder, the user selects a parent location from a tree view or dropdown of the project's complete folder structure.

## Objective

Build three folder-related API capabilities that support FE dialog components: (1) a hierarchical folder tree endpoint returning the full nested structure for tree picker components (FE-020 Move Folder Dialog), (2) a flat folder list with depth metadata for dropdown selectors (FE-006 Create Folder Dialog), and (3) ensure the existing `POST /projects/:projectId/folders` endpoint returns the created folder with its computed full path. These endpoints power the parent folder selectors used throughout the frontend.

## Hierarchical Folder Tree Endpoint

`GET /api/v1/projects/:projectId/folders/tree`

Returns the complete folder hierarchy for a project as a nested JSON tree. This endpoint is consumed by the Move Folder Dialog (FE-020), which renders it using Blueprint's Tree component.

### Query

Fetch all folders for the project in a single query:

```sql
SELECT id, name, parent_folder_id, path, depth, created_at
FROM folders
WHERE project_id = $1
ORDER BY depth ASC, name ASC
```

Ordering by `depth ASC` ensures parent folders are processed before their children during tree assembly. The secondary sort by `name ASC` ensures sibling folders are alphabetically ordered within each level.

### Tree Assembly Algorithm

Build the tree in-memory from the flat query result:

```typescript
function buildFolderTree(folders: FolderRow[]): FolderTreeNode[] {
  const nodeMap = new Map<string, FolderTreeNode>();
  const roots: FolderTreeNode[] = [];

  // First pass: create all nodes
  for (const folder of folders) {
    nodeMap.set(folder.id, {
      id: folder.id,
      name: folder.name,
      parentFolderId: folder.parent_folder_id,
      children: []
    });
  }

  // Second pass: link children to parents
  for (const folder of folders) {
    const node = nodeMap.get(folder.id)!;
    if (folder.parent_folder_id === null) {
      roots.push(node);
    } else {
      const parent = nodeMap.get(folder.parent_folder_id);
      if (parent) {
        parent.children.push(node);
      } else {
        // Orphan folder (parent deleted) — treat as root
        roots.push(node);
      }
    }
  }

  return roots;
}
```

### Response Shape

```json
{
  "success": true,
  "data": [
    {
      "id": "uuid-1",
      "name": "Speedrun: Your First E2E Workflow",
      "parentFolderId": null,
      "children": [
        {
          "id": "uuid-2",
          "name": "Raw Data",
          "parentFolderId": "uuid-1",
          "children": [
            {
              "id": "uuid-3",
              "name": "2024",
              "parentFolderId": "uuid-2",
              "children": []
            }
          ]
        }
      ]
    }
  ]
}
```

An empty project (no folders) returns `{ success: true, data: [] }`.

## Flat Folder List Endpoint

`GET /api/v1/projects/:projectId/folders`

Returns all folders as a flat array with depth metadata for rendering indented dropdown selectors. This endpoint is consumed by the Create Folder Dialog (FE-006), which renders each option with `paddingLeft: depth * 20px`.

### Query

```sql
SELECT id, name, parent_folder_id, path, depth, created_at, updated_at
FROM folders
WHERE project_id = $1
ORDER BY path ASC
```

Ordering by `path ASC` (ltree column) produces a depth-first traversal order, which is exactly what's needed for an indented dropdown: parent folders appear immediately before their children.

### Response Shape

```json
{
  "success": true,
  "data": [
    { "id": "uuid-1", "name": "Speedrun: Your First E2E Workflow", "parentFolderId": null, "depth": 0 },
    { "id": "uuid-2", "name": "Raw Data", "parentFolderId": "uuid-1", "depth": 1 },
    { "id": "uuid-3", "name": "2024", "parentFolderId": "uuid-2", "depth": 2 }
  ]
}
```

The `depth` field (computed from the ltree path via `nlevel(path) - 1`) tells the frontend how much to indent each option. Root folders have `depth: 0`.

## Folder Creation Response Enhancement

Ensure `POST /api/v1/projects/:projectId/folders` (originally defined in BE-004) returns the created folder with its full computed path:

```json
{
  "success": true,
  "data": {
    "id": "uuid-new",
    "name": "New Folder",
    "parentFolderId": "uuid-1",
    "projectId": "uuid-project",
    "path": "project_abc.folder_1.folder_new",
    "depth": 2,
    "createdAt": "2024-03-15T10:00:00Z",
    "updatedAt": "2024-03-15T10:00:00Z"
  }
}
```

The `path` field is computed by the folder path trigger (defined in BE-002's schema) and is available immediately after INSERT via `RETURNING *`.

### Duplicate Folder Name Detection

When creating a folder, check for an existing folder with the same name under the same parent within the same project. The UNIQUE constraint on `(project_id, parent_folder_id, name)` (from BE-002) enforces this at the database level. Catch the unique constraint violation and return a structured error:

```typescript
try {
  const [folder] = await trx('folders').insert({
    name, parent_folder_id: parentFolderId, project_id: projectId
  }).returning('*');
  return folder;
} catch (error) {
  if (error.code === '23505') { // PostgreSQL unique violation
    throw new AppError(409, 'A folder with this name already exists in this location');
  }
  throw error;
}
```

Return 409 with `'A folder with this name already exists in this location'` so the frontend can display the error inline on the name field.

## Validation

All folder-related endpoints validate `projectId` as a UUID. Return 400 for malformed UUIDs. Return 404 if the project does not exist.

For the tree and flat list endpoints, no additional body validation is needed (GET requests with no body).

## Performance Considerations

The tree endpoint fetches all folders for a project in a single query. For projects with thousands of folders, this could become slow. However, in the Palantir Foundry Speedrun course context, projects typically contain fewer than 100 folders, so this approach is acceptable. If scaling becomes necessary, consider adding a `maxDepth` query parameter to limit tree depth, or implementing lazy-loading where children are fetched on expand.

The flat list endpoint leverages the ltree `path` column's GIST index for efficient `ORDER BY path ASC` sorting.

## Acceptance Criteria

- GET /api/v1/projects/:projectId/folders/tree returns a nested JSON tree of all folders in the project
- Tree nodes contain `id`, `name`, `parentFolderId`, and `children[]` fields
- Sibling folders within each tree level are sorted alphabetically by name
- Orphan folders (parent deleted) appear as root-level nodes rather than being lost
- GET /api/v1/projects/:projectId/folders returns a flat array of all folders with `depth` metadata
- Flat list is ordered by ltree path (depth-first traversal order suitable for indented dropdowns)
- POST /api/v1/projects/:projectId/folders returns the created folder with `path` and `depth` fields
- Creating a folder with a duplicate name under the same parent returns 409 with descriptive error message
- An empty project (no folders) returns `data: []` for both tree and flat list endpoints
- Invalid projectId format returns 400
- Non-existent projectId returns 404
- Response field names use camelCase
