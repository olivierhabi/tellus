# BE-015: Implement Lightweight Dataset Status Polling Endpoint

**Palantir Feature:** Data Ingestion — Efficient real-time status checking for datasets undergoing CSV parsing. In Foundry, uploaded datasets transition through processing states (pending, processing, ready, error), and the UI polls for updates to reflect progress without requiring a full page reload.

## Objective

Build a minimal, high-performance `GET /datasets/:datasetId/status` endpoint optimized for frequent polling (every 3 seconds per dataset, as consumed by FE-015). The endpoint returns only the dataset's current status and last update timestamp — no schema info, no preview data, no column metadata. It uses HTTP conditional requests (ETag/If-None-Match) to return 304 Not Modified when the status has not changed, minimizing bandwidth and serialization cost for the common case where status is unchanged between polls.

## Endpoint Definition

`GET /api/datasets/:datasetId/status`

### Path Parameters

- `datasetId` (UUID, required) — the dataset to check. Return 404 with `'Dataset not found'` if no dataset exists with this ID.

### Query

Select only the two columns needed — no `SELECT *`, no joins:

```sql
SELECT status, updated_at FROM datasets WHERE id = $1
```

This query touches only the `datasets` table with a primary key lookup (O(1) via B-tree index on `id`). No joins to `folders`, `projects`, `dataset_columns`, or any other table.

### Response Shape

```json
{
  "success": true,
  "data": {
    "status": "processing",
    "updatedAt": "2024-03-15T10:05:30.123Z"
  }
}
```

The response is intentionally minimal. The frontend uses this to update the status badge and decide whether to continue polling. When the status reaches a terminal state (`ready` or `error`), the frontend stops polling and optionally fetches the full dataset detail via `GET /datasets/:datasetId`.

## ETag Implementation

Generate an ETag from the status and updated_at values to support conditional requests:

```typescript
import crypto from 'crypto';

async getDatasetStatus(datasetId: string, req: Request, res: Response) {
  const dataset = await this.knex('datasets')
    .where({ id: datasetId })
    .select('status', 'updated_at')
    .first();

  if (!dataset) {
    throw new AppError(404, 'Dataset not found');
  }

  // Generate ETag from status + updated_at
  const etagSource = `${dataset.status}:${dataset.updated_at.toISOString()}`;
  const etag = `"${crypto.createHash('md5').update(etagSource).digest('hex')}"`;

  // Check If-None-Match header
  if (req.headers['if-none-match'] === etag) {
    res.status(304).end();
    return;
  }

  res.set('ETag', etag);
  res.set('Cache-Control', 'no-cache');

  res.json({
    success: true,
    data: {
      status: dataset.status,
      updatedAt: dataset.updated_at
    }
  });
}
```

### Why ETag and not Last-Modified

The `Last-Modified` header has one-second granularity (HTTP-date format). Dataset status transitions can happen within the same second (e.g., `pending` to `processing` during rapid uploads). ETag, being content-based, correctly detects sub-second changes. Additionally, `Last-Modified` does not account for status rollbacks (e.g., re-parsing a dataset resets status to `pending` with the same `updated_at` second).

### Cache-Control Header

Set `Cache-Control: no-cache` on every response. This instructs the browser (and any intermediate proxies) to always revalidate with the server before using a cached response. Combined with ETag, this means:
- First request: full 200 response with body.
- Subsequent requests (status unchanged): client sends `If-None-Match`, server returns 304 with no body.
- Subsequent requests (status changed): client sends `If-None-Match`, server returns 200 with new body and new ETag.

Do NOT set `Cache-Control: no-store`, which would prevent the browser from caching the response at all and defeat the purpose of ETag.

## Performance Characteristics

This endpoint is designed for high-frequency polling. Performance targets:

- **Query time:** < 1ms (primary key lookup on indexed UUID column).
- **Serialization time:** < 0.1ms (2-field JSON object).
- **304 response:** Zero serialization cost (no body), zero bandwidth cost.
- **Concurrency:** Safe for 100+ concurrent polling clients without contention (read-only query, no locks).

### Column Selection Rationale

The `SELECT status, updated_at` query reads only 2 columns (~60 bytes) versus a full `SELECT *` which reads all 14 columns including the potentially large `schema_info` JSONB field (which can be 100KB+ for datasets with many columns and sample rows). For a polling endpoint called every 3 seconds, this difference compounds significantly.

## Error Cases

- `datasetId` is not a valid UUID format: return 400 with `'Invalid dataset ID format'`.
- Dataset does not exist: return 404 with `'Dataset not found'`.
- Database connection error: return 500 (handled by global error handler).

## Acceptance Criteria

- GET /api/datasets/:datasetId/status returns 200 with `{ status, updatedAt }` for an existing dataset
- Response contains only `status` and `updatedAt` fields — no schema info, no preview, no column metadata
- The SQL query selects only `status` and `updated_at` columns (verified via query logging or EXPLAIN)
- ETag header is present on every 200 response
- Sending the same ETag back via `If-None-Match` returns 304 Not Modified with no response body
- When the status changes (e.g., pending to processing), the ETag changes and a new 200 response is returned
- `Cache-Control: no-cache` header is present on every 200 response
- Non-existent datasetId returns 404
- Invalid UUID format returns 400
- The endpoint performs a primary key lookup only — no joins, no subqueries
- Response time under 5ms for a single dataset status check (measured under normal load)
