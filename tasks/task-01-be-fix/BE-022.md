## BE-022: Implement Progressive Loading Support with Response Timing Headers

**Palantir Feature:** Platform Infrastructure — Server-Timing headers and consistent empty-state response shapes for progressive frontend loading.

### Objective

Add performance observability and consistent response shape contracts so the frontend can implement skeleton screens with confidence. FE-022 renders skeleton placeholders while data loads and needs two guarantees from the backend: (1) every response includes timing metadata so the frontend can adaptively tune skeleton display duration, and (2) empty collections always return the same shape as populated collections so skeleton-to-content transitions never encounter unexpected nulls or missing fields.

### Implementation

**Server-Timing Header Middleware**

Create `src/middleware/serverTiming.ts` that measures request processing time and adds a `Server-Timing` header to every response.

```typescript
import { Request, Response, NextFunction } from 'express';

export function serverTiming(req: Request, res: Response, next: NextFunction) {
  const start = process.hrtime.bigint();

  const originalJson = res.json.bind(res);
  res.json = function (body: any) {
    const end = process.hrtime.bigint();
    const durationMs = Number(end - start) / 1_000_000;
    res.setHeader('Server-Timing', `total;dur=${durationMs.toFixed(2)};desc="Total Processing"`);
    return originalJson(body);
  };

  next();
}
```

Register this middleware in `src/index.ts` immediately after the security headers (helmet) and before route handlers. The `Server-Timing` header is part of the W3C Server Timing specification and is natively parsed by browser DevTools in the Network tab's Timing section. FE-022 reads this header via `response.headers['server-timing']` to log slow responses and adjust skeleton display thresholds.

**X-Total-Count Header for Paginated Responses**

All endpoints that return paginated data must include an `X-Total-Count` response header containing the total number of items across all pages. This allows FE-022's skeleton screens to render the correct number of skeleton rows before data arrives.

Update these endpoints:
- `GET /api/projects` — add `X-Total-Count` header with total project count
- `GET /api/projects/:projectId/folders/:folderId/datasets` — add `X-Total-Count` from the existing `meta.total` value
- Any future list endpoint added by subsequent tasks

The header is set in the controller layer after the service returns the paginated result:

```typescript
res.setHeader('X-Total-Count', String(result.meta.total));
res.setHeader('Access-Control-Expose-Headers', 'X-Total-Count, Server-Timing');
```

The `Access-Control-Expose-Headers` header is required because custom headers are not accessible to frontend JavaScript by default under CORS. Without this header, `response.headers['x-total-count']` returns `undefined` in the browser even though the header is present in the network response.

**Consistent Empty Collection Response Shapes**

Define and enforce these rules for all list endpoints:

1. Empty arrays are returned as `[]`, never as `null`, never omitted from the response.
2. Paginated list responses always include `meta` even when empty:
   ```json
   { "data": [], "meta": { "total": 0, "page": 1, "limit": 20, "totalPages": 0, "hasNext": false, "hasPrev": false } }
   ```
3. Nested arrays within detail responses follow the same rule. For example, `GET /api/projects/:id` returns `root_folders` as `[]` (not `null`) when the project has no folders. Update the SQL query's `FILTER (WHERE f.id IS NOT NULL)` to use `COALESCE(..., '[]'::json)` to guarantee an empty array instead of null.
4. Object fields that are optional use `null` explicitly (never `undefined` or omitted). Every field declared in the TypeScript interface must be present in the JSON response.

**Audit Existing Endpoints**

Review every service method that returns list data and verify:
- `projectService.listProjects()` returns `[]` for users with no projects (not an error, not null)
- `datasetService.listDatasets()` returns `{ data: [], meta: { total: 0, ... } }` when a folder is empty
- `GET /api/projects/:id` returns `root_folders: []` instead of `root_folders: null`
- Folder contents endpoints return `{ folders: [], datasets: [] }` for empty folders

**CORS Configuration Update**

Update the CORS middleware in `src/index.ts` to expose the new headers:

```typescript
cors({
  origin: config.FRONTEND_URL,
  credentials: true,
  exposedHeaders: ['X-Total-Count', 'Server-Timing', 'Retry-After']
})
```

### Acceptance Criteria

- Every API response includes a `Server-Timing` header with processing duration in milliseconds
- `Server-Timing` header format matches W3C spec: `total;dur=12.34;desc="Total Processing"`
- All paginated endpoints include `X-Total-Count` response header
- `X-Total-Count` and `Server-Timing` headers are accessible from frontend JavaScript (exposed via CORS)
- Empty project lists return `{ data: [], meta: { total: 0 } }` shape (not null, not omitted)
- Empty dataset lists return `{ data: [], meta: { total: 0, page: 1, limit: 20, totalPages: 0, hasNext: false, hasPrev: false } }`
- Project detail returns `root_folders: []` for projects with no folders (not null)
- Folder contents returns `{ folders: [], datasets: [] }` for empty folders
- No list endpoint returns null where an empty array is expected
- Response shapes for empty collections are identical to populated collections (same keys, same nesting)
