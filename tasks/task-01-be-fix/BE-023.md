## BE-023: Implement Responsive API Support with Conditional Field Selection

**Palantir Feature:** Data Browsing — Lightweight API responses for mobile and low-bandwidth clients requesting only the fields they need.

### Objective

Add a `?fields=` query parameter to GET list endpoints so the frontend can request a subset of fields per resource. FE-023 builds a responsive layout where mobile views display only project name and status (not description, owner, timestamps, nested folders), reducing payload size by 60-80%. Without server-side field selection, mobile clients download full payloads and discard most fields, wasting bandwidth on metered connections. This task implements sparse fieldsets following the JSON:API sparse fieldsets pattern.

### Implementation

**Field Selection Middleware**

Create `src/middleware/fieldSelection.ts` that parses the `fields` query parameter and attaches the validated field list to the request object.

```typescript
import { Request, Response, NextFunction } from 'express';
import { AppError } from '@/utils/AppError';

interface FieldSelectionConfig {
  allowedFields: string[];
  defaultFields?: string[];
}

export function fieldSelection(config: FieldSelectionConfig) {
  return (req: Request, _res: Response, next: NextFunction) => {
    const fieldsParam = req.query.fields as string | undefined;

    if (!fieldsParam) {
      req.selectedFields = undefined; // undefined means "return all fields"
      return next();
    }

    const requested = fieldsParam.split(',').map(f => f.trim()).filter(Boolean);

    const invalid = requested.filter(f => !config.allowedFields.includes(f));
    if (invalid.length > 0) {
      throw new AppError(400, `Unknown fields: ${invalid.join(', ')}. Allowed: ${config.allowedFields.join(', ')}`, 'VALIDATION_ERROR');
    }

    // Always include 'id' even if not explicitly requested
    if (!requested.includes('id')) {
      requested.unshift('id');
    }

    req.selectedFields = requested;
    next();
  };
}
```

Extend the Express `Request` type in `src/types/express.d.ts`:
```typescript
declare global {
  namespace Express {
    interface Request {
      selectedFields?: string[];
    }
  }
}
```

**Apply to GET /api/v1/projects**

Allowed fields for projects: `id`, `name`, `description`, `owner_id`, `default_role`, `created_at`, `updated_at`.

Route definition:
```typescript
router.get('/',
  authenticate,
  fieldSelection({ allowedFields: ['id', 'name', 'description', 'owner_id', 'default_role', 'created_at', 'updated_at'] }),
  controller.list
);
```

In `projectService.listProjects()`, when `selectedFields` is defined, use Knex's `.select(selectedFields)` instead of `.select('*')`:

```typescript
async listProjects(ownerId: string, fields?: string[]) {
  const query = this.knex('projects').where({ owner_id: ownerId });
  if (fields) {
    query.select(fields.map(f => `projects.${f}`));
  } else {
    query.select('*');
  }
  return query.orderBy('updated_at', 'desc');
}
```

When fields are specified, the SQL query becomes `SELECT id, name, status FROM projects WHERE ...` instead of `SELECT * FROM projects WHERE ...`. This reduces both database I/O (PostgreSQL reads fewer columns from disk) and network transfer (smaller JSON payloads).

**Apply to GET /api/v1/projects/:projectId/folders/:folderId Contents**

Allowed fields for folder contents datasets: `id`, `name`, `status`, `file_size_bytes`, `row_count`, `column_count`, `original_filename`, `mime_type`, `created_at`, `updated_at`.

Allowed fields for folder contents subfolders: `id`, `name`, `depth`, `created_at`.

The folder contents endpoint returns both folders and datasets. The `fields` parameter applies to datasets only. Subfolder data is always minimal so no field selection is needed.

**Backward Compatibility**

When `?fields=` is absent, return all fields exactly as before. No existing API consumer is affected. The `fields` parameter is entirely opt-in.

**Response Shape with Field Selection**

When fields are selected, the response only contains the requested fields plus `id`:

Request: `GET /api/v1/projects?fields=name,status`
Response:
```json
{
  "data": [
    { "id": "uuid-1", "name": "My Project" },
    { "id": "uuid-2", "name": "Another Project" }
  ]
}
```

Note: `status` is not a real project field in this example. The validation would reject it. The frontend must only request fields that exist.

**SQL Injection Prevention**

Field names are validated against the `allowedFields` whitelist before being interpolated into the SQL query. The middleware rejects any field name not in the whitelist with a 400 error. This prevents SQL injection via the `fields` parameter since only pre-approved column names are used in `.select()`.

### Acceptance Criteria

- `GET /api/v1/projects?fields=id,name` returns only `id` and `name` for each project
- `GET /api/v1/projects?fields=name` returns `id` and `name` (id is always included)
- `GET /api/v1/projects` without `fields` parameter returns all fields (backward compatible)
- `GET /api/v1/projects?fields=nonexistent` returns 400 with list of allowed fields
- `GET /api/v1/projects?fields=` (empty value) returns all fields (treated as absent)
- Field names are validated against a whitelist; arbitrary strings cannot be passed to SQL
- The `id` field is always included even when not explicitly requested
- Folder contents endpoint supports `fields` parameter for dataset columns
- SQL queries use `SELECT field1, field2` instead of `SELECT *` when fields are specified
- Response payloads are measurably smaller when fewer fields are requested
- No existing API behavior changes when the `fields` parameter is omitted
