# BE-020: Implement Folder Move API with Circular Reference Prevention

**Palantir Feature:** Project Setup — Moving folders within Foundry's project hierarchy. When a user moves a folder via the Move Folder Dialog (FE-020), the backend must validate the move, prevent circular references, and update the ltree path for the folder and all its descendants.

## Objective

Build the `PUT /projects/:projectId/folders/:folderId` endpoint for moving a folder to a new parent location. The endpoint must validate that the target parent is not the folder itself or any of its descendants (which would create a circular reference), update the folder's `parent_folder_id`, and recursively recompute the ltree path for the moved folder and all of its descendants. Unlike rename (BE-019) which only changes the `name` field, a move changes `parent_folder_id` and triggers a cascade of path updates.

## Endpoint Definition

`PUT /api/v1/projects/:projectId/folders/:folderId`

This endpoint shares the same URL as the rename endpoint (BE-019). The backend differentiates between rename and move based on the request body: if `name` is present, it's a rename; if `parentFolderId` is present, it's a move. Both can be present in a single request (rename and move simultaneously).

### Path Parameters

- `projectId` (UUID, required) — validated against the folder's actual `project_id`. Return 403 if the folder does not belong to this project.
- `folderId` (UUID, required) — the folder to move. Return 404 with `'Folder not found'` if no folder exists with this ID.

### Request Body

```typescript
const MoveFolderSchema = z.object({
  parentFolderId: z.string().uuid().nullable()
  // null means move to project root
});
```

## Circular Reference Prevention

The most critical validation: a folder cannot be moved into itself or any of its descendants. If folder A contains folder B which contains folder C, moving A into C would create a cycle: A → B → C → A. The ltree extension provides an efficient way to detect this.

### Detection Using Ltree Ancestor Check

```typescript
async moveFolder(projectId: string, folderId: string, newParentFolderId: string | null): Promise<Folder> {
  // 1. Verify folder exists and belongs to this project
  const folder = await this.knex('folders')
    .where({ id: folderId, project_id: projectId })
    .first();

  if (!folder) {
    throw new AppError(404, 'Folder not found');
  }

  // 2. Check if already in the requested location
  if (folder.parent_folder_id === newParentFolderId) {
    throw new AppError(400, 'Folder is already in this location');
  }

  // 3. Cannot move folder to itself
  if (newParentFolderId === folderId) {
    throw new AppError(400, 'Cannot move folder into its own descendant');
  }

  // 4. If moving to a non-root parent, validate the target
  if (newParentFolderId !== null) {
    const targetParent = await this.knex('folders')
      .where({ id: newParentFolderId, project_id: projectId })
      .first();

    if (!targetParent) {
      throw new AppError(404, 'Target parent folder not found');
    }

    // Check if targetParent is a descendant of the folder being moved
    // Using ltree: if targetParent.path is a descendant of folder.path, it's circular
    const isDescendant = await this.knex.raw(
      'SELECT EXISTS(SELECT 1 FROM folders WHERE id = ? AND path <@ ?) AS is_descendant',
      [newParentFolderId, folder.path]
    );

    if (isDescendant.rows[0].is_descendant) {
      throw new AppError(400, 'Cannot move folder into its own descendant');
    }
  }
```

The `path <@ folder.path` ltree operator checks whether the target parent's path is a descendant of (or equal to) the folder's path. This is an O(log n) operation using the GIST index on the `path` column, far more efficient than a recursive CTE traversal.

## Path Update for Folder and Descendants

When a folder moves to a new parent, its ltree path changes (because the parent portion of the path changes). All descendants' paths must also be updated because they include the moved folder's path as a prefix.

### Implementation

```typescript
  // 5. Perform the move in a transaction
  return this.knex.transaction(async (trx) => {
    // Get the old path before update
    const oldPath = folder.path;

    // Update parent_folder_id — the trigger will recompute this folder's path
    const [updated] = await trx('folders')
      .where({ id: folderId })
      .update({
        parent_folder_id: newParentFolderId,
        updated_at: new Date()
      })
      .returning('*');

    const newPath = updated.path;

    // Update all descendant paths: replace the old prefix with the new prefix
    // This uses ltree string manipulation to rewrite paths in bulk
    if (oldPath !== newPath) {
      await trx.raw(`
        UPDATE folders
        SET path = ? || subpath(path, nlevel(?)),
            depth = nlevel(? || subpath(path, nlevel(?))) - 1,
            updated_at = NOW()
        WHERE path <@ ? AND id != ?
      `, [newPath, oldPath, newPath, oldPath, oldPath, folderId]);
    }

    return updated;
  });
}
```

### How the Bulk Path Update Works

The SQL expression `newPath || subpath(path, nlevel(oldPath))` replaces the old prefix of each descendant's path with the new prefix:

- `nlevel(oldPath)` — number of segments in the old path (e.g., 3 for `project.parent.folder`).
- `subpath(path, nlevel(oldPath))` — extracts everything AFTER the old prefix (the descendant-specific suffix).
- `newPath || subpath(...)` — prepends the new prefix to the suffix.

**Example:** Moving folder `B` (path: `P.A.B`) from under `A` to root (path becomes `P.B`):
- Descendant `C` has path `P.A.B.C`
- `subpath('P.A.B.C', nlevel('P.A.B'))` = `subpath('P.A.B.C', 3)` = `C`
- New path: `P.B` || `C` = `P.B.C`

The `WHERE path <@ oldPath AND id != folderId` clause selects all descendants of the moved folder (but not the folder itself, which was already updated by the trigger).

## Duplicate Name Detection at New Location

After computing the new parent, check whether a folder with the same name already exists at the destination:

```typescript
const duplicateAtTarget = await trx('folders')
  .where({ project_id: projectId, name: folder.name })
  .modify((qb) => {
    if (newParentFolderId === null) {
      qb.whereNull('parent_folder_id');
    } else {
      qb.where({ parent_folder_id: newParentFolderId });
    }
  })
  .whereNot({ id: folderId })
  .first();

if (duplicateAtTarget) {
  throw new AppError(409, 'A folder with this name already exists in the target location');
}
```

## Edge Cases

### Moving to Root

When `parentFolderId` is `null`, the folder moves to the project root level. The path trigger recomputes the path as `replace(project_id, '-', '_') || '.' || replace(folder_id, '-', '_')`. Descendants are updated accordingly.

### Moving a Root Folder to a Subfolder

A folder currently at root (parent_folder_id IS NULL) can be moved into any non-descendant subfolder. The path lengthens as the folder gains a parent prefix.

### Large Subtree Moves

Moving a folder with many descendants (e.g., 1000 child/grandchild folders) requires updating all their paths in a single transaction. The bulk `UPDATE ... WHERE path <@ oldPath` query handles this efficiently using the GIST index. For extremely large trees, consider adding an index hint or monitoring query performance.

## Acceptance Criteria

- PUT /api/v1/projects/:projectId/folders/:folderId with `{ parentFolderId: "uuid" }` moves the folder and returns 200 with the updated folder object
- PUT with `{ parentFolderId: null }` moves the folder to the project root
- Moving a folder into itself returns 400 with 'Cannot move folder into its own descendant'
- Moving a folder into any of its descendants returns 400 with 'Cannot move folder into its own descendant'
- Circular reference detection uses ltree `<@` operator (verified via EXPLAIN showing GIST index usage)
- Moving a folder to its current parent returns 400 with 'Folder is already in this location'
- All descendant paths are updated correctly after a move (verified by querying descendants and checking path prefixes)
- Descendant depths are updated to reflect the new hierarchy level
- Moving a folder with no descendants does not execute the bulk path update query
- Non-existent folderId returns 404
- Non-existent target parentFolderId returns 404
- Folder belonging to a different project returns 403
- Duplicate folder name at target location returns 409
- All path updates occur within a single database transaction (atomicity)
- Response field names use camelCase
