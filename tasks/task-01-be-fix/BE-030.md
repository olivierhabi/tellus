## BE-030: Implement Accessibility Support with Semantic API Metadata

**Palantir Feature:** Platform Infrastructure — API-level accessibility support ensuring screen readers and assistive technologies receive well-structured, descriptive content from all endpoints.

### Objective

Ensure all API responses are optimized for frontend accessibility. FE-030 implements ARIA attributes, keyboard navigation, and screen reader announcements. Many of these frontend features depend on backend response quality: error messages must be human-readable sentences (not cryptic codes), paginated responses need descriptive link metadata for screen reader navigation, and response headers must declare the content language. This task adds the backend conventions and headers that make FE-030's accessibility features work correctly.

### Implementation

**Content-Language Header**

Add a middleware that sets `Content-Language: en-US` on every API response:

```typescript
// src/middleware/contentLanguage.ts
import { Request, Response, NextFunction } from 'express';

export function contentLanguage(req: Request, res: Response, next: NextFunction) {
  res.setHeader('Content-Language', 'en-US');
  next();
}
```

Register this middleware in `src/index.ts` alongside other global middleware. The `Content-Language` header tells assistive technologies which language the response content is in, enabling screen readers to select the correct pronunciation engine. Without this header, screen readers default to the user's OS language setting, which may mispronounce English field names and error messages for non-English users.

**Descriptive Pagination Links**

Update all paginated responses to include a `links` object with `rel` and `title` fields that screen readers can use for navigation:

```json
{
  "data": [...],
  "meta": { "total": 150, "page": 2, "limit": 20, "totalPages": 8 },
  "links": {
    "self": { "href": "/api/v1/projects?page=2&limit=20", "rel": "self", "title": "Current page (page 2 of 8)" },
    "first": { "href": "/api/v1/projects?page=1&limit=20", "rel": "first", "title": "First page" },
    "prev": { "href": "/api/v1/projects?page=1&limit=20", "rel": "prev", "title": "Previous page (page 1)" },
    "next": { "href": "/api/v1/projects?page=3&limit=20", "rel": "next", "title": "Next page (page 3)" },
    "last": { "href": "/api/v1/projects?page=8&limit=20", "rel": "last", "title": "Last page (page 8)" }
  }
}
```

When on the first page, omit `prev`. When on the last page, omit `next`. The `title` field provides context that FE-030 renders as `aria-label` on pagination buttons. The `rel` field follows the IANA Link Relations standard (RFC 8288).

Create a pagination links utility in `src/utils/paginationLinks.ts`:

```typescript
interface PaginationInput {
  basePath: string;
  page: number;
  limit: number;
  totalPages: number;
}

export function buildPaginationLinks(input: PaginationInput) {
  const { basePath, page, limit, totalPages } = input;
  const links: Record<string, { href: string; rel: string; title: string }> = {};

  links.self = { href: `${basePath}?page=${page}&limit=${limit}`, rel: 'self', title: `Current page (page ${page} of ${totalPages})` };
  links.first = { href: `${basePath}?page=1&limit=${limit}`, rel: 'first', title: 'First page' };
  links.last = { href: `${basePath}?page=${totalPages}&limit=${limit}`, rel: 'last', title: `Last page (page ${totalPages})` };

  if (page > 1) {
    links.prev = { href: `${basePath}?page=${page - 1}&limit=${limit}`, rel: 'prev', title: `Previous page (page ${page - 1})` };
  }
  if (page < totalPages) {
    links.next = { href: `${basePath}?page=${page + 1}&limit=${limit}`, rel: 'next', title: `Next page (page ${page + 1})` };
  }

  return links;
}
```

**Human-Readable Error Messages**

Audit all `AppError` instantiations and error handler output to ensure every error includes a human-readable `message` field. Screen readers announce error messages via ARIA live regions (FE-030 sets `aria-live="assertive"` on toast containers). The messages must be complete sentences, not codes or abbreviations.

Rules for error messages:
- Always start with a capital letter and end with a period
- Use plain language, no technical jargon (e.g., "The project could not be found." not "ENOENT: no such entry")
- Include context when possible (e.g., "A project named 'Analysis' already exists." not "Duplicate entry")
- Never expose internal details (table names, column names, SQL errors) in production messages
- For validation errors, each `details[].message` must be a complete phrase (e.g., "Project name is required." not "Required")

Review and update these specific error messages:
- 404 errors: "The requested {resource} was not found." (where resource is project/folder/dataset)
- 409 conflicts: "A {resource} with this name already exists."
- 401 errors: "Your session has expired. Please log in again."
- 403 errors: "You do not have permission to access this {resource}."
- File upload errors: "The file could not be uploaded. {reason}."

**Field Naming Conventions Documentation**

Document API field naming conventions in a comment block at the top of `src/types/common.ts` (or create this file if it does not exist):

```typescript
/**
 * API Field Naming Conventions (Accessibility)
 *
 * All API response fields follow these rules for screen reader compatibility:
 * - Use camelCase for JSON response fields (matches JavaScript convention)
 * - No abbreviations: use "description" not "desc", "configuration" not "config"
 * - Boolean fields start with "is" or "has": "isDefault", "hasNext", "isOperational"
 * - Date fields end with "At": "createdAt", "updatedAt", "parsedAt"
 * - Count fields end with "Count": "rowCount", "columnCount", "totalCount"
 * - ID fields end with "Id": "datasetId", "projectId", "folderId"
 *
 * These conventions ensure screen readers can parse field names into
 * pronounceable words when developers inspect API responses.
 */
```

**CORS Exposed Headers Update**

Ensure `Content-Language` is included in the CORS `exposedHeaders` configuration so the frontend can read it:

```typescript
cors({
  origin: config.FRONTEND_URL,
  credentials: true,
  exposedHeaders: ['X-Total-Count', 'Server-Timing', 'Retry-After', 'Content-Language']
})
```

### Acceptance Criteria

- Every API response includes the `Content-Language: en-US` header
- `Content-Language` header is accessible from frontend JavaScript (exposed via CORS)
- Paginated responses include a `links` object with `self`, `first`, `last`, and conditional `prev`/`next`
- Each link includes `href`, `rel`, and `title` fields
- `links.prev` is omitted on the first page; `links.next` is omitted on the last page
- `links.title` provides human-readable page context (e.g., "Current page (page 2 of 8)")
- All error messages are complete, human-readable sentences starting with a capital letter and ending with a period
- No error response exposes internal implementation details (table names, SQL, stack traces) in production
- Validation error details include descriptive messages (not just "Required" but "Project name is required.")
- Field naming conventions are documented in `src/types/common.ts`
- Boolean fields use `is`/`has` prefix; date fields use `At` suffix; count fields use `Count` suffix
- The `buildPaginationLinks` utility is used by all paginated endpoints
