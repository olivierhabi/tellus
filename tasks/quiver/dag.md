### Notes on a few subtle edges

- **F5 before F3.** The brief explicitly states `F5 (card registry + plugins) blocks F3, F4, F6 — without plugins there is nothing to render.` Hence F5 precedes F3 within Phase 2. The spec's "Depends on: F2, F5" on F3 confirms.
- **B3 deferred to Phase 3.** `submitInstructions` is implemented as a stub-with-401 in Phase 1 so F2 can be unit-tested in isolation; full server-side OT lands in Phase 3 per the recommended sequencing (`B3 → F8`).
- **F2 ↔ B3.** F2's OT client property test (1000-instruction convergence) uses a shared in-memory transport (no real WS/B3 server). Real-WS convergence is GATE-01 after F8 + B3.
- **F4 after F2.** F4 reads from the same shared store as F3; the spec's "Depends on: F2".
- **Cross-phase rebound.** If a downstream task surfaces a defect in a `DONE` upstream, the upstream is re-opened (with a new test that fails before the fix and passes after) and the downstream blocks until upstream is re-`DONE`.
